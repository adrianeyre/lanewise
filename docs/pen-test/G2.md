# G2 — arguments chosen by refs, URLs and paths

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #19, label `prd:pen-test`). G2 probes whether a name a Hostile repository or a remote chooses — a ref from `packed-refs` or a fetch, a remote's name or URL, a path — can reach the `git` command line as an option rather than as the value it is. It starts from H7.

- **Trust boundary.** The names in a Hostile repository's `packed-refs`, the names a remote hands back on a fetch, and the URLs and paths in its `.git/config`, on one side; the `git` command line Lanewise builds, on the other. Between them are `core/src/git.rs` (how `git` is started), `core/src/branch.rs`, `core/src/merge.rs`, `core/src/remote.rs`, `core/src/remote_config.rs` and `core/src/commit_actions.rs` (where the arguments are chosen).
- **Governed by.** `CONTEXT.md`: Label, Upstream, Hostile repository, Finding. ADR 0002 (the system `git`, run as an argument list), ADR 0009 (branches changed through `git`, a new name checked first), ADR 0010 (merges made through `git merge`), ADR 0014 (remotes managed through `git remote`, each change `--`-guarded).
- **Deliverables.** `core/tests/hostile_ref_arguments.rs`, which pins what held:
  - `a_local_ref_whose_name_starts_with_a_dash_is_refused_before_git_runs`: a branch or tag whose short name starts with `-` is refused, and no ref changes;
  - `checking_out_a_remote_tracking_branch_whose_name_starts_with_a_dash_makes_no_branch`: checking out `origin/-u` makes no branch and leaves `HEAD` on `main`;
  - `a_remote_url_starting_with_a_dash_is_stored_as_a_url_not_read_as_an_option`: a remote URL starting with `-` is stored as a URL, and nothing runs it.

## How it was probed

This was done headless on Linux, with `gix` 0.88.0 (the version in `Cargo.lock`) and `git` 2.47.3. Everything was written under `/tmp`. Nothing was fetched from a Host, and nothing was committed but the deliverables.

1. **Built E1's Hostile repositories** with `pnpm pen-test:fixtures`, and used `refs-and-tags`, which carries branches and tags whose short names start with `-` (`refs/heads/-u`, `refs/heads/--output=pwned`, `refs/heads/--upload-pack=touch`, `refs/tags/-n`) both in its own `packed-refs` and on a local remote `git fetch --all` reads into `refs/remotes/origin/*`.
2. **Read every `.command([…])` the six files in scope build** (`git grep "\.command("`), and for each asked: is the name on it one a Hostile repository chose, and if so is there a `--` before it, or a check it can't be passed round?
3. **Ran the core itself** against `refs-and-tags` in a scratch crate under `/tmp` that depends on `lanewise-core` by path, calling `read_branches`, `delete_branch`, `rename_branch`, `check_out` (every `CheckOut`), `preview_merge`, `set_upstream`, `create_tag`, `delete_tag` and `rename_tag` with the `-`-named refs, and listed the refs before and after.
4. **Ran `git switch --create <name> --track …`** on its own with each `-`-named branch, and with real `git switch` options as the name (`--orphan`, `--discard-changes`, `-C`, `--no-track`), to see whether `git` reads the name as an operand or re-parses it as an option.
5. **Pinned what held** in the tests above.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Refs from `packed-refs` and from a remote whose names start with `-`

**What I did.** Opened `refs-and-tags` through the core and called every branch, merge and tag entry point with the `-`-named local branches and tags it carries in `packed-refs`, and with the `-`-named `origin/*` remote-tracking branches a fetch left.

**What I read.** Every branch operation that takes a name looks it up first through a guard that rejects a leading `-`:

- `create_branch`, `rename_branch`, `delete_branch` and the `Branch` and `BranchAt` arms of `check_out` go through `check_branch` / `check_new_name`, which call `is_branch_name` — `!name.is_empty() && !name.starts_with('-') && name != "HEAD"` (`core/src/branch.rs:522`) — and, for a new name, `git check-ref-format` as well. A `-`-named branch stops as `NotFound` or `InvalidName` before any `git branch` or `git switch` runs (`core/src/branch.rs:267`, `:276`, `:302`, `:340-392`).
- `preview_merge` / `merge` of a local branch go through `check_branch` too (`core/src/merge.rs:304-307`). The name `git merge` is then given is either the short name, taken only when `!short.starts_with('-')`, or its full `heads/…` / `remotes/…` form, which can't start with `-` (`core/src/merge.rs:316-334`).
- `create_tag`, `delete_tag`, `rename_tag` each reject a name starting with `-` (`core/src/commit_actions.rs:167-215`, `valid_tag_ref` at `:460-473`), and `create_tag` / `delete_tag` pass the name after `--` as well.

**What held.** Every local-ref operation refused the `-`-named refs before `git` ran, and no ref changed (`a_local_ref_whose_name_starts_with_a_dash_is_refused_before_git_runs`).

The one name a Hostile remote chooses that is **not** passed through Lanewise's own `is_branch_name` guard is the short branch name taken from a remote-tracking branch in the `RemoteBranch` arm of `check_out`: `origin/-u` yields the new local branch name `-u`, given to `git switch --create -u --track refs/remotes/origin/-u` with no `--` (`core/src/branch.rs:363-383`). Here the only thing between the name and `git` is `git`'s own `check-ref-format`. Probe 3 shows it holds; `checking_out_a_remote_tracking_branch_whose_name_starts_with_a_dash_makes_no_branch` pins that the checkout makes no branch and `HEAD` stays on `main`. That this control is a single layer is noted below.

### 2. Remote URLs and paths starting with `-`

**What I read.** Every `git remote` change puts `--` before its operands: `git remote add -- <name> <url>`, `git remote rename --no-progress -- <from> <to>`, `git remote set-url -- <name> <url>`, `git remote remove -- <name>` (`core/src/remote_config.rs:116-142`), as ADR 0014 records. `check_url` only trims a URL; the `--` is what stops a URL starting with `-` being read as an option (`core/src/remote_config.rs:218-226`). A clone is `git clone --progress -- <url> <destination>` (`core/src/clone.rs:47-54`), and `set_upstream` is `git branch --set-upstream-to=refs/remotes/<upstream> -- <branch>` (`core/src/remote_config.rs:171-173`).

The command lines that reach the network — `fetch`, `pull`, `push` — carry **no** URL, remote name or ref a Hostile repository chose: `git fetch --all --prune --progress` is fixed (`core/src/remote.rs:280`), `git pull` adds only Lanewise's own flags (`core/src/remote.rs:303-321`), and `git push` puts the remote and refspec after `--` (`core/src/remote.rs:387-392`, `:487`). A URL a Hostile `.git/config` holds is read by `git` from the config, never placed on the command line by Lanewise. (Clone URLs, transports and submodules — including option-like URLs read from config — are G4's.)

**What held.** A remote URL starting with `-` is stored as a URL and nothing runs it (`a_remote_url_starting_with_a_dash_is_stored_as_a_url_not_read_as_an_option`). `check_new_remote` also rejects a remote *name* starting with `-` (`core/src/remote_config.rs:198-209`).

### 3. Every place `git` is run with a name Lanewise didn't make: is there a `--`, or a check that can't be passed round?

**What I did.** Walked every `.command([…])` in the six files in scope and, for the names a Hostile repository could choose, checked for a `--` or a guard; then ran `git switch --create <name> --track …` on its own with each `-`-named branch and with real `git switch` options as the name.

**What I read.** The names a Hostile repository chooses fall into three groups:

| How it's protected | Where |
| --- | --- |
| `--` before the operand | `git remote add/rename/set-url/remove --` (`remote_config.rs`), `git push --` (`remote.rs:392`, `:487`), `git clone --` (`clone.rs:49`), `git tag --annotate --file=- --`, `git tag --delete --` (`commit_actions.rs`), `rev-parse … --end-of-options` for a tag ref (`commit_actions.rs:208-213`) |
| A Lanewise check that rejects a leading `-` before `git` runs | branch names via `is_branch_name` + `check-ref-format` (`branch.rs`), merge source name via `!short.starts_with('-')` fallback to the full ref (`merge.rs`), tag names via `starts_with('-')` + `check-ref-format` (`commit_actions.rs`), remote names via `check_new_remote` (`remote_config.rs`) |
| Built by Lanewise, so never starts with `-`: a `refs/…` full ref, a `^`- or `HEAD...`-prefixed revision range, a hex commit id, a `--flag=value` whose value holds the name | `update-ref … <refs/…>` (`remote.rs:531`, `commit_actions.rs`), `rev-list … ^<id>` and `HEAD...<ref>` (`remote.rs:649`, `:674`, `merge.rs:356`), `--exclude=<name>`, `--remotes=<remote>`, `--set-upstream-to=<ref>`, `--source=<tree>` |

`git` reads an argument list, never a shell (`core/src/git.rs:168-181`), so none of these can be read as shell syntax; the question is only option injection.

The single place a Hostile-remote-chosen name reaches `git` with neither a `--` nor a Lanewise check is the `--create <remote.branch>` of the `RemoteBranch` checkout. Running it by hand showed `git switch --create` takes the token after it as the new branch's name **operand** even when the token is itself a real `git switch` option: each of `-u`, `--orphan`, `--discard-changes`, `-C` and `--no-track` was reported by `git` as `'…' is not a valid branch name` (its `check-ref-format`), and no branch was made. So the name is never re-parsed as an option, and the leading-dash case is refused.

**What held.** Every `git` Lanewise runs with a name a Hostile repository chose is guarded by a `--`, by a Lanewise check that rejects a leading `-` before `git` runs, or (in the one `RemoteBranch` checkout case) by `git`'s own `check-ref-format`, which refuses the name as an operand without ever reading it as an option. No probe made any argument act as an option, and no marker fired.

One observation is carried to the owner as defence in depth, not as a Finding with a way to do harm: the `RemoteBranch` checkout's new-branch name is the only Hostile-chosen name whose leading-dash protection is a single layer (`git`'s), where create, rename and delete each have Lanewise's own `is_branch_name` in front of `git`'s. It is in the private message as **G2-1**.

## Hand checks (need the owner)

Do this once on macOS and once on Windows, in the disposable account of the rules of engagement (§3), with the latest Release installed. The marker folder is `lanewise-pen-test-markers` in the OS temp folder: `$TMPDIR` on macOS, `%TEMP%` on Windows.

**A. The `-`-named refs through the UI**

1. In a clone of this tree, run `pnpm pen-test:fixtures`. It says where the Hostile repositories are.
2. Delete the marker folder, open Lanewise and open the `refs-and-tags` folder.
3. In the Branches & remotes Widget and the Commit graph, find the branches and tags whose names start with `-` (`-u`, `--output=pwned`, `-n`), and the `origin/*` ones a fetch brought in. For each, try from its menu: check out, rename, delete, merge into the current branch, and (for a remote-tracking branch) check out a local branch from it; and set one as the current branch's Upstream.
4. After each, note what Lanewise said, whether `HEAD` or any ref moved unexpectedly, and whether the marker folder holds anything (`pwned`, `touch`).
5. Record, for each step, what happened. A ref made to act as an option, or any marker, is a lead: file it as PRD §7 says, privately first under PRD §4.
