# R2 — The release workflow's secrets and tokens

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #28, label `prd:pen-test`). R2 asked what in `release.yml` runs beside the Update key and the jobs' tokens, and what a package or build script among them could take or do. It starts from H12. It is also the first of PRD §8's pre-conditions for setting the Update key.

- **Trust boundary.** On one side, the release workflow's secrets (the Update key's private half and its password, and the Windows signing secrets) and each job's `GITHUB_TOKEN`. On the other, every package, build script, proc macro, plugin and tool that runs in the same job.
- **Governed by.** `CONTEXT.md`: Release, Update key, Update, Finding. ADR 0029 (Releases by semantic-release), ADR 0030 (Updates signed by the Update key), ADR 0052 (Releases unchanged once published), and the new ADR 0053. `SECURITY.md`: "a way into the release workflow, its secrets or the packages on a Release".
- **Deliverables**, as defence in depth, made while the Update key's public half is still empty, so there was nothing yet to take:
  - ADR 0053, `docs/architectural-decision-record/0053-the-update-key-in-a-job-of-its-own-that-only-main-can-use.md`. The build jobs never have the Update key. A `sign` job in a `release` environment that only `main` can use signs the update packages. It installs and builds nothing, and checks the tag before it signs. Each job's token is narrowed to what it needs. ADR 0030, ADR 0052, `CONTEXT.md`'s Update key, `docs/releases.md` and `docs/development.md` point to it.
  - `.github/workflows/release.yml`: no Update key in the Windows or macOS job; the Mac's build gets a throwaway key so Tauri makes its `.app.tar.gz` (`:229`); the new `sign` job (`:291`); `publish` needs it, and its token reaches only its two `gh` steps; every checkout of the Release's tag names `refs/tags/` in full; the website's build (`:443`) is split from its deploy (`:493`).
  - `app/scripts/release/updater.ts sign`: a minisign signer of Lanewise's own on Node's `crypto`. It reads a key as `tauri signer generate` writes it, checks it against the committed public half, and signs as Tauri does, with the version in the trusted comment (`:194`, `:223`, `:363`).
  - `app/scripts/release/versionCommit.ts`: checks that a Release's tag is the commit merged and semantic-release's version commit, and nothing more (`:46`).
  - Tests, each checked to fail when what it holds is broken:
    - `updater.test.ts`, nine new tests on `sign`, with keys made by `tauri signer generate` in the test;
    - `versionCommit.test.ts`, seven tests against throwaway repositories;
    - `desktop/tests/updater.rs`, `a_package_the_release_script_signed_downloads`: the real updater plugin takes packages `sign` signed, and refuses them announced as another version;
    - `app/scripts/workflows.test.ts`, ten new tests on `release.yml`'s secrets, tokens, `sign` job and checkouts.
  - A fixture for those tests, `app/scripts/release/fixtures/signed/`: the stand-in packages, signed by `updater.ts sign` with a throwaway key whose private half was deleted after signing, its public half, and the `latest.json` the script wrote.

## How it was probed

This was done headless on Linux (Debian 13), with Node 26 and the tree at `75479b9`. The versions were Tauri CLI 2.12.2, `tauri-plugin-updater` 2.13.3, semantic-release 25.0.9, `@semantic-release/github` 12.0.10, `@semantic-release/git` 11.0.1, `@semantic-release/npm` 13.2.0 and Vite 8.3.4, as the lockfiles have them. The workflows were checked with actionlint 1.7.12 and shellcheck 0.11.0 before and after. Nothing was sent to GitHub but reads of its public sources and documentation. Scratch files and throwaway keys were made under `/tmp` and deleted.

1. **Counted what the build step runs** from `cargo metadata --filter-platform` for `x86_64-pc-windows-msvc` and `aarch64-apple-darwin`, walking `lanewise-desktop`'s normal and build dependencies, and from `pnpm-lock.yaml`'s snapshots for what Vite's config and semantic-release load.
2. **Read** `release.yml`, `ci.yml`, `codeql.yml`, `.releaserc.json`, `pnpm-workspace.yaml`, `app/vite.config.ts`, `desktop/tauri.conf.json`, the release scripts, and the sources of `@semantic-release/github`, Tauri CLI 2.12.2's `sign_updaters`, and `actions/checkout` and `actions/download-artifact` at the versions the workflow pins.
3. **Made throwaway keys** with `tauri signer generate`, with and without a password. Decrypted them with Node, signed stand-in packages with `updater.ts sign`, and checked the signatures with Tauri's verifier in the real plugin and with `updater.ts`'s own. Tauri's signatures are randomized, so the two signers' bytes differ each time, and each verifies the other's.
4. **Built a debug `.deb`** with `createUpdaterArtifacts` on, a public key from one throwaway key, and another throwaway key given as a file path. Tauri warned that the key doesn't match and still made and signed the update package, which is what the Mac's build now relies on.
5. **Ran the new `sign` steps' shell** in a scratch copy of the tree, in three cases: no key; a key and its public half; the public half with no key. Then ran `publish`'s manifest step on what the artifacts would merge into. They gave a notice and nothing signed; both packages signed and a `latest.json` for all six platforms; and a failure naming what's missing.
6. **Broke each behaviour the new tests hold**, one at a time, in a copy of the tree that wasn't committed. Signing a package not named for its version failed `only packages named for the version are signed…`. Signing without the version in the trusted comment failed `with the key tauri signer generate made…`.

## Probes from the brief

### 1. Which build scripts, proc macros and Vite plugins run in the step that holds `TAURI_SIGNING_PRIVATE_KEY`

**What I read.** At `75479b9`, the two secrets went to the Windows build step (`release.yml:184-188`), the macOS build step (`:264-266`), and an `Update key` step before each (`:165`, `:250`). That step ran only `updater.ts --how` and `node -p`. The build step ran `pnpm desktop:build`, which is `updater.ts build` → `tauri build` → `beforeBuildCommand` `pnpm build` (`desktop/tauri.conf.json:9`) → `vite build`, then `cargo build`, then the bundler. On Windows that's NSIS with `signWindows.ts`; on macOS, the disk image script. `app/vite.config.ts:4-7` loads `@vitejs/plugin-react`, `vitest/config` and the first-party `credits` plugin, which runs `cargo metadata` (`app/scripts/credits.ts:188`). `pnpm install` ran in an earlier step without the secrets. Of the install scripts `allowBuilds` names, only esbuild's runs (`pnpm-workspace.yaml:6-9`).

**Answer.** In that one step, for each platform:

| What runs | Windows | macOS |
| --- | --- | --- |
| Crates compiled | 430 | 430 |
| Build scripts, each run as a program | 59 | 61 |
| Proc macros, each run inside the compiler | 30 | 28 |
| npm packages Vite's config loads, one native binding per platform among them | up to 127 | up to 127 |
| Vite plugins | `@vitejs/plugin-react`, and Lanewise's own `credits` | the same |
| Tools | the Tauri CLI (a native binary from npm), the NSIS bundler, `signWindows.ts` | the Tauri CLI, the disk image script, `signMacos.ts` |

Any of them could read the step's environment. Moving the key to a later step of the same job wouldn't have kept it from them: every step of a job runs on one runner as one user. **Answered with a deliverable:** ADR 0053 takes the key out of both build jobs. The test `the build jobs never have the Update key, and the Mac's only a throwaway one made beside it` holds that.

### 2. What `semantic-release` and its plugins can do with the job's token

**What I read.** The `release` job's token has `contents`, `issues` and `pull-requests: write` (`release.yml:53-55` at `75479b9`). It is given only to the step that runs `pnpm exec semantic-release` (`:80-85`). Checkout keeps no credentials (`:66`), and `pnpm install` runs before it with none. That step loads about 314 npm packages, counted from the lockfile, all in one Node process with the token in its environment. `@semantic-release/github` creates the draft Release (`lib/publish.js:70-101`). On success it comments on and labels the issues and pull requests it released, through REST and GraphQL (`lib/success.js:81-318`). On failure it opens or comments on an issue (`lib/fail.js:77-93`). `@semantic-release/git` pushes the version commit to `main` and the tag. GitHub's documentation: a `GITHUB_TOKEN` expires when its job ends, and never has the `workflows` permission.

**Answer.** Any code in that process can do whatever the token can, until the job ends. That covers pushing commits, branches and tags that branch protection doesn't stop it from pushing, creating and editing Releases and their files (drafts, and published ones until release immutability is on, ADR 0052), and opening, editing, commenting on and labelling issues and pull requests. It can't change a workflow file, read a secret or change a setting. The parts that decide what users get are now checked outside that job:

- **What is signed and published is the commit merged.** The `sign` job runs `versionCommit.ts` from `github.sha`, not from the tag, before it signs (`release.yml:314`). The check fails unless the tag's one parent is the commit merged, it changes only `CHANGELOG.md` and the version in `package.json`, and both are plain files. `publish` needs `sign`, and the website waits for `publish`.
- **The tag is built as a tag.** Given a bare name, `actions/checkout` takes a branch of that name over the tag (its `src/ref-helper.ts`). So the build jobs, `publish` and the website now check out `refs/tags/<tag>` in full (`:136`, `:206`, `:373`, `:460`), and build what `sign` checks.
- **Its token can't reach the key.** The key is in another job, on another runner, in an environment only `main` can use. The token is dead by the time that job runs.

What `main`'s branch protection allows is R3's (TODO(#29)), as are the caches restored into these jobs. **Answered with deliverables**, held by `the sign job checks the tag against the commit merged…`, `every job that checks out the Release's tag names it in full…` and `versionCommit.test.ts`.

### 3. Whether each job has the narrowest permissions it can

**What I read.** Every job's `permissions` and every step's `env` at `75479b9`, and what each job's steps call.

**Answer.** Three jobs had more than they used, and are narrowed:

- **`publish`** gave `GH_TOKEN` to the whole job (`:310-311`), so `checkout`, `setup-node`, `download-artifact` and both Node scripts had a `contents: write` token they didn't use. It's now on the two steps that run `gh` alone.
- **`website`** had `pages` and `id-token: write` (`:396-397`) in the job that runs `pnpm install` and the website's build. The build is now its own job with `contents` and `pages: read`, and a `deploy` job with the two write permissions runs `deploy-pages` and nothing else.
- **The Update key** was a repository secret, which reaches a workflow on any branch. ADR 0053 moves it to a `release` environment that only `main` can use (hand check 1).

The rest already had the least they could:

| Job | Token | Why it's the least it can be |
| --- | --- | --- |
| `verify` | `contents: read` | checks out the tree |
| `release` | `contents`, `issues`, `pull-requests: write` | semantic-release's tag, version commit and draft Release need `contents`. Its comments and labels on what it released (ADR 0029) need the other two, which ADR 0053 leaves for the owner to drop if they choose |
| `windows`, `macos` | `contents: read` | the workflow's own; the Windows signing secrets reach only its build step, since Tauri signs while it bundles (ADR 0029) |
| `sign` | `contents: read` | new; checks out `github.sha` |
| `pages` | `pages: read` | reads whether Pages is on |

No `${{ }}` expression is interpolated into any `run:` script, in any workflow. Every job that names a value from outside passes it through `env`. `each job's token can do what that job needs, and nothing more`, `a write token reaches only the steps that use it` and `no secret or token is put in a job's or a workflow's environment…` hold all of it.

### 4. Whether the signing could move to a step that runs no third-party code

**What I read.** Tauri CLI 2.12.2's `sign_updaters`. It signs every update package after bundling. It reads the key from a string or a file path, takes the password from the environment, and only warns when the key isn't the one whose public half is configured. It skips signing under `--no-sign`, which also skips the Mac's ad hoc code signature. The updater plugin's macOS install unpacks every entry below the archive's first folder (`src/updater.rs:1421-1440`). `updater.ts` already verified minisign signatures with Node's own Ed25519 and BLAKE2b-512.

**Answer: yes, and it has.** It is a job, not a step, for the reason in probe 1. ADR 0053 has the alternatives and why each was left out. The `sign` job runs four of GitHub's own actions, pinned to commits, with `setup-node` given no cache, then Node and two of Lanewise's scripts. Neither script imports anything but Node's own modules. Nothing is installed and nothing is built. The Mac's update package is still Tauri's own archive, made in the build with a throwaway key. Its signature is discarded, and `sign` signs the package with the Update key. The signer is Lanewise's own, and the real plugin accepts what it signs. Held by `the Update key's secrets reach one step of one workflow: the sign job's`, `the sign job installs and builds nothing…`, `the scripts the sign job runs import only Node's own modules` and `a_package_the_release_script_signed_downloads`.

What it can't change: the key signs what the build made, so a dependency that changes the app it's built into still gets signed. Keeping the key out of the build stops the key being taken, not the build being changed.

## Hand checks (need the owner)

**A. The `release` environment**

1. In `adrianeyre/lanewise`, **Settings → Environments → New environment**, name it `release`.
2. Under **Deployment branches and tags**, choose **Selected branches and tags** and add `main` alone.
3. Add `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` as its **Environment secrets** when the key is made (`docs/releases.md`, "The Update key"). In **Settings → Secrets and variables → Actions**, check that neither is a repository secret.
4. Optionally, add yourself under **Required reviewers**.
5. Write the date in H12's row above.

**B. The first Release after this merges**

1. On its run, check that the jobs are `verify`, `release`, `Windows installer`, `macOS app (universal)`, `Update packages`, `publish`, `pages`, `Project website` and `Deploy the project website`, and that all of them passed.
2. In `Update packages`' log, check that `The tag is what was merged` says the tag "is … and its version commit for …, and nothing more". Before the key is set, check that `Update key` leaves the "No update package" notice.
3. Check that the Release has its disk image and installer, and that the project website deployed.
4. If any of these doesn't hold, file it as PRD §7 says.

**C. The first Release with the Update key**

1. Do ADR 0053's hand checks 2 and 3. `Update packages` signs both packages. `publish` writes `latest.json`. From the Release before it, the Update installs on a Mac and on Windows, as ADR 0030's hand check 4 says.
2. Do ADR 0053's hand check 4: a workflow on another branch that names `environment: release` doesn't get the key.
3. Write the date and the Release in H12's row above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).
