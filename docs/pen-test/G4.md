# G4 — clone URLs, transports and submodules

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #21, label `prd:pen-test`). G4 probes what `git clone` and `git fetch` do with a URL the user pastes or a Host lists: the transports Git will take, where a clone is written, whether Lanewise ever reaches into a repository's submodules, and what a credential helper is told about the Host. It starts from §6 G4.

- **Trust boundary.** A URL the user pastes into Clone, or a Host lists in Browse repositories, and the repository it brings, on one side; the user's file system, their credential helpers and the programs Git can run, on the other. Between them are `core/src/clone.rs` (the clone and its destination), `commands/src/clone.rs` (the folder's name), `core/src/remote.rs` (fetch and pull), `core/src/credential.rs` (Lanewise's own `git credential`) and `core/src/git.rs` (how `git` is started).
- **Governed by.** `CONTEXT.md`: Host, Base folder, Hostile repository, Finding. ADR 0012 (clones through `git clone`, with Git's own sign-in, and a stopped clone's folder removed), ADR 0013 (fetch, pull and push through `git`, as a clone is), with ADR 0016 (Host Integrations sign in through `git credential`) and ADR 0039 (the Base folder).
- **Deliverables.** `core/tests/clone_transports.rs`, its own test binary with a user configuration that turns submodule recursion on and allows `file` submodules, which pins what held:
  - `a_url_naming_the_ext_transport_runs_nothing_and_leaves_nothing`: Git refuses `ext::`, its command never runs, and nothing is left;
  - `a_superproject_is_cloned_checked_out_fetched_and_pulled_without_its_submodules`: a clone, a checkout, a fetch and a pull of a superproject whose `.gitmodules` names a local path and an `ext::` URL initialize no submodule and clone none;
  - `a_clone_whose_tree_names_a_parent_folder_fails_and_leaves_nothing_beside_its_destination`;
  - `a_destination_that_is_a_symbolic_link_is_refused_and_where_it_points_is_left_as_it_was` (macOS and Linux);
  - `the_credential_helper_is_asked_about_the_url_s_own_host_and_never_one_its_user_part_names`: a name before the `@` goes to the helper as the user's name, and a newline in the URL is refused before the helper is asked anything.

## How it was probed

This was done headless on Linux, with `gix` 0.88.0 (the version in `Cargo.lock`) and `git` 2.47.3. Everything was written under `/tmp`. Nothing was fetched from a Host: the only Host was a stand-in HTTP server on `127.0.0.1`, and nothing was committed but the deliverables.

1. **Built E1's Hostile repositories** with `pnpm pen-test:fixtures`, and used `submodules`, `config-and-attributes` and `paths`, with a superproject of real submodules made for probe 3.
2. **Ran the core itself**, in a scratch crate under `/tmp` that depends on `lanewise-core` by path, calling `clone_repository`, `check_out`, `fetch`, `pull`, `read_status` and `Credentials::fill_quietly` as the commands do. A marker folder was cleared before each step and listed after it.
3. **Pointed Git at a configuration of the probe's own**, as a user's would be, with `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM`: none at all, then `submodule.recurse = true`, then that with every submodule active, `file` submodules allowed and `fetch.recurseSubmodules = true`; and a credential helper that writes down what Git tells it.
4. **Read** every `git` the clone, fetch and pull run, and every place the UI hands a URL or a folder to `startClone` (`app/src/welcome/CloneForm.tsx`, `app/src/hosts/BrowseRepositories.tsx`).
5. **Pinned what held** in the tests above.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Transports other than `https` and `ssh`: `ext::`, `file://`, local paths, `fd::`

**What I read.** A clone is `git clone --progress -- <url> <destination>`, run as an argument list from the destination's parent folder (`core/src/clone.rs:46-56`); the URL is only trimmed, and a blank one is refused before Git runs (`core/src/clone.rs:39-42`). Lanewise chooses no transport and allows or refuses none itself: what Git takes is Git's `protocol.allow` policy and the user's configuration, as ADR 0012 says. Every `git` runs with `GIT_TERMINAL_PROMPT=0` and an empty stdin (`core/src/git.rs:166-181`). In the UI, the URL is what the user typed, or the one a Host listed for the repository they chose, put into the same field before Clone is pressed (`app/src/hosts/BrowseRepositories.tsx:273`, `app/src/welcome/CloneForm.tsx:125`).

**What I did and what held.**

| URL | What happened |
| --- | --- |
| `ext::sh -c touch% <marker>` | Git refused it, `transport 'ext' not allowed`; no marker; nothing left at the destination (`a_url_naming_the_ext_transport_runs_nothing_and_leaves_nothing`) |
| `fd::5`, `fd::0,1` | Git waits on the file descriptor, with no progress, until Cancel; Cancel stopped it in two seconds and left nothing (as ADR 0012's Cancel does for a Host that never answers) |
| `file://` and a local path to `config-and-attributes` | Cloned, as the user asked. The clone takes the source's objects and refs, never its configuration or hooks, so none of the source's armed programs ran; no marker |
| `<name>::<address>`, a remote helper Git doesn't have | Git says `'remote-<name>' is not a git command`, and nothing ran |
| `--upload-pack=touch <marker>`, `-c<option>` | Read as a repository's path, because of the `--` (already pinned by `a_url_is_never_read_as_an_option`, `core/tests/clone.rs:260`); no marker |

`ext::` is refused by Git's own default, which a user can change in their configuration, as they can on the command line; Lanewise adds nothing to it either way.

### 2. A clone's destination: symbolic links, existing folders, paths outside the Base folder

**What I read.** `startClone` takes a parent folder and a name, and refuses a name that is blank, `.` or `..`, or holds `/`, `\` or a NUL (`commands/src/clone.rs:140-143`, `:226-232`). The core then requires a full path whose parent is a folder, and looks at the destination with `fs::symlink_metadata`, never following a link: nothing there, or a real, empty folder, is cloned into; anything else is refused before Git runs (`core/src/clone.rs:97-118`). A clone that doesn't finish has what it made removed, a link as a link (`core/src/clone.rs:121-152`). The name follows the URL's last part until the user types one (`app/src/welcome/cloneUrl.ts:8`), and `.` or `..` there gives no name.

**What I did and what held.**

- **Symbolic links.** A destination that is a link to an empty folder, a link to nothing and a link to a folder with a file in it were each refused as `DestinationExists`, and the folder each pointed at was left as it was (`a_destination_that_is_a_symbolic_link_is_refused_and_where_it_points_is_left_as_it_was`). `git clone` itself would clone through a link to an empty folder, so this is Lanewise's own check.
- **Existing folders.** A folder with something in it, or a file, is refused and left untouched (already pinned by `a_destination_with_something_in_it_is_refused_and_left_as_it_was`, `core/tests/clone.rs:240`); an empty folder is cloned into and kept if the clone stops.
- **A tree that names `..`.** A repository whose checked-out tree names `..` fails in Git's checkout (`invalid path '..'`), and Lanewise removes the whole clone, leaving nothing beside it (`a_clone_whose_tree_names_a_parent_folder_fails_and_leaves_nothing_beside_its_destination`). A relative destination is refused as `NoParentFolder`.
- **Outside the Base folder.** The Base folder is where Clone starts, not a boundary: the user may choose any folder (`CONTEXT.md`, ADR 0039), so a clone outside it is the user's choice. What a repository can choose is held to the destination's one folder: the name can't climb, and the tree's own paths are Git's to check (as G3 found for checkouts).

Windows' own names (`CON`, a trailing dot, a `:`) and a junction in place of a link can't be shown on Linux. Hand check B does them.

### 3. Submodules with hostile URLs and paths, and whether Lanewise ever recurses into them

**What I read.** Nothing in `core/src/`, `commands/src/` or `desktop/src/` runs `git submodule` or passes `--recurse-submodules`; the clone, checkouts, fetch and pull take none (`core/src/clone.rs:46-54`, `core/src/branch.rs:308-404`, `core/src/remote.rs:280`, `:303-321`). ADR 0012 says submodules are left uninitialised. The only place the core opens a submodule's repository is to name the commit a checked-out one is at, for a diff, by the path the index gives it (`core/src/diff.rs:362-393`); it reads `HEAD` there and nothing else.

**What I did and what held.**

- E1's `submodules` repository and a superproject of real submodules (one at a local path, one over `ext::`) were cloned through the core, then a remote branch that moves both submodules on was checked out, then fetched and pulled. With no configuration and with `submodule.recurse = true`, no submodule was initialized, none was cloned, `.git/modules` was never made, and no marker appeared (`a_superproject_is_cloned_checked_out_fetched_and_pulled_without_its_submodules`, which also allows `file` submodules so that a recursion would show).
- Only with a user configuration that also marks every submodule active (`submodule.active`) and fetches every submodule did Git itself reach for one; it failed on the folder it found empty, and never ran the `ext::` URL. That is the user's own configuration, and Git does the same on the command line.
- The hostile paths in `.gitmodules` (one climbing out of the superproject) are never read by Lanewise: nothing appeared outside the clone, and the status, through `gix`, read nothing there.
- For comparison, `git clone --recurse-submodules`, which Lanewise never runs, refuses both the `ext::` submodule (`transport 'ext' not allowed`) and, by Git's default, the local-path one (`transport 'file' not allowed`).

### 4. What the credential prompt is told about a host, and whether a URL can choose it

**What I read.** Two things ask a credential helper:

- **Git, for a clone, fetch, pull or push.** It asks the user's helpers, such as Git Credential Manager, about the host in the URL, as on the command line (ADR 0012, ADR 0013). Lanewise only sets `GIT_TERMINAL_PROMPT=0`.
- **Lanewise, for a Host Integration's API.** `git credential fill` is sent `protocol=https` and `host=<host>` and nothing else (`core/src/credential.rs:150-174`), and only after `check_host` has allowed a name of letters, digits, `.` and `-` with an optional port, so nothing in it can end a line or begin another field (`core/src/credential.rs:201-212`, pinned by `only_asks_about_a_host_s_name`). The Host comes from Settings or from the repository's remote URL (`commands/src/hosts/mod.rs:206-221`), and is only asked about if a Host Integration serves it: GitHub.com and the GitHub Enterprise Server Hosts the user added for Pull Requests (`commands/src/hosts/github.rs:121-129`, `commands/src/hosts/mod.rs:103-112`). The credential it gives is sent to that Host's own API, and nowhere else. Read without the user asking, it's asked for with `GCM_INTERACTIVE=never` and an empty `GIT_ASKPASS` (`commands/src/hosts/github.rs:236-241`, `core/src/credential.rs:155-162`).

**What I did and what held.** Cloned from a stand-in Host on `127.0.0.1` that asks every request for credentials, through the core, with a helper that writes down what it's told:

| URL | What the helper was told |
| --- | --- |
| `http://127.0.0.1:<port>/…` | `protocol=http`, `host=127.0.0.1:<port>` |
| `http://github.com@127.0.0.1:<port>/…` | `host=127.0.0.1:<port>`, `username=github.com`: the part before `@` is the user's name on the Host, never the Host |
| a newline in the host, or the path, such as `%0ahost=github.com` | Nothing: Git refused the URL (`url contains a newline`) before asking |
| a carriage return in the path | Only the host, as above: the path isn't sent to the helper |

The Sign-in Failure that followed named the host Git had asked about (`127.0.0.1`), and the helper's password never reached the message. The first two rows and the newline are pinned by `the_credential_helper_is_asked_about_the_url_s_own_host_and_never_one_its_user_part_names`. So a URL chooses the Host a credential is asked for, and that is always the Host it is sent to; it can't name one Host to the helper and send the credential to another.

## Hand checks (need the owner)

Do these once on macOS and once on Windows, in the disposable account of the rules of engagement (§3), with the latest Release installed. The marker folder is `lanewise-pen-test-markers` in the OS temp folder: `$TMPDIR` on macOS, `%TEMP%` on Windows. On Windows, Git for Windows' own `sh` runs the markers' commands.

**A. Transports through Clone**

1. In a clone of this tree, run `pnpm pen-test:fixtures`. It says where the Hostile repositories are.
2. Delete the marker folder. In Lanewise's Welcome screen, Clone each of these URLs, one at a time, into a new folder in a disposable folder:
   - `ext::sh -c touch% <marker folder>/clone-ext`
   - `fd::5`, then press Cancel after a few seconds;
   - `file:///<fixtures>/config-and-attributes` (on Windows, `file:///C:/…` with forward slashes);
   - the plain path of `config-and-attributes`.
3. After each, note what Lanewise said, list the marker folder, and check the disposable folder holds only what that clone made (nothing, for one that failed or was cancelled).

**B. A clone's destination**

1. On macOS, make an empty folder, `target`, and a link to it beside the disposable folder: `ln -s <target> <disposable>/linked`. On Windows, make a junction and a link: `mklink /J <disposable>\junction <target>` and, with Developer Mode on, `mklink /D <disposable>\linked <target>`.
2. Clone `submodules` into each of `linked` and `junction`, by choosing the disposable folder and typing the name. Each should be refused, saying it already exists; check `target` is still empty.
3. On Windows, Clone `submodules` with each of these names: `CON`, `name.`, `name `, `name:stream`. Note what Lanewise said for each, and check nothing but a folder of that name (or nothing) was made in the disposable folder, and that a cancelled or failed clone left nothing.
4. Record, for each step, what happened. A clone written anywhere but the folder named, or through a link, is a lead: file it as PRD §7 says, privately first under PRD §4.

**C. Submodules**

1. In a terminal, run `git config --global submodule.recurse true`.
2. Delete the marker folder. Clone `submodules` through Lanewise. Check its `.git` folder has no `modules` folder, and that its submodule folders are empty.
3. In its Commit graph, check out the other branches if it has any, Fetch and Pull from the Toolbar, and check again. List the marker folder.
4. Run `git config --global --unset submodule.recurse` to put the setting back.

**D. Git Credential Manager's sign-in**

1. With Git Credential Manager installed, as Git for Windows has it and as `docs/installing.md` says for macOS, and no credential kept for GitHub, Clone a private repository of the round's GitHub.com account (E2) by its HTTPS URL, with `lanewise-pen-test@` before `github.com`.
2. Note which Host and which account Git Credential Manager's window names, and that the clone succeeds after signing in.
3. Remove the credential it kept (Keychain Access on macOS, Credential Manager on Windows), and record what was shown.
