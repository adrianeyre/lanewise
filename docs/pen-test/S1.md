# S1 — keys and tokens crossing IPC

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #22, label `prd:pen-test`). S1 probes the secrets the core keeps and what the command API hands the main webview of them. It starts from H8.

- **Trust boundary.** On one side are the secrets the core keeps in the OS credential store: Model Provider and Jev keys (ADR 0020, ADR 0036), Gateways' headers (ADR 0035) and Issue Tracker tokens (ADR 0038). On the other is the main webview, which holds `call` and so every command the command API has (ADR 0003). Between them are the command API's replies, its errors and its Logs, and the webview's own memory and tools.
- **Governed by.** `CONTEXT.md`: Model Provider, Gateway, Issue Tracker, Jev, Logs, Finding. ADR 0020, ADR 0022, ADR 0023, ADR 0024, ADR 0035, ADR 0038, with ADR 0028 (the Logs) and ADR 0050 (the main webview's policy). `SECURITY.md`.
- **Deliverables.** Tests that pin what held:
  - `a_request_carrying_a_secret_that_cant_be_read_never_says_the_secret` in `commands/src/lib.rs`;
  - "no Model Provider's key, or Jev's, is left in the page's memory once its request is answered" in `app/src/ai/apiKeyLifetime.test.ts`;
  - "a release build can't open devtools" in `app/scripts/release/tauriConfig.test.ts`.

  Each was checked to fail when its rule is broken: a request whose secret is sent where a list is expected, a connection kept in a module of the UI, and Tauri's `devtools` feature turned on.

## How it was probed

This was done headless on Linux, with Node 26, Tauri 2.12.3, `tauri-runtime-wry` 2.12.1, wry 0.57.0, `tokio` 1.53.1 and `tauri-plugin-http` 2.8.2, the versions in `Cargo.lock` and `pnpm-lock.yaml`. Everything was written under `/tmp`. No key was a real one, nothing was sent to a Model Provider, Gateway, Issue Tracker or Host, and nothing was committed but the deliverables.

1. **Read** every command's response and error type in the command API (`commands/src/lib.rs`, the table at its top), the four the brief names in full, the UI's callers of each command that reads or saves a secret, the Desktop App's `call` (`desktop/src/lib.rs`), and the parts of Tauri and wry that decide whether a webview has devtools.
2. **Ran the UI's own AI code** in Vitest under `/tmp`, against a stand-in credential store that made a canary key afresh for each read, and a `fetch` that answered as each API does without keeping the request. It listed models for Anthropic, Gemini, OpenAI, xAI and Meta, asked Anthropic, Gemini and OpenAI for a Suggestion, and asked Jev. After each, it wrote a V8 heap snapshot and searched every string in it for the key. Two controls, a connection and a bare key kept on purpose, were each found once.
3. **Ran the command API's `call`** with requests that carry a canary secret and can't be read, and looked for the secret in each reply and log line.
4. **Ran `cargo metadata`** for the features every target resolves for `tauri`, `tauri-runtime`, `tauri-runtime-wry` and `wry`.
5. **Pinned what held** in the tests above.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Every command that returns a secret to the UI, and why

**What I read.** All 87 commands' responses and errors (`commands/src/lib.rs:16-104`). The ones that read, keep or use a secret:

| Command | What it hands the UI |
| --- | --- |
| `modelProviderKey` (`commands/src/model_provider.rs:200`, `:238`) | **The key itself**, for a Model Provider or for Jev (`typesafe-jev`), or `null` |
| `modelProviderKeyStored`, `saveModelProviderKey`, `forgetModelProviderKey` | Whether a key is kept; `null` |
| `gatewayOf`, `saveGateway`, `forgetGateway` | A Gateway's address and its headers' names, never a value; `null` (W4) |
| `gatewayRequest` | The Gateway's answer, with a kept header's value never added by the core (W4) |
| `issueTrackerAccount`, `saveIssueTrackerAccount` | Jira's site and email, and the name the Issue Tracker gave; never the token or key (`commands/src/issues/mod.rs:109`, `:121`) |
| `issues` | Issues: key, title, status, page and when it changed |
| `signInToHost`, `hostRepositories`, `hostOwners`, `pullRequests` | Who signed in, and what the Host lists; never the token Git Credential Manager gave (`commands/src/hosts/mod.rs:322`) |
| `branches` | Remotes, with any credentials in a URL hidden as `***` (`commands/src/branches.rs:199`) |
| `diagnostics` | Versions, and the Logs' latest lines redacted again (S3's) |

Every error type that can carry a message was read for a secret. A credential store's error carrying what it read is said without it (`commands/src/model_provider.rs:145`, and the same in `commands/src/issues/mod.rs`). A rejected request's message is serde's (`commands/src/lib.rs:451`).

**Why `modelProviderKey` hands a key out.** Each Model Provider's SDK runs in the page, on the platform's `fetch`, so the page must put the key in the request (ADR 0020, ADR 0022 to ADR 0024). Jev's request is made by the page the same way (ADR 0036). Only two places call it: `connect` (`app/src/ai/requests.ts:75`) and Jev's `ask` (`app/src/ai/jev.ts:88`). `connect` is reached only through `listModels` and `requestSuggestion`, after AI is on and that Model Provider's First-use disclosure is accepted (`requests.ts:101-104`, `:137-143`). The core itself doesn't check either: it answers whoever calls, as every command does (W1, H1). Gateway headers and Issue Tracker tokens never leave the core, since the core makes those requests.

**What the runs showed.** Requests to `saveModelProviderKey`, `saveGateway`, `gatewayRequest` and `saveIssueTrackerAccount`, each carrying a canary secret and each unreadable in another way (a bad ID, a field missing, a field too many, an unknown Issue Tracker, a key sent as a list or an object), were all rejected, and no reply or log line said the secret. A string sent where a command takes something else is quoted in the rejection's message, which is why the Logs leave that message out (`commands/src/logs.rs:162`). The UI's `CommandClient` is typed by `app/src/commands/api.ts`, so it never sends one.

**Answer.** One command returns a secret: `modelProviderKey`, for the reason above, as ADR 0020 documents. No other reply hands the page a secret the core keeps.

### 2. Whether a key outlives its request in the UI's memory or state

**What I read.**

- `connect` reads the key for the one request and puts it in a `Connection` (`app/src/ai/requests.ts:62-82`). `listModels` and `requestSuggestion` hold that `Connection` in a local, and nothing else keeps it.
- Each adapter builds its SDK's client for one request from the `Connection` (`app/src/ai/anthropic.ts:63`, `app/src/ai/gemini.ts:93`, `app/src/ai/openAiCompatible.ts:138`). The one thing an adapter remembers between requests is which way of asking for JSON worked for a base URL and model, without the key (`openAiCompatible.ts:240`).
- Jev reads the key, puts it in one request's `authorization` and lets it go (`app/src/ai/jev.ts:88`, `:104`).
- Settings' key and token fields are emptied once saved (`app/src/settings/ModelProviderSettings.tsx:584`, `app/src/settings/JevSettingsSection.tsx:114`, `app/src/issues/IssueTrackerSettings.tsx:126`). A test already checks that a saved key isn't in local storage or on the page (`app/src/settings/ModelProviderSettings.test.tsx:102`).
- No Activity's words name a secret (`app/src/ui/commandActivity.ts:100-106`), and the Desktop App's `call` and `fetch` keep no record of a request or a reply (`app/src/platform/tauri.ts:69`, `:88`). The HTTP plugin closes each request's resource once it's sent.

**What the runs showed.**

| Run | Strings on the heap holding the key, once it was answered |
| --- | --- |
| `listModels` for Anthropic, Gemini, OpenAI, xAI and Meta, each | 0 |
| `requestSuggestion` for Anthropic, Gemini and OpenAI, with an `AbortSignal` kept alive across the run, as the AI Suggestion Widget keeps its own | 0 |
| `askJev`, with the same signal | 0 |
| Control: a `Connection` kept on `globalThis` | 1 |
| Control: the key alone kept on `globalThis` | 1 |

**Answer: disproved, in V8.** Once a request is answered, nothing in the UI holds its key: not React's state, not local storage, not an SDK's client and not a listener on a signal that lives on. The new test pins it. A string isn't wiped when it's let go; it stays in memory the webview owns until the garbage collector reuses it, as in any JavaScript app. The test runs in Node's V8, the engine WebView2 uses on Windows. macOS's WebKit is hand check B.

### 3. Whether a release build can open devtools

**What I read.**

- wry turns a webview's devtools on only in a build with debug assertions or its `devtools` feature. Its default is `devtools: false` without debug assertions (wry 0.57.0, `src/lib.rs:871-875`), and `tauri-runtime-wry` 2.12.1 only passes Tauri's setting on under the same condition (`src/lib.rs:5146-5148`). So in a release build:
  - on Windows, WebView2's `AreDevToolsEnabled` is false (`src/webview2/mod.rs:640`), which takes away the context menu's Inspect and F12;
  - on macOS, the webview isn't made inspectable and the private developer-extras key isn't set (`src/wkwebview/mod.rs:537-549`), so Safari's Develop menu can't attach to it;
  - `open_devtools` isn't compiled in at all.
- `desktop/Cargo.toml` asks Tauri for `unstable` alone. `cargo metadata` resolves no `devtools` feature for `tauri`, `tauri-runtime`, `tauri-runtime-wry` or `wry`, on any target, with dev dependencies included.
- `tauri build`, which `pnpm desktop:build` runs (`app/scripts/release/updater.ts:91`), builds the release profile. No `Cargo.toml` or Cargo config in the tree sets debug assertions. `release.yml` sets only the dev and test profiles' debug info, and runs `pnpm desktop:build` with no `--debug` or `--features`.
- No window in `desktop/tauri.conf.json`, or the Windows or macOS configs over it, asks for devtools.
- The Host pages' child webviews are made the same way (`desktop/src/host_pages.rs:187`), so they have none either.

**Answer: no.** A release build has no devtools in either webview. The new test holds the features, the profile, the release workflow's build and the windows to that. Hand check A checks it on a Release. Ways the OS gives to inspect a webview from outside the app need code already running as the user, which could read the credential store itself; who else can read that is S2's (#23).

### 4. Whether a secret can reach a panic, an error or a response the UI shows

**What I read.**

- **Panics.** A command runs on a blocking thread (`desktop/src/lib.rs:51`). If it panics, `tokio` 1.53.1's `JoinError` says the panic's message, which goes back to the UI as an internal rejection and into the Logs, redacted (`desktop/src/lib.rs:55`, `commands/src/logs.rs:166`). So I read every `unwrap`, `expect`, `panic!` and slice outside tests in `model_provider.rs`, `gateway.rs`, `issues/`, `diagnostics.rs` and `logs.rs`. Each `expect` says a fixed sentence, such as "a gateway is JSON", each slice is cut at a character boundary and each index stays in range. None builds its message from a secret.
- **Uncaught errors in the UI** are logged by their name and stack frames, never their message (`app/src/diagnostics/log.ts:22`). The UI writes one other line itself, a failed Suggestion by its kind (`app/src/ai/requests.ts:161`).
- **Errors the UI shows.** A key the Model Provider refuses is said in Lanewise's own words, never the API's (`app/src/ai/anthropic.ts:105`, `app/src/ai/gemini.ts:144`, `app/src/ai/openAiCompatible.ts:200`). Other failures show the Model Provider's own message, as ADR 0022 to ADR 0024 say. No adapter puts a key in a URL or a message.
- **Logs.** A reply's failure is logged by its kind, and a rejection without its request (`commands/src/logs.rs:147-166`). Only Lanewise's own crates' records are kept (`logs.rs:186`), so the HTTP plugin and `keyring` write nothing there.
- **Git's messages.** A remote URL with credentials in it was fetched and cloned from under `/tmp`. Git 2.47.3 named it without them in its errors.

**What the runs showed.** The rejections in probe 1 said no secret. The heap runs in probe 2 had every adapter's request succeed, so no error was built from a key.

**Answer.** No path was found from Lanewise's own code by which a secret it keeps reaches a panic, an uncaught error's log line, a rejection, or an error message it writes itself. An error that quotes what a remote service answered shows what that service said.

## Hand checks (need the owner)

Do each on macOS and on Windows, in the disposable account of the rules of engagement, with only E2's throwaway keys in its credential store.

**A. A Release can't open devtools**

1. Install the latest Release and open it.
2. Right-click the Commit graph, a Commit Message and the Settings dialog. Check that no menu offers Inspect or Inspect Element.
3. Press F12, Ctrl+Shift+I and Ctrl+Shift+J on Windows, or ⌥⌘I and ⌥⌘C on macOS. Check that nothing opens.
4. On macOS, open Safari, turn on Settings → Advanced → "Show features for web developers", and open the Develop menu. Check that this computer's entry lists no Lanewise window.
5. Open a Host page in a Tab, and do steps 2 and 3 on it.
6. Write the date, the Release and the platform in H8's row above.

**B. A key doesn't stay in the webview's memory** (a build from source, since a Release has no devtools)

1. In the same account, clone `adrianeyre/lanewise` and run `pnpm desktop:dev`.
2. In Settings → AI, choose Anthropic, accept its First-use disclosure, and save E2's throwaway Anthropic key.
3. Run `pnpm pen-test:fixtures`, open the `conflict-merge` fixture, and ask for a Suggestion for its Conflict Hunk.
4. Wait for it to answer or fail, then close the Settings dialog if it's open.
5. Open the devtools: on Windows, right-click → Inspect, then Memory → Heap snapshot → Take snapshot. On macOS, right-click → Inspect Element, then Timelines → JavaScript Allocations, and take a heap snapshot.
6. Search the snapshot for the key's last 12 characters: Ctrl+F in the Edge DevTools snapshot, or the filter box in Safari's. Check there's no match. Then type those 12 characters into the Console as a string, take another snapshot, and check that this one finds it, so the search works.
7. In Settings, forget the key.
8. Write the date and the platform in H8's row above.
