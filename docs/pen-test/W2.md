# W2 — Host pages' isolation

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #15, label `prd:pen-test`). W2 probes the Host pages: pages on a Host, shown in a Tab of their own, each in a child webview of the main window (ADR 0042). It starts from H2 and H3.

- **Trust boundary.** On one side is a Host page, any page it goes on to, and every frame in them, all remote pages that Lanewise doesn't write. On the other are Lanewise's commands: `call`, which carries the command API's 87 (ADR 0003), the Update and Host page commands, and the plugins the main webview's capability names. The Host page's Tab sits between them. It's drawn by the main webview, and shows where the page is.
- **Governed by.** `CONTEXT.md`: Host page, Tab, Host, Release, Finding. ADR 0040, ADR 0042, and ADR 0050 for the main webview's policy, which W1 made. `SECURITY.md`.
- **Deliverables.**
  - The Host page probe, a page that a Host page in a Release is sent on to and that checks the probes below from inside it. It's served by `pnpm pen-test:host-page-probe` (`app/scripts/pen-test/hostPageProbe.ts` and `serveHostPageProbe.ts`, with `hostPageProbe.test.ts`). Hand check A uses it.
  - Tests that pin what held:
    - `a_host_page_goes_to_https_pages_and_to_none_of_lanewises_own` in `desktop/src/host_pages.rs`;
    - frame origins added to `a_remote_page_such_as_a_host_page_reaches_no_command` in `desktop/src/lib.rs`;
    - "a Host page gone on to another site shows that site's address…" in `app/src/hostPages/hostPages.app.test.tsx`.
  - A line in `docs/development.md` §8 for the new command.

## How it was probed

This was done headless on Linux, in WebKitGTK 2.54.0, with Tauri 2.12.3 and wry 0.57.0, the versions in `Cargo.lock`. Everything was written under `/tmp`. Nothing was committed but the deliverables.

1. **Read** every file the brief names, and the parts of Tauri and wry that decide what a remote webview gets and what it may ask for. Those are where Tauri injects its scripts, how it judges an IPC request's origin, and how wry asks about a navigation and passes on a message on each platform.
2. **Built the Desktop App from a copy of the tree** under `/tmp`, with `cargo build --features tauri/custom-protocol`, so it serves the built UI as a Release does. The copy had three changes, all for the harness alone:
   - the webviews' TLS errors ignored, so a Host page could load a page served over `https` from `127.0.0.1` with a self-signed certificate;
   - a script added to the main webview, which opened a Host page at that address through `host_page_open`, as the UI's `openLink` does for a Host's link (`app/src/App.tsx:263`), and recorded every `host-page` event the page sent;
   - that address added to the main webview's `connect-src`, so the script could report.

   `desktop/src/host_pages.rs` and the capability were as committed. It ran under `xvfb-run` with `HOME` under `/tmp`.
3. **Served a hostile page as the Host page**, from a local `https` server under `/tmp`, and a second page on another origin for it to go on to. The hostile page tried each probe below from its own frame. Then it tried them from frames it made, and by navigating. It reported what it found back to the server.
4. **Ran the committed probe page** (`pnpm pen-test:host-page-probe`'s) in the same build, as the Host page, and read its results.
5. **Ran Tauri's mock runtime**, as the existing tests do, for the origins a frame can have.

## Probes from the brief

### 1. Whether a Host page, or any frame in it, can reach `__TAURI_INTERNALS__` or any command

**What I read.**

- Tauri injects its own scripts into every webview it makes, a remote one included. These are `__TAURI_INTERNALS__`, its `invoke`, and the IPC script with the app's invoke key. Each is injected into the top frame alone (`tauri-2.12.3/src/manager/webview.rs:159-226`). `host_pages.rs` doesn't turn this off, and Tauri has no way to.
- An IPC request is judged by its origin:
  - through the IPC custom protocol, by the request's `Origin` header, which the engine sets and a page can't (`tauri-2.12.3/src/ipc/protocol.rs:486-494`);
  - through the message handler, by the webview's own address on Linux (`wry-0.57.0/src/webkitgtk/mod.rs:735`), and by the sending frame's address on macOS (`wry-0.57.0/src/wkwebview/class/wry_web_view_delegate.rs:50-53`).

  Tauri refuses an app's command from a remote origin unless a capability names that origin as `remote`, and the default capability names none (`tauri-2.12.3/src/webview/mod.rs:2005-2095`, `desktop/capabilities/default.json`).

**What the live run showed.** The Host page's top frame has `__TAURI_INTERNALS__`, with `invoke`, and so has every page it goes on to. Its metadata names the webview `host-page-900`. Every command it asked for through `invoke` was refused:

| Command | Answer |
| --- | --- |
| `call`, for `recentRepositories` and for `modelProviderKey` | "call not allowed" |
| `update_status`, `host_page_open`, `host_page_go`, `host_page_close` | "… not allowed" |
| `plugin:event\|emit` | "event.emit not allowed", with the permissions that would allow it |
| `plugin:event\|listen`, `plugin:opener\|open_url`, `plugin:http\|fetch`, `plugin:clipboard-manager\|write_text` | "… not allowed on window "main", webview "host-page-900", URL: https://127.0.0.1:8443/", allowed only on the main webview at a local URL |

The same `call` was sent straight through the message handler with the invoke key, and was refused in the same words.

**Answer: disproved on a Linux source build.** A Host page can reach `__TAURI_INTERNALS__` in its top frame, as Tauri gives it to every webview, but it reached no command. Frames are probe 2. A Release on macOS and Windows is hand check A.

### 2. Frames that inherit an origin: `about:srcdoc`, `blob:`, `data:`

**What I did.** The hostile page made five frames, each with a script that tried to call `call` two ways: through the message handler with the invoke key, and through the IPC custom protocol. The five were a `srcdoc` frame, a sandboxed one, a `blob:` frame, a `data:` frame, and an `about:blank` frame the page wrote into itself.

**What I read.** On Linux and macOS, wry asks the navigation handler about every navigation, a frame's as well as the page's (`wry-0.57.0/src/webkitgtk/mod.rs:554-575`, `wry-0.57.0/src/wkwebview/navigation.rs:50-80`). `allowed` lets through only `https` and `about:blank` (`desktop/src/host_pages.rs:136`).

**What the live run showed.**

| Frame | What happened |
| --- | --- |
| `srcdoc`, sandboxed `srcdoc`, `blob:`, `data:` | Never loaded: each stayed an empty `about:blank`, and its script never ran |
| `about:blank`, written into by the page | Had the page's origin and no `__TAURI_INTERNALS__`, since Tauri's scripts are the top frame's alone. WebKit's message handler was there. A `call` sent through it with the invoke key was refused, judged by the webview's address. A request to `ipc://localhost/call` was refused too |

The mock runtime refuses `call` from each origin such a frame can have: `about:srcdoc`, `about:blank`, `blob:https://github.com/…` and `data:` (the new lines in `a_remote_page_such_as_a_host_page_reaches_no_command`). On macOS, a frame's message is judged by its own address, and none of these is Lanewise's own (`tauri-2.12.3/src/webview/mod.rs:1961-2001`).

**Answer: disproved on a Linux source build.** No frame reached a command, and the frames that would inherit an origin never loaded. macOS and Windows are hand check A.

### 3. Navigation to the app's own origin: `tauri://localhost`, `http://tauri.localhost` on Windows

**What I did.** The hostile page tried a navigation of the page itself to each of these, one at a time, and checked after 2.5 seconds whether it was still there:

- `tauri://localhost/` and `tauri://localhost/index.html`;
- `http://tauri.localhost/`;
- `ipc://localhost/call`;
- `data:`, `blob:`, `about:srcdoc`, `file:///etc/hostname` and `asset://localhost/…`.

It also made a frame at each of the first four. The committed probe page did the same.

**What I read.** `allowed` (`desktop/src/host_pages.rs:121-137`) refuses every navigation but an `https` one, or `about:blank`. `https` (`host_pages.rs:112-118`) refuses to open a Host page at anything else. Behind both, the main webview's policy has `frame-ancestors 'none'` (ADR 0050). Tauri sends it as a header with every page it serves (`tauri-2.12.3/src/protocol/tauri.rs:182`), so Lanewise's own page refuses to be drawn in a frame of any page.

**What the live run showed.** Each navigation was refused: the page stayed where it was. Each frame stayed an empty `about:blank`. Lanewise's own page never loaded in the Host page.

**Answer: disproved on a Linux source build** for `tauri://localhost`, `ipc://localhost` and `http://tauri.localhost`, which is Windows's own origin and is refused there as plain `http`. The new test `a_host_page_goes_to_https_pages_and_to_none_of_lanewises_own` pins the list. Windows itself is hand check A.

### 4. Spoofing the page's `lanewise.invalid` signals

**What I read.** Every page a Host page loads gets the `KEYS` script, in its top frame (`desktop/src/host_pages.rs:33-41`, `188`). It asks for focus back, or for its Tab to close, by starting a navigation to `https://lanewise.invalid/focus` or `/close`. `allowed` refuses that navigation and tells the UI (`host_pages.rs:121-134`). The UI moves focus to the Tab's toolbar, or closes the Tab (`app/src/App.tsx:294-301`). The page number in the news is the webview's own, bound as it's made (`host_pages.rs:189`), not anything the page sends.

**What I did.** The hostile page, then a frame in it, started navigations to `https://lanewise.invalid/close` and `/focus`, then to `https://LANEWISE.invalid/…`, and to `https://lanewise.invalid./close` with a trailing dot.

**What the live run showed.**

- The page's own navigations sent the UI Close and Focus for its own page number.
- A frame's navigation sent Close too, since wry asks about frames on Linux (probe 2).
- The upper-case host did the same, since a URL's host is lower-cased as it's read.
- The trailing dot is another host. It went through as an ordinary `https` navigation, which can't load, since `.invalid` is never a real name.
- None of them reached a command, and none could name another page's Tab.

**Answer:** anything that runs in a Host page, or in a frame in it, can send the signals, as its own F6 and Ctrl or Cmd+W do. Each names only that page's own Tab. Hand check C repeats this on a Release.

### 5. A Host page navigating on to another https site: does its Tab show where it is now?

**What I did.** The hostile page went on to a page on another origin, titled "GitHub · Sign in", and I recorded what the UI was told.

**What I read.** Each page load tells the UI the page's address as it starts and as it finishes (`desktop/src/host_pages.rs:205-214`). The UI puts that address in the Tab (`app/src/App.tsx:288-290`), and the toolbar shows it whole, cut off at its end if it's long (`app/src/hostPages/HostPageView.tsx:124-126`). The logo, in the toolbar and on the Tab, comes from the address: a known Host's logo, or a globe for anything else (`HostPageView.tsx:92`, `app/src/tabs/RepositoryTabs.tsx:180`, `app/src/hosts/OpenOnHost.tsx:33`). The Tab's name is the page's own title, or else its host (`RepositoryTabs.tsx:30`). Open in browser opens where the page is now.

**What the live run showed.** The UI was told the new page's address as soon as it started loading, and again as it finished, then the new page's title. The new page had `__TAURI_INTERNALS__` too, and reached nothing, as in probe 1. The new test in `hostPages.app.test.tsx` holds the UI to the rest: the new address in the toolbar, a globe in place of GitHub's logo, and Open in browser opening the new address.

**Answer: partly.** The Tab follows the page: its address shows where it is, and the Host's logo gives way to a globe. Its name, though, is whatever the new page calls itself, which can be a Host's name, and nothing else says the page has left the Host. Whether that's enough to keep a sign-in form on another site from being taken for a Host's is hand check B, on a Release.

## Hand checks (need the owner)

**A. The Host page probe on a Release**

Do this once on macOS and once on Windows, each in a disposable account with the latest Release installed (rules of engagement §3).

1. Make a certificate for `lanewise-probe.test` that only this machine trusts, such as with mkcert, which is free: `mkcert -install`, then `mkcert lanewise-probe.test`.
2. Point the name at this machine: add `127.0.0.1 lanewise-probe.test` to the hosts file. That's `/etc/hosts` on macOS, or `C:\Windows\System32\drivers\etc\hosts` on Windows.
3. In a clone of this tree, run `pnpm pen-test:host-page-probe --cert <the certificate> --key <its key>`. It says where the probe is.
4. In the round's own private GitHub repository (E2), add a link to `https://lanewise-probe.test:8443/` to its README. Never in a public one (rules of engagement §4).
5. In Lanewise, open a clone of that repository, and choose Open repository on GitHub, so its page opens in a Tab. Sign in there with the round's GitHub account if it asks. Follow the README's link. The Tab's address shows the probe.
6. Choose **Run the probes**, and wait about 40 seconds. If the Tab goes somewhere else, choose Back, and the probe carries on.
7. Check that every line says "Held" or "Seen", and none says "BROKE". Check that each box under "Frames at Lanewise's own origins" is empty or an error page, never Lanewise's own window.
8. Write the date, the Release and the platform in H2's row above, with any line that broke. A broken line is a lead: report it privately first (PRD §4).

**B. Where a Host page has gone, on a Release**

1. In the same account, add a link to `https://example.com/` to the README of the round's private repository.
2. Open the repository's GitHub page in a Tab, as in A.5, and follow the link.
3. Check the Tab's address: it shows `https://example.com/`. Check that a globe has taken the place of GitHub's logo, in the toolbar and on the Tab, and that the Tab's name is the new page's title.
4. With VoiceOver on macOS, or Narrator on Windows, move to the toolbar, and check the address is read out.
5. Write in H3's row whether the Tab says clearly enough that the page is no longer GitHub's.

**C. The page's own keys on a Release**

1. Open two Host page Tabs, such as the repository's page and one of its Pull Requests.
2. In the second, click into the page and press F6. Check that focus moves to its Tab's toolbar.
3. Press F6 there. Check that focus moves back into the page.
4. Press Ctrl+W, or Cmd+W on macOS, in the page. Check that its Tab closes, and only its Tab: the first Host page Tab stays open.
