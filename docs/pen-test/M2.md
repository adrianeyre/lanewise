# M2 — nothing applied without the user

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #26, label `prd:pen-test`). M2 tries to show that something a Model Provider or Jev answers reaches the Resolution, or the working tree, without the user asking for it: by any path that changes a Resolution, while Suggestions are asked for every Conflict Hunk, through any of Jev's answers, or from any Model Provider, including one on this computer and one through a Gateway. It starts from H10, which M1 left open.

- **Trust boundary.** On one side, a Suggestion or a Jev answer: whatever a Model Provider, a Gateway or TypeSafe sends back. On the other, the Resolution, which only the user changes, and the working tree, which only Mark resolved writes.
- **Governed by.** `CONTEXT.md`: Suggestion, Confidence, Resolution, Conflict Hunk, Jev, Model Provider, Gateway, Finding. ADR 0025 (Suggestions put in only by Accept or Edit), ADR 0026 (Suggestions for every Conflict Hunk, asked one at a time), ADR 0036 (Jev never acts on its answer), ADR 0035 (Gateways). PRD §8.1 (`git-client.md`): "Nothing is written to the working tree without explicit user action" and "No automatic application of AI output". CLAUDE.md's AI rule. `SECURITY.md`'s "a Model Provider's answer that makes Lanewise … apply a Suggestion you didn't ask for".
- **Deliverables.** Tests pinning what held, each checked to fail when the behaviour it holds is broken:
  - `app/src/ai/everyModelProvider.test.ts`: each of the six Model Providers as Lanewise ships them (`MODEL_PROVIDERS`), and the five cloud ones through a Gateway, answering with a tool call in its API's own shape and with fields no Suggestion has. Each answer comes back as a Suggestion of three fields and its usage, and the only commands sent read the key and the Gateway, or send the request through it;
  - `app/src/conflicts/NothingAppliedWithoutTheUser.test.tsx`, in the App under jsdom. Suggestions for every Conflict Hunk, each checked by Jev, and Jev's pick of a side change nothing and send no command that writes. The only buttons that put anything in are each Suggestion's Accept and Edit and Jev's Use. A Suggestion shown and never accepted isn't in what Mark resolved writes, nor is one still being asked for, whose late answer goes nowhere. One file's Suggestion never reaches another file's Resolution, even with the same Conflict Hunk. Jev's pick of "a person", or of none of the five, offers nothing to Use. A Suggestion with Jev not reached is still only shown;
  - `app/src/ai/jev.test.ts`: through a Gateway, Jev's answers to each of its three questions are only read, and the core is asked only to send them.

## How it was probed

This was done headless on Linux (Debian 13), with Node 26.11.1 and the tree at `abbac03`, building on M1's record and tests (`docs/pen-test/M1.md`). Scratch scripts were written under `/tmp` or deleted before anything was committed. Nothing was sent to a Model Provider, Jev or Gateway. This container's own Model Provider variables were not used, and every answer came from the fake Model Provider (`app/src/test/fakeModelProvider.ts`), a fake TypeSafe or a fake `gatewayRequest`.

1. **Listed every write.** Searched the UI for every call that changes the Resolution's editor (`putSuggestion`, `replaceResolution`, `chooseHunk`, `ResolutionHandle.put`, CodeMirror's undo and redo) and every command that writes a conflicted file (`resolveConflict`, `resolveWholeFile`), and the core for any that takes a Suggestion.
2. **Read** `app/src/conflicts/ResolutionWidget.tsx`, `app/src/conflicts/SuggestionWidget.tsx`, `app/src/conflicts/ConflictsPage.tsx`, `app/src/conflicts/conflictEditors.ts`, `app/src/conflicts/useConflictedFile.ts`, `app/src/ai/requests.ts`, `app/src/ai/suggestionRequest.ts`, `app/src/ai/gateway.ts`, `app/src/ai/jev.ts`, `app/src/ai/jevDecisions.ts`, the three adapters, `app/src/repository/CommitForm.tsx` and `core/src/conflict.rs`.
3. **Ran every shipped adapter** through `requestSuggestion` with answers written to tempt it: a tool call, a stop for tool use, and fields naming a command, a path outside the working tree and an Accept. Then the same through a Gateway.
4. **Drove the Conflicts page** in the App with Suggestions for one and for every Conflict Hunk, Jev's verdicts and picks, Jev not reached, Mark resolved partway, and a second file with the same Conflict Hunk, reading the editor's text and every command sent after each step.
5. **Broke each behaviour the tests hold**, one at a time, in a copy of the tree that wasn't committed: `readSuggestion` passing fields through, a Suggestion put in as it arrives, and the request left running once the Widget is gone. The tests failed each time.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Every path by which a Resolution changes: only Accept or Edit?

**What I read.** The Resolution is one CodeMirror editor per file (`app/src/conflicts/ResolutionWidget.tsx:344-388`), made from the file as Git left it or the draft the user left (`:348`). Its text changes in these ways and no others:

| Path | Where | Started by |
| --- | --- | --- |
| Typing in the editor, and its own undo and redo keys | `:346-352`, `app/src/conflicts/conflictEditors.ts:220-245` | the user |
| Accept Ours, Accept Theirs, Accept both either way round | `ResolutionWidget.tsx:434-440`, `conflictEditors.ts:252-260` | the user's button |
| Take all of Ours or Theirs | `ResolutionWidget.tsx:442-448`, `conflictEditors.ts:304-312` | the user's button |
| Undo, Redo, Start over | `ResolutionWidget.tsx:450-462` | the user's button |
| A Suggestion's Accept or Edit, through `ResolutionHandle.put` | `ResolutionWidget.tsx:373-379`, `app/src/conflicts/SuggestionWidget.tsx:426-442`, `:671-678` | the user's button |
| Jev's pick of a side, through the same `put` | `SuggestionWidget.tsx:216-228`, `:532-541` | the user's Use |

`put` has three callers, Accept, Edit and Use, each a button's `onClick` (`SuggestionWidget.tsx:225`, `:427`). `putSuggestion` and `replaceResolution` are called only from the Resolution Widget (`ResolutionWidget.tsx:376`, `:446`, `:460`). The handle reaches the AI Suggestion Widget as React state through the Conflicts page (`app/src/conflicts/ConflictsPage.tsx:66`, `:123`, `:134`), so nothing else holds the editor. A draft kept on choosing another file is the editor's own text (`ResolutionWidget.tsx:383`). The working tree is written only by Mark resolved, which sends the editor's text as it is (`:464-493`, `:481`), and a Whole-file choice, which has no Suggestion (`:208-230`, `:218`). In the core, `resolve_conflict` and `resolve_whole_file` take only what the UI sends (`core/src/conflict.rs:165`, `:188`, `commands/src/conflict.rs:192`, `:205`), and nothing there knows of a Suggestion.

**What the runs showed.** A Suggestion shown and never accepted, with the Conflict Hunk resolved by Accept Ours instead, left `resolveConflict` writing Ours alone. Mark resolved pressed while a Suggestion was still being asked for wrote the Resolution as it was. The Widget was drawn away with the file, its request was aborted, and the answer that came after was shown nowhere and put nowhere. A Suggestion asked for in one file was gone on choosing a second file with the same Conflict Hunk, and gone again on coming back. Neither file's Resolution had changed. Two things drop it: the Suggestions are keyed by the file's path (`SuggestionWidget.tsx:67`), and the Widget shows "Reading…" in the same render a new file is chosen (`app/src/conflicts/useConflictedFile.ts:20-24`, `:37`), so taking either away alone still drops it.

**What held.** Only the user's Accept, Edit or Use puts AI output in the Resolution, and only Mark resolved writes it. A Suggestion that isn't accepted, or arrives late, or was asked for in another file, reaches neither. Accept finds its Conflict Hunk again by its sides, as ADR 0025 says, and each Suggestion's heading names where that is now before Accept is pressed (`SuggestionWidget.tsx:583-590`).

### 2. Suggestions for every Conflict Hunk, asked one at a time

**What I read.** `askAll` (`SuggestionWidget.tsx:344-401`) asks for each Conflict Hunk left that has no Suggestion shown, one request at a time, finding each again by its sides before it's asked (`:366`). Each answer is added to the Suggestions shown (`:377`) and to nothing else. It's checked by `checkSuggestion`, and by Jev if Jev is on (`:273-286`). Each one shown has its own Accept, Edit and Reject (`:581-596`, `:670-683`), and there's no button that accepts them all. Cancel, choosing another file and leaving the page abort the request (`:238`, `:403-413`), and what an aborted request returns is dropped (`:376`, `:381`).

**What the runs showed.** On a file of two Conflict Hunks, with Jev checking each Suggestion and then asked which side, both Suggestions and Jev's pick were shown. The Resolution's text was as Git left it, and no command sent from the first click to the last wrote anything: each read a key, or whether a Gateway was kept. The only buttons in the Widget that put anything in were "Use Ours", and Accept and Edit for each Suggestion. ADR 0026's own tests (`SuggestionsForAll.test.tsx`) hold the order, one request at a time, each reviewed on its own, failures partway and Cancel.

**What held.** Asking for every Conflict Hunk only asks. Every Suggestion waits for its own Accept or Edit, whatever its Confidence.

### 3. Jev's answers, for every question Lanewise asks it

**What I read.** Lanewise asks Jev three things, each only while Jev and that decision are on (`app/src/ai/jevDecisions.ts`):

| Question | Asked from | What its answer can do |
| --- | --- | --- |
| Does this Suggestion keep both sides' changes? (`keeps_both`, `:16-46`) | after each Suggestion (`SuggestionWidget.tsx:275-286`) | be shown beside the Confidence, and below 50% make it low (`app/src/ai/confidence.ts:80-83`); never raise it |
| Which way does this Conflict Hunk go? (`resolution`, `:60-93`) | Ask Jev which side (`SuggestionWidget.tsx:195-213`) | offer Use and Dismiss, with no Use for "It needs a person" (`:532-541`). Only Use puts it in, as one change Undo takes back (`:216-228`) |
| Do the staged changes hold a secret or a leftover, and which Conventional Commit type are they? (`secret`, `leftover`, `type`, `:114-147`) | Commit, and Check with Jev (`app/src/repository/CommitForm.tsx:107-133`, `app/src/repository/RepositoryPage.tsx:486-491`) | stop a commit only to say what it found, with Commit anyway (`CommitForm.tsx:133`, `:265`). Offer a button that starts the subject with the type (`:264`, `:287-291`, `:325`). Never commit, and never change the Commit Message by itself |

Each is one request through `askJev` (`app/src/ai/jev.ts:71-123`), to TypeSafe or a Gateway kept for it, whose answer is only returned.

**What the runs showed.** Jev's pick of a side changed nothing until Use, as M1 showed. Its pick of "a person" was shown with no Use. Its pick of a choice that isn't one of the five said "Jev couldn't say. Its answer wasn't one Lanewise could use." with no Use. With TypeSafe not reached, a Suggestion was still shown at the Confidence its checks gave, saying "Jev couldn't check it. Lanewise couldn't reach TypeSafe.", and nothing was put in. Through a Gateway, the three questions' answers were read and returned, and the only commands sent were `modelProviderKey`, `gatewayOf` and `gatewayRequest`. `CommitForm.test.tsx` already holds a commit with a likely secret to Commit anyway, and the type to its button.

**What held.** No answer of Jev's, to any question Lanewise asks it, puts anything in a Resolution, writes the working tree, changes a Commit Message or makes a commit without the user's Use, button or Commit. With Jev unreachable, a commit goes ahead once the user presses Commit, and says Jev couldn't check (`CommitForm.tsx:115-117`). That's ADR 0036's "None acts", not Jev acting.

### 4. Every Model Provider, including a local one and a Gateway

**What I read.** `requestSuggestion` (`app/src/ai/requests.ts:119-168`) refuses unless AI is on and the Model Provider's First-use disclosure is accepted, and only returns the Suggestion (`:113-118`). A Gateway is used only for a cloud Model Provider (`:68`), through `gatewayFetch` (`app/src/ai/gateway.ts:11-57`), which hands back the core's answer as a `Response`. Every adapter reads only its answer's text: Claude's text blocks (`app/src/ai/anthropic.ts:139`), Gemini's text parts that aren't thoughts (`app/src/ai/gemini.ts:197`), and the OpenAI-compatible message's `content` (`app/src/ai/openAiCompatible.ts:215-228`), which covers OpenAI, xAI, Meta and a local server. None asks for tools (`completionRequest`, `:83-100`, and each `suggest`). All three end in `readSuggestion` (`app/src/ai/suggestionRequest.ts:102-117`), which keeps three fields of the right types and refuses anything else.

**What the runs showed.**

| Model Provider | Asked | Answered with | Came back as | Commands sent |
| --- | --- | --- | --- | --- |
| Anthropic | directly, and through a Gateway | a `tool_use` block, `stop_reason: "tool_use"`, and extra fields | a Suggestion of three fields and its usage | `gatewayOf`, `modelProviderKey`, and `gatewayRequest` through the Gateway |
| OpenAI, xAI, Meta | directly, and through a Gateway | `tool_calls`, `finish_reason: "tool_calls"`, and extra fields | the same | the same |
| Gemini | directly, and through a Gateway | a `functionCall` part, and extra fields | the same | the same |
| A local server | at its default address on this computer | `tool_calls` and extra fields | the same | `modelProviderKey` |

Two requests were made each time, the model list and the Suggestion, and nothing the answer named was asked for after. Nothing was logged.

**What held.** Whichever Model Provider answers, and however it's reached, its answer can only become a Suggestion to be shown, checked and left for the user.

## Hand checks (need the owner)

Do this in the disposable account of the rules of engagement, with only E2's throwaway keys in its credential store, on the first Release that has this round's changes. Never with a real project's repository or a real key.

**A. Nothing put in, on a Release, with a real Model Provider and Jev**

1. Run `pnpm pen-test:fixtures`, and open its `conflict-merge` fixture in the Release.
2. In Settings → AI, turn on "Suggest Resolutions with AI", choose a Model Provider and model, accept its First-use disclosure and save E2's throwaway key for it. Turn Jev on, with its Suggestion check and Ask Jev which side, and save E2's throwaway TypeSafe key.
3. On the Conflicts page, choose a conflicted file and press Suggest for all Conflict Hunks in this file. Wait for every Suggestion.
4. Without pressing Accept, Edit or Use, check that the Resolution is still as Git left it, and that `git status` in a terminal still shows the file as conflicted, with the working tree's copy unchanged.
5. Press Ask Jev which side, then Dismiss. Check the Resolution again.
6. Press Suggest a resolution, and while it's running press Accept Ours in the Resolution and then Mark resolved. Check, with `git diff --cached`, that the file staged is Ours' version alone, and that no Suggestion appears afterwards.
7. Do steps 2 to 4 once with a local server, such as Ollama with a small model, and once with a Gateway kept for a cloud Model Provider, if E2 has one.
8. Write the date, the Release, the platform and each Model Provider in H10's row above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).
