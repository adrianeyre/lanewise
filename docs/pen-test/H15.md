# H15 — code scanning for the tree, with a named owner for its alerts

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #33, label `prd:pen-test`). This issue **builds rather than probes**. It answers H15, "No static analysis reads the tree", with a code scanning workflow and an ADR naming who reads its alerts.

- **Trust boundary.** Between code anyone may propose, in a pull request or a dependency Dependabot proposes, and code merged to `main` and built into a Release by `release.yml` (ADR 0029). Review is the boundary's only reader today. Code scanning adds a second one, which reads every change and the whole tree each week. It is defence in depth: it moves no boundary, and closes nothing on its own.
- **Governed by.** `CONTEXT.md`: Code scanning alert (new), Finding, Release, Pen-test round. PRD §4 (Disclosure), §5 H15 and §7. ADR 0029, and the new ADR 0049. `CLAUDE.md`'s rules on versions and free tooling.
- **Deliverables.**
  - `.github/workflows/codeql.yml`: CodeQL on the Rust, the TypeScript and the workflows, on each pull request, each push to `main` and every Monday.
  - `app/scripts/workflows.test.ts`: four tests. Every action in every workflow is pinned to a commit with its release, and is at the same commit wherever it's used. No workflow uses `pull_request_target`. The code scanning workflow keeps its triggers, its narrow token, its languages and its queries.
  - ADR 0049, `docs/architectural-decision-record/0049-code-scanning-by-codeql-in-a-workflow-with-its-alerts-read-by-the-owner.md`: why CodeQL, in a workflow, what GitHub's settings turn on, and the owner as the reader of every alert, with how soon each is triaged.
  - `docs/development.md` §9, "Code scanning": where the alerts are, who can see them, how to triage one, and how to run CodeQL locally.
  - The term Code scanning alert in `CONTEXT.md`, and a line each in `CLAUDE.md` and `CONTRIBUTING.md`.

## What the brief asks for

### 1. What GitHub's own settings have turned on is written down

**What I did.** This sandbox has no GitHub token, and the rules keep a run from sending anything to a Host (rules of engagement §2). So I didn't read the repository's settings, as E4 didn't read its labels. I read what the tree decides:

- `.github/dependabot.yml:4`–`:28` turns on Dependabot version updates for npm, Cargo and GitHub Actions, weekly and grouped.
- `.github/CODEOWNERS:8`, `* @adrianeyre`, makes the owner the only code owner.
- `.github/workflows/ci.yml` and `release.yml` run no code scanning or secret scanning. `codeql.yml` is the first workflow that does.
- `SECURITY.md:13` sends a report through private vulnerability reporting, which is a setting. E3's hand check A covers it (`docs/pen-test/E3.md`, step 3).

I then read GitHub's documentation, as it stood on 12 October 2026, for what a public repository on a personal account has turned on by default.

**Answer: written down, with what was found still the owner's (hand check A).** The table is in ADR 0049, "What GitHub's own settings turn on", with the default and what's wanted for each. This is its copy for the owner to fill in:

| Setting (Settings → Advanced Security) | Default for a public repository | Wanted | Found by the owner, with the date |
| --- | --- | --- | --- |

One setting decides whether the workflow works at all. GitHub refuses a workflow's code scanning results while CodeQL's default setup is on. Since GitHub can switch the default setup on by itself for a public repository, hand check A's first step is to make sure it's off.

### 2. Code scanning runs on Rust and TypeScript with free tooling, in a workflow at the latest version of each action, pinned to a commit

**What I did.**

1. **Chose the tool.** CodeQL is free for a public repository and reads both Rust and TypeScript. It reads workflows too, which R2's secrets make worth reading. ADR 0049 says why it was chosen over GitHub's default setup, Semgrep Community Edition, a workflow secret scanner, `cargo audit` and `security-and-quality`.
2. **Looked up each action's latest release** (`CLAUDE.md`), on 12 October 2026, with `git ls-remote` and GitHub's releases:
   - `github/codeql-action` **v4.38.3**, released 8 October 2026. Its tag `cee97f86…` points at commit `24c54180a607b1449ed407dd24f251e4e9147c8d`, which is what's pinned. It runs CodeQL 2.27.2 (`src/defaults.json` at that commit).
   - `actions/checkout` **v7.0.1**, released 20 July 2026, at `3d3c42e5aac5ba805825da76410c181273ba90b1`, the commit `ci.yml` and `release.yml` already pin.
3. **Wrote `.github/workflows/codeql.yml`.** One job per language: `rust`, `javascript-typescript` and `actions`, each with `build-mode: none` and `queries: security-extended`. The token reads contents and writes security events, nothing else. The trigger is `pull_request`, never `pull_request_target`. The checkout has `persist-credentials: false`. The Rust job installs the stable toolchain, as `ci.yml` does.
4. **Ran the same CodeQL locally.** I ran CodeQL 2.27.2 from GitHub's bundle, with the same languages, build mode and query suites, on a clean `git archive` of this branch under `/tmp`. That's the tree CI's checkout sees, without `node_modules` or `target/`. The results are in "What the local run found" below.
5. **Checked every pin in the tree.** All 34 remote `uses:` lines across the three workflows name 11 actions. Each is pinned to a full commit, the commit is the one its `# vX.Y.Z` comment's tag points at (`git ls-remote`, the tag peeled), and each is at its action's latest release.

**Answer: built.** `app/scripts/workflows.test.ts` holds it, and I checked each test fails when its rule is broken: an action pinned to `@v4`, `init` and `analyze` at different commits, `pull_request_target`, Rust dropped from the matrix, a wider token. The first run on GitHub needs the merge, and is hand check E.

#### What the local run found

On 12 October 2026, I ran CodeQL 2.27.2 with `build-mode=none` and each language's `security-extended` suite, on a clean `git archive` of this branch:

| Language | What it read | Results |
| --- | --- | --- |
| `rust` | 109 of 109 Rust files, in both Cargo workspaces, none with extraction errors | 17 |
| `javascript-typescript` | 336 of 337 JavaScript and TypeScript files, with no extraction errors | 9 |
| `actions` | 3 of 3 workflows | 0 |

- **Each result was read against its code and triaged** as ADR 0049 says. The triage notes, one per result, are in this run's report to the owner, not here. Until it's triaged, an alert on `main` is seen only by people with write access, and this record keeps to that. The first run on `main` will raise the same results as alerts, for the owner to record as dismissed, fixed or reported (hand check E).
- **The log says what was read, not what was found.** The analysis printed the files it read and its metrics, never a result. That matches what `github/codeql-action` v4.38.3 passes to `codeql database interpret-results` (`src/codeql.ts` at the pinned commit: `--print-diagnostics-summary` and `--print-metrics-summary`). The action uploads its results as an artifact only in debug mode (`src/init-action.ts`: `debug` or the runner's debug logging; `src/init-action-post-helper.ts`). ADR 0049 and `docs/development.md` therefore say never to re-run with debug logging.
- **`rust-src` isn't needed.** I ran the Rust analysis a second time with `rust-src` added to a copy of the toolchain. It found the same 17 results, at the same places, from a database of the same size (254 MiB of relations with it, 259 MiB without). The workflow doesn't install it.
- **Nor are the WebKitGTK libraries `ci.yml` installs for `desktop/`.** CodeQL reads the Rust without building it, so the workflow doesn't install them. This container has them, though, so whether a runner without them reads as much is for the first run to show. Its log should say 109 of 109 Rust files, none with errors, with no warning from the extractor about Cargo or build scripts (hand check E).

### 3. The owner is named as the reader of its alerts, with how soon one is triaged, in an ADR

**Answer: ADR 0049, "The owner reads every alert, within a week".** The owner, Adrian Eyre (`@adrianeyre`), reads every code scanning, secret scanning and Dependabot alert. The triage times:

- an alert on `main`, or a Dependabot alert, within 7 days of being raised, the week `SECURITY.md` promises a reporter;
- an alert on a pull request, before the pull request is merged;
- a secret, revoked where it came from on the day it's read.

To triage is to fix the alert, dismiss it with a written reason, or, if it shows a concrete way to do harm in a Release, file it privately as a Finding (PRD §4, §7). The ADR also records two things about disclosure. An alert on a pull request is as public as the pull request. And a run in debug mode puts its results in an artifact anyone can download, so runs are never re-run with debug logging. Hand check C makes sure alerts reach the owner.

### 4. `docs/development.md` says how to read the alerts

**Answer: written, §9 "Code scanning".** It covers the three places an alert shows: a pull request's checks, its annotations, and the Security and quality tab. It says who can see each, how to triage an alert, what to do if a check fails on your pull request, why never to re-run with debug logging, and how to run CodeQL locally with its free CLI. `CONTRIBUTING.md` links to it from "Tests and lint". `app/scripts/community.test.ts` holds its paths and its heading link to the tree.

## Hand checks (need the owner)

These are ADR 0049's hand checks. Do them on `https://github.com/adrianeyre/lanewise`, signed in as the owner. A to D come before the round's pull request is merged, and E after.

**A. The settings**

1. Open **Settings → Advanced Security**.
2. Under "Code Security", find **CodeQL analysis**. If default setup is on, turn it off from the **⋯** menu beside it (**Disable CodeQL**), so it reads **Not configured**. Otherwise `codeql.yml`'s results are refused.
3. Read each row of the table in "What the brief asks for", 1, on the same page. Turn on each one that's wanted and is off.
4. Write what you found, with the date, in the table's last column, and commit it.

**B. Private vulnerability reporting**

1. Do step 3 of E3's hand check A (`docs/pen-test/E3.md`), if it isn't done yet.

**C. That alerts reach the owner**

1. On the repository, choose **Watch → Custom**, tick **Security alerts**, and apply.
2. On your account, open **Settings → Notifications**, and check that security alerts reach you where you'll see them: on GitHub, by email, or both.

**D. Optional: make the check required**

1. In **Settings → Rules → Rulesets**, add a ruleset for `main` with **Require code scanning results**.
2. Make CodeQL the required tool, blocking errors and high or critical security alerts, as its check does.
3. Leave the rest of branch protection to R3 (#29).

**E. The first runs, after the merge**

1. Open **Actions → Code scanning**. Check that the run for the merge on `main` passed, with all three jobs: **CodeQL (rust)**, **CodeQL (javascript-typescript)** and **CodeQL (actions)**. In **CodeQL (rust)**'s log, check that the metrics say about 109 Rust files extracted without error and none with errors. Look for warnings from the extractor about Cargo or build scripts too. If there are some, add `ci.yml`'s `apt-get` step to the Rust job.
2. Open **Security and quality → Code scanning**. Check that it lists CodeQL's analyses for Rust, JavaScript/TypeScript and Actions, and no message that results were refused.
3. Expect the 26 results of the local run, or close to them, as alerts ("What the local run found"). Triage each within 7 days, as ADR 0049 says, with this run's notes.
4. On the next pull request, check that the four checks of `docs/development.md` §9 appear.
5. On the Monday after the merge, check that the scheduled run ran.
