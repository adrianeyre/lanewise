# Coding standards

Binding for every contributor, human or AI. Rules here are hard review
findings — a PR that breaks one is not mergeable until fixed or the rule is
changed. Anything a tool already enforces (prettier, eslint, tsc strict) is
deliberately not restated here.

## Comments

Comments are banned. Meaning lives in names, types, tests and commit
messages — a name travels to every call site, a comment sits in one place and
goes stale.

**The one escape hatch:** a single-line guard comment is permitted only where
the code must do something that visibly invites the wrong "fix", and a test
cannot pin the behaviour instead. It states the constraint in plain words.
No ADR, ticket or glossary references in code — provenance belongs in the
commit message.

```ts
// A local worker shares this queue, so a claim must stay one atomic statement.
```

JSDoc is permitted only in published packages, only on the exported surface.

## Naming

Every function name starts with a verb that says what it does. The common
verbs have pinned meanings:

| Verb                                      | Meaning                            |
| ----------------------------------------- | ---------------------------------- |
| `get`                                     | cheap/local access, no I/O         |
| `fetch`                                   | remote call                        |
| `find`                                    | lookup that may return `undefined` |
| `load`                                    | read into memory from DB/disk      |
| `build`                                   | pure construction from parts       |
| `create` / `insert` / `update` / `delete` | persistence semantics              |
| `is` / `has` / `should` / `can`           | returns boolean                    |
| `assert`                                  | throws on failure                  |

Verbs outside the table just need to be honest.

**A name says which thing, not just what kind.** A bare generic word —
`build`, `process`, `handle`, `run`, `review`, `refresh`, `sync`, `data`,
`item`, `manager` — names an activity or a category, so it takes its object:
`buildCategoryTree`, not `build`; `refreshPriceIndex`, not `refresh`. The test:
could the name equally belong to another thing in this repo or a sibling? If so
it is too vague. This binds hardest on names read away from the code — job and
message types, queue, event, table, column and route names, env vars, config
keys and log fields — because nothing around them explains what they are.

**Parameter/argument symmetry:** a named local passed to a function uses the
parameter's name, unless the caller's name is strictly more specific and the
precision earns the difference (`absorbingCode` → `code` is fine; `jobData` →
`payload` is not). Expressions and literals are exempt.

Files are kebab-case; values camelCase; types PascalCase; value sets are
`as const` arrays whose union type derives from them — where something reads the
list at runtime (a type guard, a SQL parameter, a seed). A closed set of tags no
code ever iterates is a plain union type instead: eslint rejects an array kept
only to derive a type, and inventing a reader for it is the speculation rung 1
of Reuse forbids.

## Reuse

Before writing code, walk down; stop at the first rung that holds:

1. **Drop the requirement** — nothing speculative gets built (YAGNI).
2. **An existing pattern in this repo or a sibling repo** — mirror it.
3. **The standard library or the platform.**
4. **An already-installed dependency** — never reimplement what one provides.
5. Only then write the minimal new code.

Brevity is not a rung: never compress clear steps into a dense one-liner —
well-named intermediate values are the documentation.

## Types

No `any`. No `as` casts in source code. Named exits, and only these:

- `as const`
- `as unknown` / `as never` at genuinely untypeable third-party boundaries
  (e.g. CDK test mocks)
- test data built with shoehorn partials, never `as`

## Layout

Every repo is laid out the same way at the root, and differs only in what
`src/` holds.

```
src/                  all application code; nothing runnable lives outside it
  index.ts            the composition root, and the only file that wires things together
  config/vars.ts      the one reader of process.env, with vars.test.ts beside it
  integration.test.ts the one Postgres suite
infrastructure/       a service's CDK app (below); cdk.json runs its index.ts with tsx
config/               node-config files the stack reads: default.json and the overrides
docs/                 adr/, standards/, and the domain documents
.github/              actions/setup, the composite that installs with the org token,
                      and workflows/pr-checks.yml, lint-pr-title.yml, plus deploy.yml
                      for a service or module, publish.yml for a package
```

At the root beside those: `package.json`, `pnpm-workspace.yaml`,
`tsconfig.json` and `tsconfig.build.json`, `eslint.config.mjs`,
`vitest.config.ts`, `.gitignore`, `.prettierignore`, `.env.example` wherever
`vars.ts` exists, and for a service a `Dockerfile` and `cdk.json`. Nothing
else: no `test/` or `tests/` folder, no second lockfile, no config for a tool
the repo no longer uses.

### The CDK app

A service's short name is its repo name without the `services.` prefix,
with the dot as a hyphen: `core-vehicles`, `ingest-smmt`, `api-vehicle`.

- `infrastructure/index.ts` fetches the SSM values the stacks take at synth
  time (the npm token for the Docker asset), through `ssm.ts`, and
  instantiates the stacks. Nothing else.
- `infrastructure/<short-name>-stack.ts` exports `class <ShortName>Stack`,
  instantiated with the id `<ShortName>` (`CoreVehiclesStack`, `CoreVehicles`),
  and `<short-name>-stack.test.ts` beside it asserts the template with a stack
  id of `TestStack`.
- A service has one stack per deployable, so a second stack is earned by a
  resource the first cannot hold, such as one that must live in another
  region, and never by size. It is `<short-name>-<part>-stack.ts` exporting
  `class <ShortName><Part>Stack` with the id `<ShortName><Part>`
  (`CoreVehiclesSearchStack`, `CoreVehiclesSearch`), and its test beside it,
  with the same `TestStack` id.
- A helper a stack needs is a file named for its one idea (`ssm.ts`), with
  its test beside it. Never `utils.ts`.

An infra module is the other shape: `src/stack.ts` exports `class ModuleStack`,
`src/index.ts` instantiates it, and each resource is its own file.

### tsconfig and vitest

`tsconfig.json`: `target` `ES2024`, `module` and `moduleResolution`
`NodeNext`, `strict`, `outDir` `dist`. A service sets `rootDir` `.` and
includes `src` and `infrastructure`; a package or module sets `rootDir`
`src`. A service's `tsconfig.build.json` is exactly this, so the Docker image
carries `src` and not `infrastructure`:

```json
{
  "extends": "./tsconfig.json",
  "include": ["./src/**/*.ts"],
  "exclude": ["node_modules", "cdk.out", "coverage", "dist", "src/**/*.test.ts"]
}
```

`vitest.config.ts` includes `src/**/*.test.ts` and, for a service,
`infrastructure/**/*.test.ts`; coverage includes the same trees and excludes
only `**/*.test.ts`. The `env` block sets what `vars.ts` requires. Coverage
is gated in CI and reported locally:

```ts
thresholds: process.env.CI ? { statements: 88, branches: 70, functions: 80, lines: 88 } : undefined,
```

The numbers are the estate's; a repo below them raises its coverage rather
than lowering the gate.

### Dockerfile

Two stages, both `node:22-slim`. Build: `corepack enable`, copy `package.json`
and the lockfile, point the org scopes at the GitHub registry, install, copy
the tsconfigs and `src`, `pnpm run build && pnpm prune --prod`. Runtime: copy
`package.json`, `node_modules` and `dist` from the build stage, `ENTRYPOINT
["node", "--enable-source-maps"]`, `CMD ["dist/src/index.js"]`. A runtime
`apt-get` is allowed only for a binary the service genuinely shells out to.

What `src/` holds depends on the kind of repo:

- **A service** (`services.*`): one folder per job (`build/`, `seed/`,
  `assemble/`), one per subsystem (`worker/`, `resolve/`), `lib/` and `config/`.
  An ingest service's feeds live in `feeds/`, one file per feed.
- **A package** (`packages.ts.*`): `index.ts` is the whole public surface and
  nothing else is exported; one folder per area (`schema/`, `services/`,
  `cdk/`), tests beside the file they pin.
- **An infra module** (`infra.*.module`): `stack.ts` and `index.ts`, one file
  per resource, constructs that a service repo consumes as a package.

`src/` is two levels deep and never three. A folder is one job, one subsystem,
or shared code.

- **`lib/` holds only what more than one folder uses.** A file used by a single
  folder lives in that folder. A shared subsystem with a public face of its
  own is a folder, not a set of `lib/` files.
- **A job never imports another job, and neither `lib/` nor a subsystem imports
  a job.** Anything two jobs both need moves to `lib/` or a subsystem;
  anything that wires jobs together belongs in `src/index.ts`, the composition
  root.
- **One test file per folder, beside the folder's pure seam and named after it**
  (`build/draft.test.ts`, `promote/plan.test.ts`). The I/O halves (`run.ts`,
  `load.ts`, `write.ts`) are covered by `src/integration.test.ts`, never
  unit-tested. `lib/` and a subsystem have no single seam, so a file of theirs
  worth pinning gets its own test beside it.
- **Everything that needs Postgres lives in `src/integration.test.ts`**, one
  suite, one container, bootstrapped inline by replaying the database package's
  migrations.
- Test fixtures live in the test that uses them. There is no `testing/` folder;
  test-only code must never be reachable from `src/index.ts`, or it ships.
- **A file earns its name by holding one idea that more than one caller reaches
  for.** A module that is only constants, or only imports around one short
  function, lives inside the module that uses it. Split a file when a second
  idea arrives, not before.
- **A folder holds more than one file.** A single file is not a folder; it lives
  in the folder whose concern it serves. `config/` is the one exception, named
  above as shared code.

## Config

Every environment variable is read in one place, `src/config/vars.ts`, into a
typed `Vars` object through three helpers: `required(name)` throws when the
variable is missing, `flag(name, fallback)` reads a boolean, and
`port(name, fallback)` a number. Nothing else touches `process.env`. The
composition root loads vars once and passes what each job needs as arguments;
a job never reaches for config itself.

Two files describe the same variables as `vars.ts` and must agree with it:

- `.env.example` lists exactly the variables `vars.ts` reads, one per line,
  every value empty, in the same order. A variable the code stopped reading
  leaves the example in the same commit.
- The `env` block in `vitest.config.ts` sets every variable `required()`
  reads, so the unit suite never depends on a developer's shell.

### Deployment config

`config/` is the deploy-time configuration, read through `node-config` by
`infrastructure/` only. Runtime code never imports `config`: the stack reads
it and passes what the task needs as environment variables, which `vars.ts`
then reads. The two never meet.

- **`default.json` is the sandbox.** It holds every key with the value that
  is safe to deploy by accident: alerting off, small capacity, short
  retention, sandbox bucket and cluster names. `sandbox.json` is therefore
  empty or absent, never where sandbox values live.
- **An environment file only overrides.** `production.json` holds the keys
  production differs on and nothing else; a key it introduces that
  `default.json` lacks is a finding, because an unset environment would run
  without it. `staging.json` exists only where a staging deploy exists.
  `test.json` holds what the stack's unit tests need to exercise, such as an
  alarm switched on, and nothing else.
- **The environment is chosen by `NODE_CONFIG_ENV`**, set by the workflow from
  the repo variable, and the stack falls back to `sandbox` when it is unset.
  Never to production.
- **Config holds names, never secrets.** A credential is an SSM parameter the
  stack reads by name; the key that holds a parameter name ends in `Param`
  (`endpointParam`, `npmTokenParam`), so a reader knows it is a pointer.
- Keys are camelCase and grouped by the thing they configure (`db`, `ecs`,
  `alerting`, `task`), one object per group, no flat prefixes.

## The database

A service owns no schema. Every table lives in `packages.ts.db`, and a schema
change is a PR there, never a migration in the service. A service reads with
the database user provisioned for it and writes only to the tables that user
holds a grant on.

## Errors

An error that a caller can act on is a named class extending `Error`, with
`name` set, thrown where the condition is detected and caught where a decision
can be made. Everything else is left to propagate: a job that cannot continue
fails, the worker records the failure, and the alarm fires. Never catch to log
and rethrow, never swallow, and never return `null` where a throw is honest.

## Dependencies

`pnpm` only, with the version pinned by `packageManager` and the lockfile
committed. A new dependency is added only when rungs 1 to 4 of Reuse have
failed, and the commit that adds it says which rung failed. The estate's own
packages are declared the way every service declares them today:
`@percaysovehicleintelligence/packages.ts.*` and `@percayso/linting` by caret
range, `@percaysovehicleintelligence/packages.node.services` and
`@percayso/cdk` pinned to an exact version. Every other dependency is declared
by caret range, as `pnpm add` writes it, and the committed lockfile is what pins
an install. The lockfile is never regenerated from scratch: an upgrade is
deliberate (`pnpm update <name>`), one package or family at a time, in its own
commit, so a breaking minor cannot arrive unnoticed. A family of packages
released together (`fumadocs-*`, `@tanstack/*`) is kept on one version and
upgraded together in one commit.

## Ignore lists

`.gitignore` carries the estate baseline, and a repo may add to it but never
drop from it:

```
node_modules
dist
coverage
cdk.out
.cdk.staging
cdk.context.json
.npmrc
.npmtoken
.env
.env.*
!.env.example
*.log
.DS_Store
```

`.prettierignore` holds only files that are generated and committed, because
Prettier already skips everything `.gitignore` lists: `pnpm-lock.yaml`,
`CHANGELOG.md` where a release tool writes one, `*.local.*`, `drizzle/**`
in the database package, and `CODING_STANDARDS.md` and `docs/standards/**`,
which this plugin writes and a repo's own Prettier config would otherwise
rewrite. Beside those, a file the repo's own code generates and commits in a
format of its own, such as a learned model's weights, is named by its path,
because formatting it would be undone by the next run. Nothing else belongs in
it.

No `.env` file, `.npmrc` or `.npmtoken` is ever tracked. `.env.example` is the
one `.env*` file in the repo. There is no `.gitattributes`; line endings are
each machine's `core.autocrlf`.

## Nothing dead

Every line of configuration, every dependency and every instruction in the
repo exists because something in the repo uses it. A scaffold copied from a
sibling is not a reason for any of it to be there.

- A declared dependency is imported somewhere in `src/` or `infrastructure/`,
  or it is dead.
- An environment variable in the vitest `env` block, or a key in `config/`,
  is read by code, or it is dead.
- An ESLint override names a rule that would otherwise fire on code the repo
  has, or it is dead.
- A README instruction (copy this file, run this command) refers to a file or
  script that exists, or it is dead.
- A file at the root is one the Layout section names or the repo's own job
  needs, or it is dead.

Dead things arrive with the ticket that uses them and leave in the commit that
stops using them.

## Tests

- Test names are full sentences stating the guarantee
  (`'never lets two workers own the same job'`).
- Assert at the seams — rows in, rows out — never internal call sequences or
  private state.
- Use a library's official test utilities over hand-rolled mocks
  (`ai/test`'s mock model, testcontainers).
- A test that depends on the time freezes the clock (`vi.useFakeTimers()` with
  `vi.setSystemTime`) or derives every timestamp from one `now`. Two clock
  reads compared in one assertion are a flaky test.
- Integration tests run against real Postgres via testcontainers,
  bootstrapped by replaying the database package's migrations, and skip loudly
  without a container runtime. A green run without Docker has verified nothing
  against Postgres.

## Logging

Structured events only: a dot-namespaced `domain.noun.verb` event name plus a
payload object (`logger.info('pipeline.job.claimed', { jobId, workerId })`).
Never interpolate values into the event name.

## Commits and pull requests

- Branches are `<type>/<short-name>`: `feat/`, `fix/`, `docs/`, `chore/`,
  `refactor/`, `perf/`.
- Commit and PR titles are conventional commits with one of these types:
  `feat`, `fix`, `docs`, `chore`, `refactor`, `perf`, `test`, `ci`, `build`,
  `revert`. While the apps are in development the type is plain `feat` or
  `fix`: never `feat!` and never a `BREAKING CHANGE` footer, because either
  cuts a major release.
- A reference to an issue in another repo is its full URL, never a bare `#n`,
  which the release tooling resolves against the wrong repo.
- One ticket, one PR. A one- or two-line edit found on the way rides along in
  the open PR rather than becoming its own.
- A PR that changes behaviour updates the README section that describes it in
  the same PR. A hard-to-reverse decision becomes an ADR in the same PR.
- Verify before opening a PR: `pnpm typecheck && pnpm lint && pnpm test`.
  Commit-time hooks run lint and prettier only; the full suite is the PR's job.
- A feature that was asked for ships on, with no config flag or default-off
  gate. A test that changes means the guarantee changed, and the PR says so.

## Documents

- A document is written only when a skill asks for one; the skill decides its
  shape and where it lives. No freehand plan, design note, study or working
  list.
- An undecided ruling lives in a GitHub issue, never in notes, commit messages
  or agent memory.
- The glossary is written as terms are settled, never ahead of them. A
  principle changes the rulebook, which never names a particular case.

## Repo shape

Every repo has, at its root:

- `README.md`, in the shape of the estate template: the Cazana logo block, a
  few plain paragraphs and a table of what the repo handles, then
  **Prerequisites**, **Local setup**, **Architecture** with a mermaid diagram,
  one **How a &lt;job&gt; runs** section per job or worker where there is a
  run to describe, and **Why it is built this way** as one bold-led bullet per
  decision with the alternative it turned down. Domain notes, deviations from
  a legacy system and configuration are optional sections between. Nothing in
  it restates a rule from here.
- `CLAUDE.md`, pointers only: it names the files that hold the rules and never
  restates one, so the two cannot drift. It fits on one screen.
- `CODING_STANDARDS.md`, this file, generated by the `cazana` plugin and never
  edited in place. Rules true of this repo only go in
  `docs/standards/local.md`, and a rule that sits there for long is a
  candidate for the estate.
- `CONTEXT.md`, the glossary.
- `docs/adr/`, numbered ADRs, superseded and never edited. The folder
  appears with the first ADR; an empty one, or a `.gitkeep`, is not a
  requirement.
- `.github/workflows/pr-checks.yml`, on `pull_request` to `main`: checkout
  with full history, the repo's `.github/actions/setup` with the org npm token,
  then `pnpm run build`, `pnpm run typecheck`, `pnpm run lint`,
  `pnpm run prettier` and `pnpm test`, in that order and all five, so a green
  check means the same thing in every repo. A service then writes the org npm
  token to `.npmtoken`, because `cdk diff` builds the Docker asset and the
  asset installs private packages, runs `cdk diff` against the sandbox
  account through the OIDC role, and posts its output as one comment on the
  PR, updated on every run (`gh pr comment --edit-last --create-if-none`,
  under `pull-requests: write`), so an infrastructure change is reviewed and
  not just run. Nothing else.
- `.github/workflows/lint-pr-title.yml`, running
  `amannn/action-semantic-pull-request` with the types the Commits section
  allows, because a squash merge takes the PR title as the commit that cuts
  the release.
- `.github/CODEOWNERS`, one line, `* @PercaysoVehicleIntelligence/engineers`,
  and no template comments.
- `.github/dependabot.yml`, the `npm` ecosystem through the `npm-github`
  registry and the `github-actions` ecosystem, daily, commit prefix `depbot`.
- The release workflow for the repo kind: a service or module has
  `deploy.yml` on push to `main`, running the setup action, the `.npmtoken`
  write for a service, and `cdk deploy`; a package has `publish.yml` on push
  to `main`, cutting the release and publishing to the org registry. One
  release system per repo, and the same one across a repo kind.
- **A deploy is scoped to what deploys.** `deploy.yml` and `publish.yml`
  carry this `paths-ignore` on their push trigger, so a change to a document
  or to repo plumbing never rebuilds an image, runs a `cdk deploy` or cuts a
  release:

  ```yaml
  paths-ignore:
    - '**/*.md'
    - 'docs/**'
    - '.github/CODEOWNERS'
    - '.github/dependabot.yml'
    - '.github/workflows/lint-pr-title.yml'
    - '.gitignore'
    - '.prettierignore'
    - '.env.example'
  ```

  `pr-checks.yml` has no path filter: Prettier checks the markdown, and a
  required check that never reports leaves a docs-only PR unmergeable.

`docs/agents/` is needed only where the Matt Pocock skills cannot use their
defaults: a repo with more than one glossary (it has a `CONTEXT-MAP.md`) or one
that triages issues other people file. `/setup-matt-pocock-skills` writes it.
