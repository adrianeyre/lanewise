# E2 — throwaway accounts, keys and disposable machines

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #11, label `prd:pen-test`). This is an **enablement** scope issue. It sets up the accounts, keys and machines that every scope issue signing in to a Host or asking a Model Provider uses. It probes no trust boundary of its own.

- **Trust boundary.** None. E2 makes sure that what the round holds is throwaway, so a Finding never costs a real credential, a real repository or real money (PRD §3: "Never the tester's own machine account, credential store or repositories").
- **Governed by.** `CONTEXT.md`: Host, Model Provider, Gateway, Issue Tracker, Jev. PRD §3 (engagement shape: grey-box, synthetic data, a Release on Windows and macOS in a disposable machine). ADR 0016 and ADR 0037 (Host sign-in through `git credential`), ADR 0020 (Model Provider keys in the OS credential store), ADR 0035 (Gateways), ADR 0036 (Jev), ADR 0038 (Issue Tracker tokens).
- **Code.** `SECURITY.md`, which asks reporters not to send real credentials, API keys or private repositories. The round keeps to the same rule.
- **Deliverable.** This file. It holds the inventory of what has to exist, built from what the code keeps (below), how to make each item, where it is written down, and how it is revoked. **Nobody but the owner can make the accounts**: this sandbox has no browser, no payment method, no Windows, no macOS and no Release, and is barred from Hosts, Model Providers and Issue Trackers. So every probe ends in a hand check for the owner. Nothing here was signed up for, and nothing is ticked off that wasn't done.

## What Lanewise keeps in a credential store, read from the code

A disposable machine's credential store must hold "only the above" (the brief). This is the full list of what the Desktop App can put there, so the owner can check a store against it before the round and after teardown. Every entry goes through the `keyring` crate (4.2.0, `commands/Cargo.toml:13`).

| Service | User name (one entry each) | What it holds | Read at |
| --- | --- | --- | --- |
| `com.adrianeyre.lanewise.model-provider` | `anthropic`, `gemini`, `openai`, `xai`, `meta`, `local`, `typesafe-jev` | A Model Provider's API key, or Jev's | `commands/src/model_provider.rs:19`; IDs at `app/src/ai/modelProviderDetails.ts:20`, `:31`, `:72`, `:80`, `:88`, `:96` and `app/src/ai/jev.ts:20` |
| `com.adrianeyre.lanewise.gateway` | the same IDs | A Gateway's address and up to 32 headers, as JSON | `commands/src/gateway.rs:24` |
| `com.adrianeyre.lanewise.issue-tracker` | `jira`, `trello` | Jira Cloud's site, email and API token, or Trello's Power-Up key and token, as JSON | `commands/src/issues/mod.rs:32`, `:50`–`:51` |

Host credentials are never kept by Lanewise. They are Git Credential Manager's, filled through `git credential fill` for each call and dropped afterwards (ADR 0016, ADR 0037), so they sit in the same store under Git Credential Manager's own names.

How each OS shows a Lanewise entry. This was read from the `keyring` crate's platform stores at the versions in `Cargo.lock`, and is what the hand checks below look for:

- **macOS (Keychain Access, login keychain).** A generic password whose *Where* (service) is the service above and whose *Account* is the user name. The store is `apple-native-keyring-store` 1.0.2.
- **Windows (Credential Manager → Windows Credentials → Generic Credentials).** The target is `<user name>.<service>`, such as `anthropic.com.adrianeyre.lanewise.model-provider`. The store is `windows-native-keyring-store` 1.1.0, `src/cred.rs`, with the default empty prefix, `.` divider and empty suffix.
- **Linux (Seahorse, or `secret-tool`).** A Secret Service item with the attributes `service` and `username` set as above. The store is `zbus-secret-service-keyring-store` 1.0.1.

## Probes from the brief

### 1. A throwaway account on GitHub.com, GitLab, Bitbucket and Azure DevOps, each with a private repository of its own

**What I did.** I read which Hosts the round needs: GitHub.com at Tier 2 and Tier 3 (ADR 0016, ADR 0040), and GitLab.com, Bitbucket Cloud and Azure DevOps Services at Tier 2 (ADR 0037). I also read what each one's sign-in and listing need. I made no account: the sandbox can reach no Host.

**Answer: owed by the owner (hand check A).** Each account must meet these conditions:

- It is made for the round alone, with an email address of the owner's that no other account uses, two-factor authentication on, and its recovery codes kept with its other details (below).
- It is a member of no real organization or team. It has no access to `adrianeyre/lanewise` or any other real repository, and no real repository has access to it.
- It holds one **private** repository, made by pushing one of E1's Hostile repositories (`pnpm pen-test:fixtures`, `docs/pen-test/E1.md`) or a synthetic commit. Its content includes a **canary line**: a random string made for that repository and used nowhere else. If the canary shows up in the Logs, the Diagnostics, a prompt or a Host page's requests, file contents left a private repository (S3, M1). The canary is recorded with the account, not here.
- Each Host's terms decide whether a second account may be made and how. The owner reads them before signing up. One throwaway Atlassian account can serve Bitbucket, the Jira Cloud site and Trello (probe 2), because all three sign in with it. Each still gets a token of its own.
- Sign-in is Git Credential Manager's browser flow on the disposable machine (ADR 0016, ADR 0037), so its token never passes through the owner's own machine. Where a hand check in ADR 0016 or ADR 0037 needs a personal access token with too few scopes, the token is made with the **least** scope that check needs, and with an **expiry no later than the round's end**.
- For Bitbucket, ADR 0037's hand check names an app password. Atlassian has been retiring app passwords in favour of scoped API tokens, so use an API token if an app password can no longer be made. This is a note for the ADR's hand check, not a Finding.

### 2. Throwaway Model Provider keys with a spending limit, a Jev key, and Jira Cloud and Trello tokens on throwaway sites

**What I did.** I read every key the Desktop App can keep (the table above), where Settings sends the user to make one (`app/src/ai/modelProviders.ts:60`–`:86`, `app/src/issues/issueWords.ts:10`, `:13`), and how Jev keys are given out (`docs/research/jev-ai.md:17`, `:33`). I made no key and used none. The sandbox's own `ANTHROPIC_API_KEY` is the harness's (R5), not a key for Lanewise, and no probe touched it.

**Answer: owed by the owner (hand check B).** Each key must meet these conditions:

- **Model Providers** (Anthropic, OpenAI, xAI, Google Gemini and, where the owner can get one, Meta's US-only preview). Each key is made in an organization, project or workspace of its own, belonging to the throwaway identity. It has a **hard spending limit**, or a small prepaid credit with automatic top-up off where the Model Provider has no hard limit (a budget alert alone isn't a limit). It gets an expiry at the round's end where the Model Provider offers one. A local Model Provider (`local`) needs no account: an OpenAI-compatible server on the disposable machine stands in, with a made-up key.
- **Jev.** Jev has been in early access since 15 September 2026, so a key may not be available to the owner. If it isn't, the scopes that need Jev (S1, M2) say so and test against the fake in `app/src/ai/jev.test.ts`, and nothing is faked.
- **Jira Cloud.** A free Jira Cloud site of the throwaway Atlassian account, with a few synthetic Issues assigned to it. One of them has markup and prompt-injection text in its summary, as E1's `injection` fixture has (W1, M1). The API token is made with an expiry at the round's end.
- **Trello.** A Power-Up of the throwaway account's own, for its key, and a token with an expiry (Trello offers `1day` and `30days`) that covers the window. A board holds a few synthetic cards, one carrying the same kind of payload.
- **Gateway** (W4). No account is needed. A local HTTP server on the disposable machine (`http://` on this computer is allowed, ADR 0035) stands in, with made-up header values. A real Gateway is optional and, if used, is throwaway on the same terms.

### 3. A Windows and a macOS virtual machine (or user account) with the latest Release installed, whose credential store holds only the above

**What I did.** I listed what the Desktop App can put in each OS's credential store and how each OS names it (the table above). The sandbox has no Windows, no macOS and no Release (`docs/processes/running-sandcastle.md`, "What a sandbox here cannot do").

**Answer: owed by the owner (hand check C).** A virtual machine is better than a user account. Snapshotting it clean makes reset and teardown one step, and its keychain or Credential Manager can't be the owner's by mistake. Free tooling only: UTM or Tart for a macOS guest on Apple hardware, and Hyper-V, VirtualBox or UTM for a Windows evaluation image.

### 4. A Linux source build for exploring

**What I did.** I built the Desktop App from this tree in this sandbox with `pnpm desktop:build --no-bundle`. That is the release profile, with no installer and no update packages, because the sandbox has no Update key. I also checked what this sandbox holds that a credential could be in, by name only and never by value:

- no `GH_TOKEN` or any other GitHub token, no `~/.git-credentials`, no `gh` configuration and no `credential.helper` (H14's design: the sandbox gets no GitHub token);
- no Secret Service running, so Lanewise here keeps no key. Settings would say the credential store isn't available (ADR 0020, "Consequences");
- the harness's own Model Provider variables, which belong to R5 and were not used.

**Answer: it exists, for exploring only. 12 October 2026.** `pnpm desktop:build --no-bundle` finished in about three minutes and built `target/release/lanewise-desktop` (Lanewise 1.1.1). Run under `xvfb-run -a` for 20 seconds with `HOME` and the `XDG_*` folders pointed at a fresh folder under `/tmp`, it started and kept running. It wrote its Logs, local storage and webview caches only there. Its Logs held two lines: that Lanewise 1.1.1 started on Linux, and the Git Setup ("git 2.47.3, with Git Credential Manager not a credential helper"). Starting it may also have made the version check of ADR 0047, which carries no credential. No repository was opened, so nothing was fetched.

This build is enough to explore the webview, the command API and the Hostile repository fixtures. It is not a Release, so a Finding still has to be confirmed on one (PRD §3). It also can't explore anything that needs a key kept until a Secret Service runs (hand check D). Each Sandcastle run is a fresh Linux source build of this kind, with nothing in its credential store.

## Where it is written down, and who can read it

- **Only in the owner's password manager**, in a vault or folder of its own named for the round. Each entry records the role (such as "the round's GitLab.com account"), its sign-in, its two-factor recovery codes, its private repository's canary, each token or key with its scope, spending limit and expiry, the date it was made, and the date it was revoked.
- **Never inside a clone of `adrianeyre/lanewise`, not even a gitignored file.** Sandcastle bind-mounts the clone into an agent's container (`docs/processes/running-sandcastle.md`), so a file there is readable by a run that was given public text (H14).
- **Never in `.sandcastle/.env`.** Sandcastle forwards exactly the keys that file names, from the file or from the owner's shell (`docs/processes/running-sandcastle.md`, "A key named with no value is filled from your shell"). A throwaway key named there would reach every run.
- **Never in an issue, a comment, an advisory, a commit or this folder.** The public record names accounts by role only. A Finding's steps say "the round's GitHub.com account", never its username or a key.
- On the disposable machines, credentials live only where Lanewise and Git Credential Manager put them, entered by hand or through the browser sign-in. They are not left in a notes file, a shell history or the clipboard history.

## Hypotheses this enables (PRD §5)

E2 starts from no hypothesis of its own. It is the pre-condition for the scopes that sign in or ask a Model Provider, recorded here so each has a home:

- **H8** (a Model Provider's key crosses IPC in plaintext) needs a real, throwaway key in a Release's credential store. Dated answer: owed by S1 (#22).
- **H9** (the Logs keep what they say they don't) needs real token shapes: Atlassian, Trello, Azure DevOps and Bitbucket tokens without a known prefix. Dated answer: owed by S3 (#24).
- **H2, H3** (Host pages) need a signed-in Host account on a Release. Dated answer: owed by W2 (#15).
- **H4, H5** (the allow-list, and requests outside it) need a local Model Provider and a real one to watch. Dated answer: owed by W3 (#16).
- **H10** (a Conflict Hunk can write its own Suggestion) needs a throwaway Model Provider key on a Release, beyond the mocks. Dated answer: owed by M1 (#25).
- **H14** (Sandcastle hands an agent public text and a token) is checked by E2 only in one respect. **12 October 2026:** this sandbox holds no GitHub token and no Lanewise credential, and the round's throwaway credentials are kept out of the clone and `.sandcastle/.env` by the rule above. The rest is owed by R5 (#31).

## Hand checks (need the owner, a real account, a real key or another platform)

**A. Host accounts**

1. For each of GitHub.com, GitLab.com, Bitbucket Cloud and Azure DevOps Services, make a throwaway account on the terms in probe 1, with two-factor authentication on. Record it in the password manager.
2. In each, make one private repository. Push to it, from the disposable machine, a fixture from `pnpm pen-test:fixtures` or a synthetic commit, with a file holding a fresh canary line. Record the canary.
3. Check that the account belongs to no organization but its own, and that it has no access to `adrianeyre/lanewise`.

**B. Keys and tokens**

1. For each cloud Model Provider, make a key in a project or workspace of the throwaway identity, with a hard spending limit (or a small prepaid credit with top-up off), and an expiry at the round's end where offered. Record the key, the limit and the expiry.
2. Ask TypeSafe for a Jev key at `console.typesafe.ai/keys`. If early access doesn't give one, record that S1 and M2 have no live Jev.
3. Make a free Jira Cloud site and a Trello board for the throwaway Atlassian account, with synthetic Issues, and make a Jira API token and a Trello Power-Up key and token, each expiring by the round's end. Record them.

**C. Disposable machines**

1. Make a Windows virtual machine and a macOS virtual machine, or a user account of their own on each, with no sign-in to the owner's Apple ID, Microsoft account or password manager. Take a clean snapshot.
2. Install Git 2.40 or later with Git Credential Manager (`docs/installing.md`), then the latest Release from `https://github.com/adrianeyre/lanewise/releases/latest`, past the Gatekeeper or SmartScreen warning the README describes (out of scope, PRD §3.1).
3. Open Keychain Access (macOS) or Credential Manager → Generic Credentials (Windows) and check the store holds **nothing** from the owner. Take the snapshot "before credentials".
4. Sign in to each Host through Lanewise (Clone → a Host's repositories, which runs Git Credential Manager's browser sign-in). Save each key and token in Settings.
5. Check the store again. It should hold only Git Credential Manager's entries for the four Hosts and Lanewise's entries from the table above, under exactly those services and user names. Anything else is either a stray to remove or, if Lanewise put it there, a lead for S2 (#23). Take the snapshot "round start".

**D. The Linux source build**

1. On a disposable Linux machine (not the owner's own account), follow `docs/development.md` and run `pnpm desktop:build --no-bundle`.
2. Run it with `HOME` and `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME` and `XDG_STATE_HOME` pointed at a fresh folder, so its Settings, Logs and webview storage start empty and are thrown away afterwards: `xvfb-run -a target/release/lanewise-desktop` without a screen.
3. To explore key handling, start a session with a Secret Service, such as GNOME Keyring under `dbus-run-session`, so Settings can keep a throwaway key. Without one it says the credential store isn't available.
4. Remember that a Finding is confirmed on a Release (PRD §3), not on this build.

**E. Teardown, when the round ends**

1. In Lanewise's Settings on each machine, forget every key, Gateway and Issue Tracker account, then check the credential store holds none of the table's entries. Forgetting is ADR 0020's and ADR 0038's promise, and the snapshot shows whether it held.
2. Revoke every key and token at its source: each Model Provider's key page, TypeSafe's console, Atlassian's API tokens page, and Trello's Power-Up admin page (delete the Power-Up). Revoke Git Credential Manager's OAuth grant on each Host.
3. Delete the private repositories, then the Host accounts, the Jira Cloud site, the Trello board and the throwaway Model Provider organizations or workspaces, and remove any payment method on them.
4. Delete both virtual machines and their snapshots, or the user accounts and their keychains.
5. Fill in "Revoked or deleted" for every row of the private inventory. The round isn't over until every row has a date.
