# E3 — rules of engagement

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #12, label `prd:pen-test`). This is an **enablement** scope issue. It writes the rules every tester agrees to before the window opens, and probes no trust boundary of its own.

- **Trust boundary.** None. E3 decides what a tester may do, so the round never harms a Host, a Model Provider, an Issue Tracker, a real person or a Lanewise user while it tries to harm Lanewise.
- **Governed by.** PRD §3 (engagement shape) and §4 (Disclosure), `SECURITY.md`. `CONTEXT.md`: Pen-test round, Finding, Hostile repository, Host, Model Provider, Issue Tracker, Gateway.
- **Deliverable.** [`docs/product-requirements-document/pen-testing-rules-of-engagement.md`](../product-requirements-document/pen-testing-rules-of-engagement.md), beside the PRD. It is linked from the PRD's §3 and §6, and from `SECURITY.md`'s "What's in scope" for outside researchers. A test in `app/scripts/community.test.ts` ("the pen-testing PRD and the security policy link to the rules of engagement, which date each window") holds both links and the window's row. Adding the file to that test's documents also holds every path it names to the tree, and its slug to `adrianeyre/lanewise`.

## Probes from the brief

### 1. The window's dates

**What I did.** I read what has to be in place before a round account is used: E2's accounts, keys and machines (`docs/pen-test/E2.md`, hand checks A to C), and the expiries they're made with. Every token expires no later than the round's end (`docs/pen-test/E2.md:40`), and Trello's longest is 30 days (`docs/pen-test/E2.md:52`). PRD §3 says the rules are written before the window opens (`docs/product-requirements-document/pen-testing.md:45`).

**Answer: set, 12 October 2026.** Round 1 runs from Monday 19 October 2026 to Sunday 15 November 2026, UK time, 28 days (rules §1). That fits inside one 30-day Trello token with a margin. The window opens only once the rules are on `main` and E2's hand checks A to C are done. If they aren't done in time, only the owner moves the dates, with a commit to the rules on `main` before the date passes. Before it opens, only preparation happens: the source, and Sandcastle runs on synthetic data, with no account, key or Release. An outside researcher, testing with accounts of their own, isn't bound to the window.

### 2. The accounts and machines that may be used (E2), and nothing else

**What I did.** I read E2's inventory (`docs/pen-test/E2.md`) and PRD §3's limits (`docs/product-requirements-document/pen-testing.md:43`–`:44`). I checked this sandbox for anything a credential could be in, by name only and never by value. It holds no GitHub token, no `gh` configuration, no `credential.helper` and no Lanewise credential. The one Model Provider variable is the harness's own, which no probe used.

**Answer: written, rules §3.** The round uses only E2's throwaway accounts and keys, E2's disposable machines and the Sandcastle containers, and synthetic data (E1's fixtures, E2's canaries). An outside researcher uses equivalents of their own. The rules name what's never used: the tester's own account, store, profile or repositories; the account that maintains `adrianeyre/lanewise`; and anything real. They also say what a tester does on coming across something real: stop, keep nothing, tell the owner privately.

### 3. Nothing done to a Host, Model Provider or Issue Tracker beyond what a normal user's account does; no pushing to any repository but the round's own

**What I did.** I read where the Desktop App sends requests, so the rules could say what "normal" includes. The window's HTTP plugin may only reach the five cloud Model Providers, TypeSafe, the Model catalog, the repository's `package.json` and this computer (`desktop/capabilities/default.json:15`–`:24`, held by `app/src/platform/allowList.test.ts:29`). The Updater asks only the latest Release's `latest.json` (`app/src/platform/allowList.test.ts:49`). The core reaches Hosts' APIs, such as `https://api.github.com` (`commands/src/hosts/github.rs:70`) and `https://api.bitbucket.org/2.0` (`commands/src/hosts/bitbucket.rs:61`), and Jira Cloud sites (`commands/src/issues/jira.rs:34`). It fetches on its own as the window is focused, at most every 30 seconds (`app/src/repository/useRemoteOperation.ts:19`, ADR 0044). I read which services are out of scope (`docs/product-requirements-document/pen-testing.md:49`) and how E1 proves a command ran, with a marker file under `lanewise-pen-test-markers` in the OS temp folder (`app/scripts/pen-test/buildFixtures.ts:33`).

**Answer: written, rules §4 and §5.** "Normal" is what Lanewise does through its UI, including its own fetches and checks, plus what a service's website or `git` lets the round's account do to its own repositories, sites and boards, plus watching Lanewise's traffic through a local proxy on the disposable machine. These are ruled out:

- scanning, fuzzing, floods, deliberately running into a rate limit, or replaying altered requests at a service;
- anything outside the round's own accounts;
- spending past a key's limit;
- a Hostile repository or payload anywhere public.

A payload only writes a marker file, or sends a canary to a listener on the same machine. Pushing goes only to E2's private repositories and E1's local remotes. Nobody pushes, opens a Pull Request or comments on `adrianeyre/lanewise`, or makes a public fork of it, as a test. Nobody publishes a Release, `latest.json` or Model catalog change to test the updater or catalog. Agents push nothing.

### 4. The private channel for a critical Finding, and that a lead with a concrete way to do harm goes there first

**What I did.** I read `SECURITY.md`'s private vulnerability reporting and its email fallback (`SECURITY.md:13`–`:14`), the issue forms' link to it (`.github/ISSUE_TEMPLATE/config.yml`), PRD §4 (`docs/product-requirements-document/pen-testing.md:62`–`:63`), PRD §7's severity table (`:178`) and PRD §10's one-day target (`:208`).

**Answer: written, rules §6.** The channel is private vulnerability reporting on `adrianeyre/lanewise`, with the email as fallback. Every lead with a concrete way to do harm goes there first, whatever its severity and whoever found it.

- An agent writes the lead only in its final message, under `## PRIVATE LEADS`, and the owner files it.
- A possibly critical lead reaches the owner the same day. Anything else is filed within a day.
- The fix is made in the advisory's temporary private fork, because a public diff discloses the hole.

The rules list everywhere a lead must never appear first, and say what counts as "a concrete way to do harm": when in doubt, it's private. They also say what may be public: hypotheses, disproved probes, and hardening described as defence in depth.

### 5. Who may run the round

**What I did.** I read PRD §3's "Who tests" (`docs/product-requirements-document/pen-testing.md:41`) and how a Sandcastle run is launched and merged back (`docs/processes/running-sandcastle.md`, `.sandcastle/main.ts:132`–`:177`). The run merges back to the branch it was launched from, and refuses to start on `main`.

**Answer: written, rules §2.** Only three kinds of tester run the round:

- the owner;
- agents briefed by one scope issue each, in a Sandcastle container, given the brief by the owner, with no GitHub token, none of E2's accounts and no Lanewise credential. They file, label and push nothing, and the owner reviews their commits in the round's pull request;
- outside researchers, through private vulnerability reporting, on their own disposable machines and throwaway accounts.

Nobody tests on someone else's machine, account, repository or service. The round isn't independent, and its report says so.

## Hand checks (need the owner)

**A. Before the window opens**

1. Merge the round's pull request, so the rules are on `main` and linked from the PRD.
2. Check that E2's hand checks A to C are done. If they won't be by Monday 19 October 2026, move both dates in the rules' §1 with a commit to `main` before then.
3. Signed in as one of the round's throwaway GitHub accounts, which has no access to `adrianeyre/lanewise`, open `https://github.com/adrianeyre/lanewise/security/advisories/new`. Check that it shows the private report form, so private vulnerability reporting is on for an outsider. If it isn't, turn it on under Settings → Code security, and then check again.
4. Send a test email with "Lanewise security" in the subject from a throwaway address to the fallback address in `SECURITY.md`, and check that it arrives, not in spam.

**B. For every Sandcastle run during the round**

1. Check that `.sandcastle/.env` names no throwaway key of E2, and that no GitHub token reaches the container, whether named there or filled from your shell. Fetch the brief on the host instead.
2. Read the run's final message for `## PRIVATE LEADS`, and file each lead as a draft advisory within a day (rules §6).

**C. When the window closes**

1. Follow the rules' §8: E2's hand check E, deleting the evidence, and the report that says who ran the round and that it isn't independent.
