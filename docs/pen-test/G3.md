# G3 — Lanewise's own writes and deletes

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #20, label `prd:pen-test`). G3 probes every place Lanewise writes, creates or removes a file by a path a Hostile repository chose, whether it does so itself or through `git`: resolving conflicts, Whole-file choices, Undo and Redo, and checkouts. It starts from §6 G3, and no hypothesis of §5 names it.

- **Trust boundary.** Paths a Hostile repository chooses, from its index, its trees and its working tree, on one side; the file system outside its working tree, on the other. Between them are `core/src/conflict.rs` (a Resolution and a Whole-file choice), `core/src/operation.rs` (an In-Progress Operation continued or aborted), `core/src/stash.rs` (a stash apply's record), `core/src/branch.rs` (a checkout), `core/src/clone.rs` (a stopped clone's leftovers) and `app/src/repository/undo.ts` (Undo and Redo).
- **Governed by.** `CONTEXT.md`: Resolution, Whole-file choice, Undo, In-Progress Operation, Hostile repository, Finding. ADR 0017 (In-Progress Operations resolved through `git`, and a stash apply's record in the Git directory), ADR 0018 (a Resolution written to the working tree, never through a symbolic link), ADR 0019 (Whole-file choices through the index and `git checkout`), ADR 0045 (Undo and Redo through the commands Lanewise already has).
- **Deliverables.** `core/tests/hostile_paths.rs`, which pins what held:
  - `a_merge_that_makes_a_folder_a_link_leaves_its_conflicted_files_written_inside_the_working_tree`: a merge whose Ours turned a folder into a symbolic link to a folder outside, against a Theirs that changed a file in it, leaves the link moved aside and the conflicted file in a real folder; its Resolution, and Keep Ours for the link, are written inside the working tree, and the folder outside is untouched;
  - `checking_out_a_commit_whose_tree_names_a_parent_folder_writes_nothing_and_leaves_head`: checking out a commit whose tree names `..` fails, `HEAD` stays, and nothing is written beside the working tree.

## How it was probed

This was done headless on Linux, with `gix` 0.88.0 (the version in `Cargo.lock`) and `git` 2.47.3, on ext4, which is case-sensitive. Everything was written under `/tmp`. Nothing was fetched from a Host, and nothing was committed but the deliverables.

1. **Built E1's Hostile repositories** with `pnpm pen-test:fixtures`, and used `paths` (a tree naming `..`, `sub/..`, symbolic links to an absolute and a climbing path, a case collision and Windows-reserved names, never checked out) and the `conflict-*` family.
2. **Listed every place the core writes, creates or removes a file itself** (`std::fs` in `core/src/`, `commands/src/` and `desktop/src/`), and every `git` it runs that writes the working tree, and for each asked where its path comes from.
3. **Ran the core itself** in a scratch crate under `/tmp` that depends on `lanewise-core` by path, calling `read_operation`, `read_conflict`, `resolve_conflict`, `resolve_whole_file`, `abort_operation` and `check_out`, against E1's repositories and against repositories made under `/tmp` for each probe, with a folder outside each working tree to watch.
4. **Made Git's own conflicts on the paths in question**: a folder one side turned into a symbolic link, the other side changing a file in it.
5. **Read Undo and Redo** (`app/src/repository/undo.ts`) for every command each step sends.
6. **Pinned what held** in the tests above.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Every place Lanewise writes or removes a file by a path a repository chose

**What I read.** The places, and who does the writing:

| Where | What it writes or removes | Written by |
| --- | --- | --- |
| `resolve_conflict` (`core/src/conflict.rs:165-186`) | A Resolution, at a path the index lists as conflicted (`core/src/merge.rs:287-299`), then `git add` | Lanewise (`fs::write`), then `git` |
| `resolve_whole_file`, keeping a side (`core/src/conflict.rs:188-230`) | That side's index entry at stage 0 (`git update-index --index-info`), then `git checkout -- <path>`, with `GIT_LITERAL_PATHSPECS` | `git` |
| `resolve_whole_file`, deleting (`core/src/conflict.rs:198-204`) | `git rm --force -- <path>`, with `GIT_LITERAL_PATHSPECS` | `git` |
| Mark resolved and Mark unresolved (`core/src/operation.rs:236-276`) | `git add` and `git update-index --unresolve`, the index alone | `git` |
| Continue and Abort (`core/src/operation.rs:209-234`, `:418-480`) | `git commit`, `git rebase`, `git merge --abort`, `git reset --merge` and `git restore`; for a stash apply Lanewise ran, the stash's untracked files it wrote are removed (`core/src/operation.rs:525-544`) | `git`, and Lanewise (`fs::remove_file`) for those untracked files |
| A stash apply's record (`core/src/stash.rs:492-521`) | `<git dir>/lanewise/stash-apply`, a fixed name holding commit and tree IDs only | Lanewise |
| A checkout, and Undo and Redo (`core/src/branch.rs:308-404`, `app/src/repository/undo.ts:118-194`) | `git switch`, `git reset`, `git branch`, `git stash` | `git` |
| A stopped clone (`core/src/clone.rs:97-150`) | What the clone made at a destination the user chose, never following a link (`fs::symlink_metadata`, `DirEntry::file_type`, `fs::remove_dir_all`) | Lanewise, at a path the user chose, not the repository |
| Staging hunks (`core/src/stage.rs:134-160`) | `git apply --cached`, the index alone | `git` |
| The Logs (`commands/src/logs.rs`) | Rolling files in the OS's log folder, whose names Lanewise chooses | Lanewise, at no path a repository chose |

In `commands/src/`, only the Logs call `std::fs`, and `desktop/src/` calls it nowhere. Undo and Redo send only `previewReset`, `reset`, `checkOut`, `createBranch`, `deleteBranch`, `createStash` and `popStash` (`app/src/repository/undo.ts:136-194`), as ADR 0045 says: each is `git`, with the guards those commands already have, so Undo and Redo add no write of their own.

**What held.**

- Every write and removal **through `git`** is held to `git`'s own path checks: a pathspec outside the repository is refused (`fatal: … is outside repository`), as is a tree entry naming `..` (`error: invalid path '..'`), and `git` never writes through a symbolic link in the working tree. Whole-file choices, Mark resolved and unresolved, Continue, Abort's `git` steps, checkouts, Undo and Redo are all of this kind.
- **A Resolution is never written through a symbolic link at its own path**: `resolve_conflict` refuses one as `notText` (`core/src/conflict.rs:171-178`), pinned already by `a_resolution_is_never_written_through_a_symbolic_link` (`core/tests/conflict.rs:314`). Keeping a side writes a regular file in a link's place, never through it (`a_side_kept_whole_is_never_written_through_a_symbolic_link`, `core/tests/conflict.rs:654`).
- **A stash apply's record** is at a name Lanewise chooses, in the Git directory, holding only IDs Lanewise wrote.
- **A stopped clone's leftovers** are removed at the destination the user chose, and a link is removed as a link, never followed.

### 2. Paths from the index, from trees and from the working tree

**What I did.** Opened E1's `paths` repository and checked its hostile commit out through the core; made Git's own merge conflict over a folder one side made a symbolic link; and called `read_conflict`, `resolve_conflict` and `resolve_whole_file` on the paths each left conflicted.

**What I read.** A conflicted path comes from the index, through `gix` (`core/src/merge.rs:287-299`) for `resolve_conflict`, and through `git ls-files --unmerged -- <path>` (`core/src/conflict.rs:249-280`) for reading a conflicted file and for a Whole-file choice. The paths a Continue or an Abort works on come from trees, through `git diff --name-only` and `git ls-tree -r` (`core/src/operation.rs:482-506`). The working tree is read with `fs::symlink_metadata` for a conflicted file's own path (`core/src/conflict.rs:150-157`).

**What held.**

- **Trees.** Checking out a commit whose tree names `..`, or `sub/..`, fails in `git switch` with `invalid path`, before anything is written; `HEAD` stays, and nothing appears beside the working tree (`checking_out_a_commit_whose_tree_names_a_parent_folder_writes_nothing_and_leaves_head`). The status read that follows refuses the tree too (`gix`: `Could not create index from tree`).
- **The working tree, as Git leaves it.** A merge whose Ours made `sub` a symbolic link to a folder outside, against a Theirs that changed `sub/file.txt`, stops with Git moving the link aside to `sub~HEAD` and writing `sub/file.txt` in a real folder. Resolving `sub/file.txt` and keeping the link as Ours wrote both inside the working tree, and the folder outside kept its file as it was (`a_merge_that_makes_a_folder_a_link_leaves_its_conflicted_files_written_inside_the_working_tree`).
- **The index.** Reading a conflicted file, and both Whole-file choices, take the path to `git ls-files -- <path>` with `GIT_LITERAL_PATHSPECS` first, so a path outside the repository fails there, before any file is touched.

### 3. `..`, absolute paths, symbolic links anywhere along a path, and case-folding on Windows and macOS

**What I did.** The `..`, `sub/..`, absolute-link and climbing-link entries of E1's `paths` repository, and the conflicts of probe 2.

**What held.** As probe 2: a tree's `..` and `sub/..` are refused by `git` on checkout; an absolute or climbing symbolic link in a tree is written by `git` as a link, never followed, and a link at a conflicted file's own path is refused by `resolve_conflict` and replaced, not followed, by a Whole-file choice; a folder made a link by one side of a merge is moved aside by Git, leaving its conflicted files in a real folder.

**Case-folding** can't be shown on this sandbox's case-sensitive file system, and needs a Release on macOS (APFS, case-insensitive by default) and on Windows (NTFS). Hand check B does it.

## Hand checks (need the owner)

Do these once on macOS and once on Windows, in the disposable account of the rules of engagement (§3), with the latest Release installed. The marker folder is `lanewise-pen-test-markers` in the OS temp folder: `$TMPDIR` on macOS, `%TEMP%` on Windows. On Windows, do them once with Git for Windows' default `core.symlinks=false` and once with Developer Mode on and `core.symlinks=true`.

**A. Resolving each `conflict-*` repository's conflicts**

1. In a clone of this tree, run `pnpm pen-test:fixtures`. It says where the Hostile repositories are.
2. Make an empty folder beside the fixtures, named `outside`, and put one file in it, `outside.txt`, holding `untouched`.
3. Open Lanewise, and open each of `conflict-merge`, `conflict-rebase`, `conflict-cherry-pick` and `conflict-revert` in turn. Each shows the Conflicts page.
4. For each conflicted file, choose it, and resolve it: a text file with Accept Theirs and Mark resolved; a symbolic link or binary file with each Whole-file choice in turn, using Mark unresolved in Conflicted files between them. Then Abort, and open it again to do Continue.
5. After each step, check that `outside` holds only `outside.txt`, still saying `untouched`, that nothing new is beside the fixtures' folder, and that the marker folder is empty.

**B. Case-folding**

1. In a disposable folder on the system volume (APFS on macOS, NTFS on Windows), run `pnpm pen-test:fixtures --out <that folder>` and open the `paths` repository in Lanewise.
2. In the Commit graph, check out its commit "hostile paths, never checked out". Note what Lanewise says; `HEAD` should not move.
3. Repeat hand check A in this folder, and with `outside` made beside it.
4. After each step, check as A's step 5 says, and also that nothing in the repository's `.git` folder changed but what Git itself changes for that step (compare a copy of the `.git` folder taken first).
5. Record, for each step, what happened. A file written or removed outside the working tree, a change to `.git/config` or `.git/hooks`, or any marker, is a lead: file it as PRD §7 says, privately first under PRD §4.

**C. Undo and Redo**

1. In a disposable repository made from `paths`'s first commit, commit, check out a branch, make one and stash, through Lanewise's Toolbar.
2. Undo each in turn and Redo them, by the buttons and with Ctrl+Z (⌘Z) and Ctrl+Shift+Z (⇧⌘Z).
3. After each, check as A's step 5 says.
