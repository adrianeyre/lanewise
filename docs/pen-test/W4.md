# W4 — Gateways

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #17, label `prd:pen-test`). W4 probes Gateways: an address a Model Provider's or Jev's requests go to in place of its own API, with headers of its own, kept by the core (ADR 0035). It starts from §6's W4, which no hypothesis of §5 names on its own.

- **Trust boundary.** A Gateway's secret headers, which the UI never sees, and the address they were saved for. On one side is the main webview, which holds `call` and so the four Gateway commands: `gatewayOf`, `saveGateway`, `forgetGateway` and `gatewayRequest` (ADR 0003). On the other are the OS credential store, where a Gateway is kept, and the network, where its requests go. Between them is `commands/src/gateway.rs`.
- **Governed by.** `CONTEXT.md`: Gateway, Model Provider, Jev, Logs, Finding. ADR 0035, with ADR 0020 (keys in the OS credential store and the HTTP allow-list), ADR 0028 (the Logs), ADR 0036 (Jev) and ADR 0051 (this computer's servers).
- **Deliverables.** Tests that pin what held:
  - `a_redirect_comes_back_as_it_was_answered_and_nothing_follows_it` in `commands/src/gateway.rs`;
  - `a_request_stays_on_its_gateways_host_whatever_its_path_and_sends_no_header_http_sets_itself` in `commands/src/gateway.rs`;
  - more addresses refused in `only_an_https_address_or_one_on_this_computer_is_a_gateway_and_http_keeps_its_own_headers`;
  - more URLs refused in "a request anywhere else, or of another method, is never sent" in `app/src/ai/gateway.test.ts`.

## How it was probed

This was done headless on Linux, with `ureq` 3.4.2 and `keyring` 4.2.0, the versions in `Cargo.lock`. Everything was written under `/tmp`. Nothing was sent to a real Gateway, Model Provider or Host, and nothing was committed but the deliverables.

1. **Read** `commands/src/gateway.rs`, every caller of its four commands in the UI, the command API's `call` and its logging (`commands/src/lib.rs`, `commands/src/logs.rs`), and the parts of `ureq` 3.4.2 that decide where a request goes and what it carries.
2. **Ran `gateway.rs` itself** in a scratch crate under `/tmp`. It was a copy of the file, with the Gateways kept in memory as its own tests keep them, never in a credential store. Listeners on `127.0.0.1` logged every request line, header and body that reached them, and answered as each probe needed: `200`, a `307` naming a second listener, or an answer that isn't UTF-8. A local `https` server with a self-signed certificate stood in for a Gateway the OS doesn't trust.
3. **Pinned what held** in the tests above, in the tree.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. That a Gateway's secret headers go only to the address they were saved for, through every command that changes or uses a Gateway

**What I read.**

| Where | What it does with a header's value |
| --- | --- |
| `gatewayOf` (`commands/src/gateway.rs:226`) | Tells the UI the address and the headers' names. Never a value |
| `saveGateway` (`gateway.rs:239`) | Takes the address and up to 32 headers from the UI. The address must be `https://`, or `http://` to `localhost` or `127.0.0.1`, with no user, query, fragment or space, and all ASCII (`valid_url`, `gateway.rs:114`). A name must be an HTTP token, and not one of the eight HTTP sets itself (`valid_header`, `gateway.rs:135`, `RESERVED`, `gateway.rs:36`). It answers `()`, or an error that names a header by its name alone |
| `forgetGateway` (`gateway.rs:270`) | Deletes the credential store's entry, address and headers together |
| `gatewayRequest` (`gateway.rs:276`) | Adds the request's path to the kept address (`gateway.rs:287`). Drops the request's headers that share a name with a kept one, whatever their case, then adds the kept ones (`gateway.rs:297`). Sends it through one `ureq` agent that follows no redirect (`gateway.rs:313-314`) |
| A header's `Debug` (`gateway.rs:55`) | Shows its name and "hidden" |
| `call` and the Logs (`commands/src/logs.rs:147`) | A command is logged by its name, and a failure by its kind. A request that isn't what a command takes is logged without its message, which quotes the request (`logs.rs:162`) |
| The UI | Settings shows a kept header's name, with its value field empty and "Kept: type to replace" (`app/src/settings/GatewaySettings.tsx:65`, `:165`). A Model Provider's requests, and Jev's, go through `gatewayFetch` where a Gateway is kept (`app/src/ai/requests.ts:68`, `app/src/ai/jev.ts:100`). It hands `gatewayRequest` only a request for the Model Provider's own `https://<host>`, as a path, and only `GET` or `POST` (`app/src/ai/gateway.ts:17`, `:21`, `:29`) |

**What the runs showed.**

| Run | What reached which listener |
| --- | --- |
| A header kept for a Gateway at one listener, and a `POST /v1/messages` through `gatewayRequest` | That listener alone, with the kept header and the kept address's path in front |
| The page's request carrying a header of the same name as a kept one, in another case | The kept value alone |
| The Gateway answering `307`, with `location` naming a second listener | The first listener alone. The page was handed the `307` and its `location`, and the second listener saw nothing |
| A Gateway at an address where nothing listens | Nothing sent. The error said only "The request to the gateway failed." or which kind of failure it was, never the address |
| `gatewayOf` after saving | The names alone |
| `forgetGateway`, then `gatewayOf`; and `gatewayRequest` with no Gateway kept | Nothing kept; `noGateway`, with nothing sent |

**What held.** No command hands the page a header's value: not `gatewayOf`, not an error, not a header's `Debug`, and not a log line. In each run above, `gatewayRequest`'s request, with the kept headers, reached the kept address and nowhere else, and a redirect was handed back to the page, not followed. `forgetGateway` removes every header with the address. The two new Rust tests pin the redirect and the headers.

### 2. That `gatewayRequest` stays under its Gateway's address for every encoding of a path

**What I read.** `gatewayRequest` joins the kept address and the path as text (`gateway.rs:287`). It refuses a path that doesn't start with `/`, or holds `..`, `://`, `#` or a space (`gateway.rs:281-283`). `ureq` makes the request from the joined text. The address has no `?`, `#` or `@`, so its host and port end where its own path, or the request's, begins.

**What the runs showed**, with the Gateway kept at `http://127.0.0.1:<port>/anthropic`:

| Path | Request line, at the Gateway's own listener |
| --- | --- |
| `/v1/messages` | `/anthropic/v1/messages` |
| `//elsewhere.example/x` | `/anthropic//elsewhere.example/x` |
| `/@elsewhere.example/x` | `/anthropic/@elsewhere.example/x` |
| `/http:/elsewhere.example` | `/anthropic/http:/elsewhere.example` |
| `/:elsewhere.example`, `/%2felsewhere.example` | `/anthropic/:elsewhere.example`, `/anthropic/%2felsewhere.example` |
| `/x?u=//elsewhere.example` | `/anthropic/x?u=//elsewhere.example` |
| `/./x`, `/x/.` | `/anthropic/./x`, `/anthropic/x/.` |

| Path | Refused before anything was sent |
| --- | --- |
| `v1/models`, `?q`, the empty path, `http://elsewhere.example/x` | `invalidPath`: it doesn't start with `/` |
| `/../x`, `/..%2fx`, `/..;/x`, `/\..\x`, `/x?a=..` | `invalidPath`: `..` |
| `/x://y` | `invalidPath`: `://` |
| `/x#y`, `/x y`, `/x\r\nHost: …` | `invalidPath`: `#` or a space |
| `/x\ty`, `/x\0y` | The request couldn't be made, so nothing was sent |

The listener saw every request it was sent with its own `host`. A `Host` header from the page is never sent.

**Also tried at `saveGateway`**, since the address is half of every URL. Each of these was refused as `invalidUrl`:

- `http://localhost.example.com`, `http://127.0.0.1.example.com`, `http://localhost.`, `http://127.1`, `http://[::1]:4000` and `http://0.0.0.0:4000`;
- `http://localhost\@…`, `http://localhost\…` and `https://…\@…`;
- `https:/…`, `https:…` and `https:///…`;
- a host with a Cyrillic letter, and anything with a query, a space or a user.

`HTTPS://…` and `http://LOCALHOST:4000` are kept, as the same addresses.

**What held.** No path tried changed the scheme, host or port a request went to, and every request line began with the Gateway's own path. The new Rust tests pin four of those paths, and the refused addresses.

### 3. What `gatewayRequest` can be made to do as an HTTPS client

**What I read and ran.**

| Of the request | What it can be |
| --- | --- |
| Where | The kept address, with any path from `/` under it and any query (probe 2) |
| Method | `GET` or `POST`, exactly. Anything else, `get` included, is refused before anything is sent, as `invalidPath` (`gateway.rs:362`) |
| Headers | Any name that's an HTTP token, with any value with no line break, except the eight HTTP sets itself: `host`, `content-length`, `connection`, `transfer-encoding`, `upgrade`, `te`, `keep-alive` and `proxy-connection`. Those are dropped. The kept headers win over the page's. `ureq` adds `user-agent: Lanewise/<version>`, `accept: */*` and `accept-encoding: gzip` |
| Body | Any text, with `POST`. `ureq` sets its length |
| TLS | The OS's certificates, through `rustls-platform-verifier` (`gateway.rs:319`). A local `https` server with a self-signed certificate was refused, with nothing read from it. `http://` only to `localhost` or `127.0.0.1` |
| Time | 180 seconds for the whole request (`gateway.rs:30`) |

| Of the answer | What the page is handed |
| --- | --- |
| Status | Any, `3xx` included. A redirect is never followed |
| Headers | Every one the Gateway answered with whose value is visible ASCII, `set-cookie` and `location` included |
| Body | Up to 16 MiB of it, decompressed if it came gzipped, as UTF-8 text (`gateway.rs:33`, `:380`). An answer that isn't UTF-8 fails as `unreachable`, "The gateway's answer couldn't be read." |

**Answer.** `gatewayRequest` is a client for `GET` and `POST` to its Gateway's address, at any path under it, with any header but those HTTP sets itself and any text body, whose whole answer the page reads. It follows no redirect, trusts only the OS's certificates, and keeps to its address as probe 2 says. The new tests pin the methods, the dropped headers and a line break in a value.

**Two things seen that break no promise**, so they're notes, not Findings:

- A method other than `GET` or `POST` fails as `invalidPath`, not a kind of its own. The UI never sends one (`app/src/ai/gateway.ts:21`).
- A self-signed certificate failed as "The request to the gateway failed.", not as "The gateway's certificate wasn't trusted.", which `send` has for a TLS failure. `ureq` reported it as an I/O error carrying the certificate's, which `send` doesn't match. Hand check B checks the message on a Release.

## Hand checks (need the owner)

**A. A Gateway on this computer, on a Release**

Do this once on macOS and once on Windows, each in the disposable account of the rules of engagement, with the latest Release installed. E2 has a local server stand in for a Gateway, with made-up header values.

1. Install Python 3, which is free. Save this as `gateway.py`, and run `python3 gateway.py`:

   ```python
   import http.server

   class Gateway(http.server.BaseHTTPRequestHandler):
       def do_POST(self):
           print(self.requestline, dict(self.headers), flush=True)
           self.send_response(500)
           self.end_headers()

       do_GET = do_POST

   http.server.HTTPServer(("127.0.0.1", 4000), Gateway).serve_forever()
   ```

2. In Lanewise, open Settings. Under Anthropic, choose "Use a gateway for Anthropic…". Set the address to `http://127.0.0.1:4000/anthropic`, add the header `X-Gateway-Key` with the value `throwaway-w4`, and save.
3. Open E1's `conflict-merge` fixture and ask for a Suggestion. It fails, as the server answers `500`. Check that the server printed `POST /anthropic/v1/messages HTTP/1.1` with `X-Gateway-Key: throwaway-w4`.
4. Open Settings again. Check that the header's value field is empty and says "Kept: type to replace".
5. In Settings, choose Copy diagnostics, and paste it into a text editor. Check that `throwaway-w4` isn't in it. Search the Logs folder for `throwaway-w4` too: `~/Library/Logs/com.adrianeyre.lanewise` on macOS, `%LOCALAPPDATA%\com.adrianeyre.lanewise\logs` on Windows. It should be in neither.
6. Choose "Stop using the gateway". In Keychain Access on macOS, or Credential Manager on Windows, check that there's no entry for `com.adrianeyre.lanewise.gateway`.
7. Write the date, the Release and the platform in H4's row above.

**B. A Gateway whose certificate the OS doesn't trust, on a Release**

1. In the same account, make a self-signed certificate and serve it on this computer:
   - `openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem -out cert.pem -days 1 -subj /CN=127.0.0.1 -addext subjectAltName=IP:127.0.0.1`
   - `openssl s_server -accept 4443 -cert cert.pem -key key.pem -www`
2. Set Anthropic's Gateway address to `https://127.0.0.1:4443`, keep the header, and save.
3. Ask for a Suggestion. Check that it fails, and that `s_server` printed no request. Write down the message Lanewise shows. It's one of the two in probe 3's notes.
4. Choose "Stop using the gateway".
