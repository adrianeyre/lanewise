# S2 — the OS credential store entries

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #23, label `prd:pen-test`). S2 probes the entries Lanewise keeps in Keychain, Credential Manager and the Secret Service: which they are, who else can read them, whether forgetting one leaves a copy behind, and whether Lanewise ever keeps a Host's credentials itself.

- **Trust boundary.** On one side are Lanewise's entries in the OS credential store: Model Provider and Jev keys (ADR 0020, ADR 0036), Gateways' headers (ADR 0035) and Issue Tracker tokens (ADR 0038). On the other are other programs running as the same user, the OS's own tools, and anything that outlives a Forget.
- **Governed by.** `CONTEXT.md`: Model Provider, Gateway, Issue Tracker, Jev, Host, Host page, Finding. ADR 0016, ADR 0020, ADR 0038, with ADR 0035 (Gateways) and ADR 0042 (Host pages). `SECURITY.md` ("How Lanewise protects what it holds").
- **Deliverables.**
  - `every_credential_store_entry_is_under_a_service_of_lanewises_own_by_a_name_no_other_shares` in `commands/src/lib.rs`: the three files that use `keyring`, the seven places that open an entry and the service each names, and names with no dot and never empty.
  - `keeps_no_token_between_calls_and_asks_the_helper_for_each` in each of `commands/src/hosts/github.rs`, `gitlab.rs`, `bitbucket.rs` and `azure_devops.rs`, through `keeps_no_token` in `commands/src/hosts/stand_in.rs`: a second sign-in, after the credential helper has forgotten the credential, asks the helper again, gets nothing, and sends nothing to the Host.
  - `SECURITY.md`'s "How Lanewise protects what it holds" now names the three services, says what Forget and uninstalling do, and says a Host page's sign-in is kept as a browser keeps one (ADR 0042).

  Each test was checked to fail when its rule is broken: GitHub's integration keeping the first credential it was given, a dot allowed in a Model Provider's ID, and a Gateway's entry opened under another service.

## How it was probed

This was done headless on Linux, with `keyring` 4.2.0, `keyring-core` 1.0.0, `apple-native-keyring-store` 1.0.2, `windows-native-keyring-store` 1.1.0, `zbus-secret-service-keyring-store` 1.0.1, `secret-service` 5.2.0, `security-framework` 3.7.0 and Tauri 2.12.3, the versions in `Cargo.lock`. Everything was written under `/tmp`. No key was a real one, and nothing was sent to a Model Provider, Gateway, Issue Tracker or Host.

1. **Read** every use of `keyring` in the tree, the three stores `keyring` 4.2.0 picks for macOS, Windows and Linux, the four Host Integrations and `core/src/credential.rs`, the Settings sections that save and forget, everything the UI keeps in local storage, and where Tauri keeps a webview's data.
2. **Ran the command API's `call`** from a program under `/tmp`, built against `lanewise-commands`, with no session bus and then with a session bus but no Secret Service (`dbus-run-session`). It saved, read and forgot a Model Provider key, a Gateway and an Issue Tracker account, each carrying a canary secret, with `HOME` set to an empty folder under `/tmp`.
3. **Pinned what held** in the tests above.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Which entries Lanewise makes, under which service names, and who else can read them on each OS

**What I read.**

- Only three files use `keyring`, and between them they open an entry in seven places, each under a service constant of its own (now pinned by the first test):

  | Service | Name (the entry's user) | What's kept | Code |
  | --- | --- | --- | --- |
  | `com.adrianeyre.lanewise.model-provider` | The Model Provider's ID: `anthropic`, `gemini`, `openai`, `xai`, `meta`, `local`, or Jev's, `typesafe-jev` | The API key, trimmed | `commands/src/model_provider.rs:19`, `:164-192` |
  | `com.adrianeyre.lanewise.gateway` | The Model Provider's ID | The Gateway as JSON: its address and its headers, values included | `commands/src/gateway.rs:24`, `:150-172` |
  | `com.adrianeyre.lanewise.issue-tracker` | `jira` or `trello` | The account as JSON: Jira's site, email, token and name, or Trello's key, token and name | `commands/src/issues/mod.rs:32`, `:48-53`, `:195-217` |

- E2's table (`docs/pen-test/E2.md`) lists the same entries, for checking a disposable machine's store.
- A Model Provider's ID is 1 to 64 lowercase letters, digits and dashes (`commands/src/model_provider.rs:27-43`), so a name is never empty and never has a dot.
- `keyring` 4.2.0, with its default `v1` feature, picks the store once per run (`src/v1.rs:109-118`):
  - **macOS:** a generic password in the user's login keychain, its service the service above and its account the name (`apple-native-keyring-store` 1.0.2, `src/keychain.rs:71-99`). An empty service or account is refused, since Keychain would read it as any (`:138`).
  - **Windows:** a generic credential whose target is `{name}.{service}`, such as `anthropic.com.adrianeyre.lanewise.model-provider` (`windows-native-keyring-store` 1.1.0, `src/cred.rs:35-58`). Since no name has a dot, no two of Lanewise's entries share a target.
  - **Linux:** a Secret Service item in the default collection, found by its `service` and `username` attributes and labelled `keyring:{name}@{service}` (`zbus-secret-service-keyring-store` 1.0.1, `src/cred.rs:46`, `:83-123`). The secret crosses D-Bus inside an encrypted session (`src/service.rs:26`).
- Nothing else in the tree, the UI included, writes to the credential store. Local storage holds no secret: every key it has is listed in `app/src/legal/stored.ts`, and `app/src/settings/ModelProviderSettings.test.tsx:102` checks a saved key isn't there.

**What the runs showed.** With no Secret Service, every command failed as `storeUnavailable` (or, for an Issue Tracker, `store`) and said no secret, and nothing was written under `HOME`: there's no fallback to a file.

**Who else can read them.**

- **The user**, in Keychain Access, Credential Manager or Seahorse, as with any app's entries.
- **Windows:** any program running as the same user, with no prompt. Credential Manager has no list of programs for a generic credential, and protects it with the user's own sign-in. That is Credential Manager's design (PRD §3.1), and the same for every app's entries, Git Credential Manager's among them.
- **Linux:** any program on the user's session bus, while the collection is unlocked, by the Secret Service's own design. Linux isn't a platform a Release is built for.
- **macOS:** the item's access list says which programs read it without macOS asking the user. It is checked on a Release in hand check B.

**Answer.** Three services of Lanewise's own, each entry named by a Model Provider's ID or an Issue Tracker. On Windows and Linux, a program running as the user can read them, as it can every app's; macOS's answer is hand check B. S1 left this question here: a program that could inspect the webview from outside could read the credential store directly on Windows and Linux, so that path gives it nothing more.

### 2. Whether forgetting a key removes every copy

**What I read.**

- **What Forget deletes.** `forgetModelProviderKey` (Jev's key too), `forgetGateway` and `forgetIssueTrackerAccount` each delete the one entry for that service and name, and succeed when there's none (`commands/src/model_provider.rs:185-190`, `commands/src/gateway.rs:167-172`, `commands/src/issues/mod.rs:211-216`):
  - macOS deletes every generic password in the login keychain with that service and account (`src/keychain.rs:87-99`);
  - Windows deletes the one credential with that target;
  - Linux deletes the one matching item. If another program has made a second item with the same attributes, it deletes neither and says so (`src/cred.rs:83-99`, `:155-158`), so Settings shows the failure rather than claiming the key is gone.
- **Where Forget is.** Settings shows a key and its Forget for the Model Provider chosen (`app/src/settings/ModelProviderSettings.tsx:447`, `:641-648`). A Gateway has a Forget of its own (`app/src/settings/GatewaySettings.tsx:99`), as do Jev's key (`app/src/settings/JevSettingsSection.tsx:158`) and each Issue Tracker account (`app/src/issues/IssueTrackerSettings.tsx:141`). Forgetting a Model Provider's key leaves its Gateway, which is kept on its own. Turning AI off forgets nothing.
- **Other copies of Lanewise's own.** There are none. Local storage holds no secret (probe 1). The Settings fields are emptied once saved, and the UI keeps no key once its request is answered (S1, probe 2). The Logs never hold one (ADR 0028, S3). With no credential store there's no fallback file (the runs above).
- **Copies Forget doesn't reach.** Uninstalling Lanewise leaves its entries, as ADR 0020 and ADR 0038 say, and `SECURITY.md` now says so too. A copy the OS makes of its own credential store, such as a backup, is the OS's.

**Answer: yes**, for every copy Lanewise makes. Forget deletes the one entry it was kept in, on each OS, and Lanewise keeps the secret nowhere else. Where the store can't delete it, Settings says so. Hand check A checks this on a Release.

### 3. Whether Host credentials are ever kept by Lanewise itself

**What I read.**

- **The credentials Git signs in with.** Every Host Integration asks `git credential fill` for the token when a command needs it, uses it for that command's requests, and drops it (`core/src/credential.rs:150-197`, `commands/src/hosts/github.rs:75-79`, `:131-155`, and the same in `gitlab.rs`, `bitbucket.rs` and `azure_devops.rs`). A Host Integration holds its Hosts and a handle to the helpers, never a credential, and there's no `static` holding one in `commands` or `core`. `approve` tells the user's helpers the Host took it, and the helper keeps it where it keeps credentials; for Git Credential Manager, the OS credential store under Git Credential Manager's own names, not Lanewise's.
- **Git's own runs.** Lanewise passes `git` no credential: no `http.extraHeader`, no askpass program, and `GIT_TERMINAL_PROMPT=0` (`core/src/git.rs:181`). A remote URL with a user and token in it, typed by the user, is kept by `git` in the repository's `.git/config`, as on the command line. Lanewise shows it as `***` (`commands/src/branches.rs:199`), and the Recent Repositories and Tabs it keeps are folders alone (`app/src/tabs/tabs.ts:197-203`).
- **Host pages.** A Host page's cookies are the Desktop App's webview's own, "so signing in to GitHub there stays signed in, as in a browser" (ADR 0042). They are kept in the Desktop App's web data: on Windows the WebView2 folder Tauri makes in `%LOCALAPPDATA%\com.adrianeyre.lanewise` (Tauri 2.12.3, `src/manager/webview.rs:559-569`), on macOS WebKit's store for the app. They stay until the user signs out on the page or removes the app's data. `SECURITY.md` didn't say so; it does now. The Privacy Policy's wording for it is #60's (`TODO(#60)` in `app/src/legal/PrivacyPolicy.tsx:4`).

**What the tests showed.** After a sign-in, with the helper then forgetting its credential, a second sign-in through the same Host Integration asks the helper again, finds nothing and sends nothing to the Host, on all four Host Integrations.

**Answer.** Git's credentials: **never**, as E2 found. Lanewise asks the user's helpers for each command and keeps nothing, and the new tests pin that. A Host page's own web sign-in **is** kept, by ADR 0042's design, as a browser keeps one, which E2's "never kept by Lanewise" leaves out, and `SECURITY.md` now says so. Hand check C checks it on a Release.

## Hand checks (need the owner)

Do each on macOS and on Windows, in the disposable account of the rules of engagement, with only E2's throwaway keys and accounts in its credential store.

**A. The entries, and Forget**

1. Install the latest Release and open it.
2. In Settings → AI, choose Anthropic, accept its First-use disclosure, and save E2's throwaway Anthropic key. Add a Gateway for Anthropic with one header, `x-throwaway`, whose value is a made-up string. In Settings → Jev decisions, save E2's throwaway Jev key. In Settings → Issue Trackers, save E2's throwaway Jira account.
3. On macOS, open Keychain Access, choose the login keychain and search for `com.adrianeyre.lanewise`. On Windows, open Control Panel → Credential Manager → Windows Credentials, and look under Generic Credentials.
4. Check that there are exactly four entries: `anthropic` and `typesafe-jev` under `com.adrianeyre.lanewise.model-provider`, `anthropic` under `com.adrianeyre.lanewise.gateway`, and `jira` under `com.adrianeyre.lanewise.issue-tracker`. On Windows they're named `anthropic.com.adrianeyre.lanewise.model-provider` and so on.
5. In Settings, Forget each of the four: the API key, the Gateway, Jev's key and the Jira account.
6. Search again, and check that none is left.
7. Write the date, the Release and the platform in the table above.

**B. Who else can read them on macOS**

1. Save E2's throwaway Anthropic key again, as in A.2.
2. In Keychain Access, open the `com.adrianeyre.lanewise.model-provider` item and choose Access Control. Note which applications it lists.
3. In Terminal, run `security find-generic-password -s com.adrianeyre.lanewise.model-provider -a anthropic -w`.
4. Check that macOS asks before the key is shown. Choose Deny.
5. Forget the key in Settings.
6. Write what step 2 listed, what step 4 did and the date in the table above.

**C. A Host page's sign-in**

1. With Settings → Host pages left to open them in Tabs, as it is at first, open a Pull Request or a repository on GitHub in a Tab, and sign in there with E2's throwaway GitHub account.
2. Quit Lanewise and open it again, and open a GitHub page in a Tab. Check that it's signed in, as `SECURITY.md` now says.
3. Sign out on the page. Quit, open Lanewise again and open a GitHub page in a Tab. Check that it's signed out.
4. Check that Git Credential Manager's own entry for `github.com`, if any, was neither made nor changed by steps 1 to 3.
5. Write the date and the platform in the table above.

**D. Uninstalling**

1. Save E2's throwaway Anthropic key, as in A.2.
2. Uninstall Lanewise: on Windows from Settings → Apps; on macOS by dragging Lanewise to the Bin.
3. Search the credential store as in A.3. Check that the `anthropic` entry under `com.adrianeyre.lanewise.model-provider` is still there, as `SECURITY.md` says.
4. Delete it in Keychain Access or Credential Manager.
5. Write the date and the platform in the table above.
