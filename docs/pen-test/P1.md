# P1 — Web Mode's design, before it is built

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #32, label `prd:pen-test`). Web Mode isn't built: `serve/` is a placeholder that says so and fails (`serve/src/main.rs:8`). So P1 is a design review, not a probe of a running server. It answers the pen-testing PRD's §9 questions in an ADR before the first line of Web Mode is written. Each answer stands on what the tree has now and on what a real browser did against a stand-in server.

- **Trust boundary.** On one side are the core and its command API, which will run as `lanewise serve` on `127.0.0.1` (ADR 0003, PRD `git-client.md` §7.12). On the other are four things that can reach it:
  - a browser on the same machine;
  - other sites that browser has open;
  - other users on the machine, who share its loopback;
  - and anything that can speak to the WebSocket the command API will cross.
- **Governed by.** `CONTEXT.md`: Web Mode, and the new Access token. ADR 0003. PRD `git-client.md` §7.12. Pen-testing PRD §9. With ADR 0020 (Model Providers' requests), ADR 0028 (the Logs), ADR 0035 (Gateways), ADR 0050 (the main webview's policy) and ADR 0051 (a Model Provider on this computer).
- **Deliverables.**
  - ADR 0055, `docs/architectural-decision-record/0055-web-mode-reached-only-from-its-own-page-with-a-fresh-access-token-and-never-handed-a-key.md`, which answers each of §9's questions. ADR 0003, ADR 0020, ADR 0050 and ADR 0051 point to it.
  - `serve/tests/design.rs`, which holds ADR 0055's table of the commands that cross the WebSocket to the command API's `NAMES`. A new command fails it until it has a row, and `modelProviderKey` is the one command that doesn't cross. Each test was checked to fail when its rule is broken: a command taken out of the table, and `modelProviderKey` moved to "Crosses".
  - **Access token** in `CONTEXT.md`. A line in `docs/development.md` §4. The `TODO(#50)` in `app/src/platform/unavailable.ts:21` reworded to the ADR's decision.

## How it was probed

1. **Read** ADR 0003, PRD `git-client.md` §7.12 (`:144-149`), pen-testing PRD §9, and every ADR Web Mode will lean on. Then read the command API (`commands/src/lib.rs`), the `Platform` the UI reaches its shell through (`app/src/platform/platform.ts`), the placeholders that stand in for Web Mode now (`serve/`, `app/src/platform/unavailable.ts`), and what the UI keeps in the browser (`app/src/settings/localSettings.ts`).
2. **Ran a stand-in** of the server's front door against a real browser engine, under `/tmp` and on loopback only:
   - **The browser.** WebKitGTK 2.54.0's MiniBrowser, under `xvfb-run`, with `HOME` under `/tmp`.
   - **Port B, standing in for `serve`.** A Python script that served a page and a WebSocket. It logged every request line, `Host`, `Origin`, `Cookie` and `Referer`.
     - Its page took a token from the URL's fragment, kept it in `sessionStorage` and took it out of the address bar. Then it sent the token as its WebSocket's first frame.
     - The WebSocket applied ADR 0055's first two checks: `Host` names `127.0.0.1` or `localhost`, and `Origin` is exactly `http://` and that `Host`. Then it checked the first frame against the token.
     - Every page it served set a cookie marked `HttpOnly; SameSite=Strict`, to see where a browser would send one.
   - **Port A, standing in for another site.** It served a page that tried B's WebSocket under both names, and made two `fetch`es to B. It reported what it got back.
   - **A rebinding name.** The run ended at `http://p1-rebind.localhost:<B>/`: WebKitGTK sends any `*.localhost` name to loopback. That stood in for an attacker's name made to resolve to `127.0.0.1`.

   Nothing in it is committed. It used no Host, Model Provider or credential, and sent nothing off the machine.

## Probes from the brief

### 1. How the Access token is made, how long it is, and where it can leak

**What I read.** ADR 0003 says "a random per-start access token in the URL", and PRD §7.12 says it is "generated at start and printed as part of the URL (as Jupyter does)". Neither says how it's made, how long it is, which part of the URL it's in, how the WebSocket is given it, or what keeps it out of the Logs. The Logs log a command by its name and its failure's kind, never a request (`commands/src/lib.rs:348`, `commands/src/logs.rs:179`). Nothing yet logs a URL, because nothing serves one.

**What the run showed.**

| Where the token was | What reached the server or another site |
| --- | --- |
| In the URL's fragment, `/#token=…` | The request line was `GET /`. No request or `Referer`, to B or to A, held the token |
| In `sessionStorage`, after `history.replaceState` | The address bar, `location.href` and the next same-origin `Referer` were all `http://127.0.0.1:<B>/` |
| Sent as the WebSocket's first frame | B read it, and it matched |

A token in the query, as Jupyter's is, would have been in B's request line, and in the full-URL `Referer` the page's own requests sent.

**Answer: decided in ADR 0055 §1.**

- **How it's made.** 32 bytes from the OS's random source, written as 43 base64url characters: 256 bits. It's fresh at each start, written nowhere and compared in constant time.
- **Where it travels.** It's printed once, in the URL's fragment. The page reads it, keeps it in `sessionStorage` and clears it from the address bar. From then on it's sent only as the WebSocket's first frame.
- **Where it could leak.** The ADR has a row for each place:
  - a `Referer`: never, since the token is in no URL a request is made for;
  - the browser's history: hand check 1;
  - the Logs: never a URL, a header or a frame;
  - a shell's history: no flag or environment variable takes a token;
  - the terminal: it's printed there once, and the docs will say who can read that;
  - the page's own storage: never local storage or a cookie;
  - browser extensions: the docs will advise a profile without them.

### 2. How the WebSocket checks a connection's `Origin`, and how DNS rebinding is refused

**What I read.** Nothing in the tree yet: ADR 0003 and PRD §7.12 name `127.0.0.1` and the token, and neither says `Origin`, `Host` or rebinding.

**What the run showed.**

| Connection | `Host` | `Origin` | `Origin` is `http://` + `Host` | `Host` names loopback | Outcome |
| --- | --- | --- | --- | --- | --- |
| B's own page | `127.0.0.1:<B>` | `http://127.0.0.1:<B>` | yes | yes | Upgraded; first frame was the token |
| A's page, to `ws://127.0.0.1:<B>` | `127.0.0.1:<B>` | `http://127.0.0.1:<A>` | **no** | yes | Refused with `403` |
| A's page, to `ws://localhost:<B>` | `localhost:<B>` | `http://127.0.0.1:<A>` | **no** | yes | Refused with `403` |
| The rebinding name's own page | `p1-rebind.localhost:<B>` | `http://p1-rebind.localhost:<B>` | yes | **no** | Refused with `403` |

Two more things showed:

- **The cookie.** B's `SameSite=Strict`, `HttpOnly` cookie was sent with A's handshake to `127.0.0.1:<B>`, and with A's `no-cors` `fetch`. Ports don't make a different site, so a cookie would have been an ambient credential for every page on every loopback port.
- **The rebinding name.** Its `Origin` matched its `Host`, so the `Origin` check alone would have let it in. Only the `Host` check refused it.

**Answer: decided in ADR 0055 §2.** `serve` listens on `127.0.0.1` only. Each request and handshake passes three checks, in order, before anything runs:

1. `Host` is `127.0.0.1` or `localhost`, at any port, so that an SSH tunnel works. This refuses DNS rebinding.
2. `Origin` is present and exactly `http://` and that `Host`. This refuses other sites and other loopback ports.
3. The first frame is the Access token. This refuses another user's process, which can send any header.

There's no cookie and no HTTP authentication.

### 3. Whether a page on another site can open the WebSocket, and what it gets

**What the run showed.** A's page couldn't open B's WebSocket under either name:

- each handshake was refused with `403` at the `Origin` check;
- the page saw `close` with code `1006`, and nothing else;
- its credentialed `fetch` to B was blocked by CORS, since B sends no CORS header;
- its `no-cors` `fetch` came back `opaque`, unreadable.

What it could tell was that something answered on B's port.

**Answer: no, and it gets nothing but that a port answers** (ADR 0055 §3).

- **The checks behind it.** Even with the right `Origin`, it would need the Access token, which no browser sends on its own. Nothing ambient counts.
- **What it can't do besides.** `serve` will send no CORS header, and frames nothing (`frame-ancestors 'none'`, `X-Frame-Options: DENY`).
- **What it can load.** The UI's own scripts, which hold nothing the public repository doesn't.

### 4. Which commands cross the WebSocket, and whether `modelProviderKey` is one

**What I read.**

- **The command API.** It has 87 commands (`commands/src/lib.rs:255`). Every one is transport-agnostic, and none is tied to a window.
- **The Desktop App's other commands.** Its Update and Host page commands are Tauri commands of its own, not the command API's (`desktop/src/lib.rs`). `Platform.updater` and `Platform.hostPages` are `null` where a shell has none (`app/src/platform/platform.ts`).
- **The one command that hands out a secret.** S1 found it is `modelProviderKey`. The UI asks for it in two places: for each Model Provider request (`app/src/ai/requests.ts:75`) and for Jev's (`app/src/ai/jev.ts:88`). It puts the key in the request itself and sends it through `Platform.fetch` (`app/src/platform/platform.ts:78`).
- **Gateways.** They already work the other way. The core makes the request and adds the headers, which the page never sees (`app/src/ai/gateway.ts:27`, ADR 0035).
- **What the tree said before this review.** PRD §7.12 says "Rust makes all Model Provider HTTP requests in both modes". ADR 0020 and the old `TODO(#50)` said only that `serve` would "forward" them, at an endpoint of its own, and nothing said whether the key would still cross.

**Answer: every command crosses but `modelProviderKey`** (ADR 0055 §4).

- **The table.** ADR 0055 places all 87 commands. `serve/tests/design.rs` holds that table to `NAMES`.
- **Model Provider and Jev requests.** In Web Mode they're a command over the same WebSocket, as `gatewayRequest` is. The core makes the request:
  - only to the same list the Desktop App's allow-list has, shared by both shells;
  - following no redirect;
  - and with the key read from the credential store and put in that Model Provider's own header.

  So no key reaches a tab of the user's everyday browser, where its extensions could read the page.
- **No second way in.** A forwarding endpoint beside the WebSocket was left out: it would need the same three checks again.
- **What doesn't change.** The Desktop App keeps `modelProviderKey` as ADR 0020 has it.

### 5. Two browsers, or two users on one machine

**What I read.**

- **The core is one process.** It shares its clone, fetch, pull and push runs, each numbered by a counter, and their long polls (`commands/src/running.rs:72`).
- **Undo is the page's own.** It takes an action back only while the repository is as the action left it (`app/src/repository/undo.ts`, ADR 0045).
- **Settings are the origin's.** They're kept in that origin's local storage, Recent Repositories and the Base folder among them (`app/src/settings/localSettings.ts:51`, `:66`). No key is ever kept there (`app/src/settings/ModelProviderSettings.test.tsx:102`).

**Answer: decided in ADR 0055 §5.**

- **Two browsers or tabs of one user.** They are equal connections with the same Access token. Each sees the other's runs, `git`'s own locks keep two writes apart, and Undo can't undo over the other's later change. Settings are each browser's own.
- **Two users.** Loopback is shared, so only the Access token stands between them. It's never on a command line, which `ps` shows every user, or in a file or the Logs.
- **The port.** It's fixed by default, so Settings last, and `--port` changes it. If it's taken, `serve` stops and says so rather than moving. Another user who takes the port first gets only a token that's already worthless, and the URL `serve` prints is the only one to trust.
- **Local storage.** What the UI keeps there can be read by whatever later serves the same origin, so it holds no secret, and never the token.
