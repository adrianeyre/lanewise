# R1 — Updates: signatures and downgrades

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #27, label `prd:pen-test`). R1 tried to make the installed Desktop App take an Update it shouldn't: an older Release the Update key really signed, or one offered by a page that reached the updater plugin's own commands. It also asked who can change what a Release offers, and what happens if the Update key leaks. It starts from H11, and it answers what PRD §8 needs before the Update key's public half is set.

- **Trust boundary.** On one side, a Release's assets and its `latest.json`, which whoever can edit the Release can change. On the other, the installed Desktop App, which trusts only the Update key's public half built into it.
- **Governed by.** `CONTEXT.md`: Update, Update key, Release, Finding. ADR 0030 (Updates signed by the Update key, installed only when the user agrees), ADR 0047 (the latest version checked as Lanewise starts), and the new ADR 0052. `SECURITY.md`: "a way to have the Desktop App install an Update not signed by the Update key", "a way into the release workflow, its secrets or the packages on a Release", and "An Update is installed only if it is signed by the Update key".
- **Deliverables.**
  - Tests pinning what held, each checked to fail when the behaviour it holds is broken:
    - `desktop/tests/updater.rs`: `an_older_release_genuinely_signed_is_no_update`, `an_older_release_announced_as_newer_is_turned_away` and `a_package_signed_with_no_version_is_turned_away`, against the real plugin with the committed config. `the_page_cant_call_the_updaters_own_commands` now names all four of the plugin's commands, not two;
    - `desktop/src/lib.rs`: `the_apps_own_updater_offers_no_older_release`, against the updater as the app itself builds it. `a_remote_page_such_as_a_host_page_reaches_no_command` now names every `update_*` command;
    - `desktop/src/update.rs`: `the_committed_config_is_the_updaters` also holds the config to no `allowDowngrades`, plain `http` or unchecked certificates;
    - `app/scripts/release/updater.test.ts`: a package signed with no version bound to it is refused before any `latest.json` is written.
  - A fixture for those tests, `app/scripts/release/fixtures/unversioned/`: a stand-in package and its signature from a throwaway key with no version in its trusted comment, and that key's public half. The private half was deleted after signing, as the existing fixtures' were.
  - ADR 0052, `docs/architectural-decision-record/0052-releases-unchanged-once-published-and-the-update-key-held-backed-up-and-rotated.md`: who can change a Release's files, release immutability, and who holds the Update key, where its backup is and how it's rotated. ADR 0030 points to it. `docs/releases.md`'s "The Update key" has the rotation and the immutability setting. `SECURITY.md` says Updates are offered only once the key is made, and that an older Release is never installed as an Update.

## How it was probed

This was done headless on Linux (Debian 13), with Node 26 and the tree at `57cf378`. The versions were `tauri-plugin-updater` 2.13.3, `tauri-cli` 2.12.2 and `semver` 1.0.28, as `Cargo.lock` and `pnpm-lock.yaml` have them. Nothing was sent to GitHub but reads of its public documentation. Scratch files were written under `/tmp` and deleted.

1. **Read the plugin's own source**, the crate as Cargo fetched it: how it decides an Update is newer, what it checks a package's signature against, and what `requireSignedVersion` adds.
2. **Read** `desktop/src/update.rs`, `desktop/src/lib.rs`, `desktop/tauri.conf.json`, `desktop/capabilities/default.json`, `app/scripts/release/updater.ts`, `.github/workflows/release.yml`, `.github/workflows/ci.yml`, `.github/workflows/codeql.yml` and `.releaserc.json`, and GitHub's pages on Release assets and immutable releases.
3. **Made a throwaway Update key** in `/tmp` with `tauri signer generate`. It signed one stand-in package with `tauri signer sign` and no `--app-version`, as a package signed by hand, or by an older Tauri, is signed. Then the key was deleted.
4. **Served `latest.json` from this machine** to the real plugin and to the updater the app builds, as copies at several versions, announcing a Release at 1.2.3 truthfully, as newer than it is, and with that unversioned signature.
5. **Broke each behaviour the new tests hold**, one at a time, in a copy of the tree that wasn't committed. `allowDowngrades: true` with `requireSignedVersion: false` failed `an_older_release_genuinely_signed_is_no_update` and `a_package_signed_with_no_version_is_turned_away`. A `default_version_comparator` of "any other version" in `app()` failed `the_apps_own_updater_offers_no_older_release`.

## Probes from the brief

### 1. Whether an older, genuinely signed Update is refused

**What I read.** `update_check` and `check` (`desktop/src/update.rs:252`, `:261`) use `app.updater()` as the plugin builds it. `app()` registers the plugin with `tauri_plugin_updater::Builder::new().build()` (`desktop/src/lib.rs:29`), with no version comparator of its own. The plugin then uses "must be different" only if the config says `allowDowngrades`, which Lanewise's doesn't (the plugin's `src/lib.rs:99-104`). Otherwise an Update is offered only when `release.version > self.current_version` (`src/updater.rs:669-672`). Its package is checked when it downloads (`src/updater.rs:842`): the minisign signature over the file against the config's `pubkey`, then, with `requireSignedVersion`, the version in the signed trusted comment against the version `latest.json` announced (`src/updater.rs:1829-1864`). `desktop/tauri.conf.json:53` sets `requireSignedVersion`. `tauri build` writes the version into the trusted comment (`tauri signer sign --help`), and `updater.ts`'s `release` refuses to publish any package not signed for the tag's version, one with no version included (`app/scripts/release/updater.ts:242`).

**What the runs showed.** Each way an older Release's genuine package can be offered to a newer copy was refused:

| How it's offered, to a copy at 1.2.4 | What the updater did | Held by |
| --- | --- | --- |
| As itself, 1.2.3, with its own package and signature (also to copies at 1.3.0 and 2.0.0) | Found no Update | `an_older_release_genuinely_signed_is_no_update`, `the_apps_own_updater_offers_no_older_release` |
| As `1.2.5`, `v1.2.5`, `1.2.4+1`, `1.3.0-rc.1` or `99.0.0`, with 1.2.3's package and signature | Found it, then refused the download: signed for version 1.2.3 | `an_older_release_announced_as_newer_is_turned_away` |
| As newer, with a signature that names no version | Refused the download: `requireSignedVersion` needs one | `a_package_signed_with_no_version_is_turned_away` |
| As the version running | Found no Update | `the_version_running_is_no_update` |

`1.2.4+1` counts as newer than `1.2.4` to the plugin's `semver`, which breaks ties on build metadata, so it reaches the signature check, which refuses it. Two other things don't depend on the plugin. `release.yml`'s `publish` job wouldn't write a `latest.json` for a package with no version, and the committed config is held to have no `allowDowngrades` (`desktop/src/update.rs:372`).

A user can still download an older Release's installer from its page and run it. That's the user's own choice, not an Update, and isn't what this probe covers.

**Answer: disproved, and pinned.** An older Release, even one the Update key really signed, is never installed as an Update, however `latest.json` announces it. On Releases, with the real key, that is hand check A.

### 2. Whether the page can reach the updater plugin's own commands

**What I read.** The main webview's one capability (`desktop/capabilities/default.json:6-38`) lists no `updater:` permission, and no other capability file exists. The plugin has four commands, `check`, `download`, `install` and `download_and_install` (its `build.rs`). The page does reach the app's own four (`desktop/src/lib.rs:32-42`), as ADR 0030 decided. `update_status`, `update_check`, `update_install` and `update_progress` (`desktop/src/update.rs:243`, `:252`, `:282`, `:303`) take nothing from the page. There's no endpoint, key or URL among their arguments. `update_install` installs only what the last check found, at the committed endpoint, under the committed key. `withGlobalTauri` isn't set, so the plugin's JavaScript isn't put in the page either.

**What the runs showed.** Through Tauri's mock runtime, with the app's own capability, the page's call of each of the plugin's four commands was refused as "not allowed". A remote page, such as a Host page, reached none of the four `update_*` commands.

**Answer: disproved, and pinned.** The page can't point the updater at another endpoint or key, or call any of the plugin's own commands.

### 3. Who can edit a Release's assets, and so `latest.json`

**What I read.** GitHub: "Users with push access to the repository can edit a release asset" (the REST API's Release assets page). `release.yml` gives `contents: write` to two jobs: `release` (`.github/workflows/release.yml:52-55`), which runs only for `adrianeyre/lanewise`'s `main`, and `publish` (`:308-309`), which uploads every file to the draft and then publishes it (`:346-349`). Every other job, and `ci.yml` and `codeql.yml`, can only read contents. `.releaserc.json` makes semantic-release's Release a draft. Any workflow on a branch of this repository can ask for `contents: write` itself, and only someone with push access can push one. A fork's pull request, and Dependabot's, get a token that can only read.

**Answer.** The owner, any collaborator with Write, Maintain or Admin, those two jobs, any workflow someone with push access writes, and any App or token with write access to contents. Who has that on `adrianeyre/lanewise` today is in its settings, which this sandbox can't read: hand check B. ADR 0052 writes the list down.

What they can do to an installed copy is limited by probe 1. They can offer only packages the Update key signed, for their own versions, newer than the copy running. They can hold an Update back, by taking `latest.json` away or putting an older one in its place, and ADR 0047's check still says a newer version is out, since it reads `main`'s `package.json`. They can change what a first install downloads, which the updater doesn't check. So ADR 0052 decides to turn on GitHub's release immutability. Once a Release is published, nobody can change its files, the owner and the workflows included. `release.yml` already puts every file on the draft before it publishes, which is the workflow GitHub recommends for it. It's a setting the owner turns on: hand check B.

### 4. How the Update key would be rotated if it leaked

**What I read.** The plugin trusts one public key, the config's `pubkey` (its `src/config.rs`). `publish` checks every package against the public key committed in the tag it builds (`app/scripts/release/updater.ts:242`, `.github/workflows/release.yml:339`). So a Release can only carry the public half of the key it was signed with.

**Answer.** Rotating today is a clean break, written as steps in ADR 0052's "Rotating it" and `docs/releases.md`:

1. Make a new key.
2. Replace the two secrets before anything else merges.
3. Commit the new public half in a `fix:` Release.
4. Copies of earlier Releases refuse that Release's package and say why, and their users install it by hand once. ADR 0047's dialog tells them it's out.
5. Publish an advisory if the key leaked.
6. Back up the new key and destroy the old one.

Until each user reinstalls, their copy still trusts the old key. Whoever holds that key would also need those copies to read their own `latest.json`, which takes push access to `adrianeyre/lanewise` or a break of TLS to `github.com`.

A bridging Release, signed by the old key and carrying the new public half, would move copies over at their next Update instead. It needs `publish` to check against the previous Release's public key. It isn't built: it's one of the issues listed under PRD §8 below.

## Hand checks (need the owner)

Do these in the disposable account of the rules of engagement, on Windows 10 22H2 or 11 and on a Mac. A and C need the Update key made as `docs/releases.md` says. A also needs two signed Releases, N and N+1, as ADR 0030's hand checks 2 and 3 make.

**A. An older, genuinely signed Release is refused, on Releases**

1. Install Release N+1 from its page, and open it once.
2. On GitHub, on Release N's page, edit it and mark it as the latest Release. Release immutability allows this. Check that `https://github.com/adrianeyre/lanewise/releases/latest/download/latest.json` now announces N.
3. Quit and start the installed N+1. No Update notice appears. In Settings → Updates, press Check for updates: it says "Lanewise N+1 is the latest Release.", and offers nothing to install.
4. Mark Release N+1 as the latest again straight away, and check that `latest.json` announces N+1.
5. Write the date, the Releases and the platforms in H11's row above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).

**B. Who can edit a Release's assets, and immutability**

1. Do ADR 0052's hand checks 1 to 3: turn on release immutability, note everyone and every App with write access to contents, and check on the next Release that an upload to it is refused.
2. Write the date in H11's row above.

**C. The Update key's backup**

1. Do ADR 0052's hand check 4: make the key and back it up, write in your own records where the backup is, and check that the backup signs.
2. Write the date in §8's row 2 above. Write it there, not where the backup is.
