# E4 — the Findings workflow: labels and an issue form

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #13, label `prd:pen-test`). This is an **enablement** scope issue. It builds how a Finding is filed and triaged (PRD §7), and probes no trust boundary of its own.

- **Trust boundary.** None. E4 decides how a Finding is filed, so that what the round finds reaches the owner with what it needs, and a Finding with a way to do harm doesn't reach the public first.
- **Governed by.** `CONTEXT.md`: Finding, Pen-test round, Release. PRD §4 (Disclosure) and §7 (Findings workflow), and the rules of engagement's §6.
- **Deliverables.**
  - The Finding issue form, `.github/ISSUE_TEMPLATE/finding.yml`.
  - The owner's triage guide, `docs/processes/triaging-a-finding.md`, linked from PRD §7 with the form.
  - Three tests in `app/scripts/community.test.ts`, which now reads every issue form with the `yaml` package, as GitHub reads it.
  - A line in `CONTRIBUTING.md` beside the other issue forms.

## Probes from the brief

### 1. Labels `severity:critical`, `severity:high`, `severity:medium`, `severity:low`

**What I did.** I read what PRD §7 asks a Finding to carry (`docs/product-requirements-document/pen-testing.md:172`). This sandbox has no GitHub token, and the rules keep a run from sending anything to a Host (rules §2), so I didn't read the repository's labels from GitHub. The brief says the owner made the four labels on `adrianeyre/lanewise` on 12 October 2026.

**Answer: made by the owner, 12 October 2026, and checked by hand (A below).** The triage guide lists them with `prd:pen-test` and `wontfix`, and says when each goes on (`docs/processes/triaging-a-finding.md`, "The labels").

An issue form can only add fixed labels, not one chosen in the form, so the form adds `prd:pen-test` and the owner adds the severity label while triaging. I didn't add a workflow to copy the chosen severity into a label. It would need a token that can write to issues, acting on text anyone can write, which is the kind of surface R2 and R5 probe. The guide says why. A test now holds that each form names labels GitHub can parse, including one with a `:` such as `prd:pen-test` (`app/scripts/community.test.ts`, "each issue form is valid YAML of GitHub's shape").

### 2. An issue form for a Finding: its scope issue, the promise it breaks, the Release it was shown on, the steps, and the test that would have caught it

**What I did.** I read the other forms (`.github/ISSUE_TEMPLATE/`) and PRD §7's list. I wrote `finding.yml`, titled `[finding] <ID> — <what it does>` and labelled `prd:pen-test`. It has six required fields:

- **Scope issue**, such as `#18`;
- **Severity**, a dropdown (probe 4);
- **The promise it breaks**, quoted, with where it's made: the PRD, an ADR or `SECURITY.md`;
- **The Release it was shown on**, with the operating system, since a Finding is a hypothesis until then (`CONTEXT.md`);
- **Steps to show it**, with throwaway accounts and synthetic data only;
- **The test that would have caught it**.

The `yaml` package parses the form in the test, as GitHub would.

**Answer: built.** The test "the Finding form sends a critical or high Finding to private vulnerability reporting before anything else" holds each of those fields to `required: true`. The existing tests hold every path the form names to the tree, and its slug to `adrianeyre/lanewise`.

**What reading the forms as YAML turned up.** Parsing every form showed that `feature-request.yml` wasn't valid YAML: an unquoted description held `: `. GitHub doesn't offer a form it can't parse, so the feature form was probably missing from the issue chooser. The old tests matched the forms as text, so they couldn't see it. I quoted the description, and the new test parses every form, so it would have caught this. This is a plain bug, not a Finding: nothing is given up. It's confirmed on GitHub by hand (B below).

### 3. The form says, before anything else, that a critical or high Finding goes through private vulnerability reporting instead

**What I did.** I read PRD §4 (`docs/product-requirements-document/pen-testing.md:58`–`:65`) and the rules of engagement's §6 (`docs/product-requirements-document/pen-testing-rules-of-engagement.md`). Both are stricter than "critical or high": **any** lead with a concrete way to do harm goes privately first, whatever its severity, until its fix is released.

**Answer: built, in three places, in this order.**

1. The form's description, which GitHub's issue chooser shows before the form is even opened: "A critical or high Finding goes through private vulnerability reporting instead."
2. The first thing in the form: "**Stop here if the Finding is critical or high.**", linking to private vulnerability reporting. Next comes the rules' wider rule for any Finding with a concrete way to do harm, in the rules' own words.
3. Before the first field, three required checkboxes: the Finding is medium or low, or its fix is in a Release; it holds no unfixed concrete way to do harm; and it holds no real credential.

The test holds all three: the description, the first body element and its link, and the checkboxes coming before the scope issue.

A public form can't stop someone ignoring it, and blank issues are still allowed for everyone else (`.github/ISSUE_TEMPLATE/config.yml`). So the triage guide's first step is to check the Finding is safe in public. If it isn't, the owner moves it into a draft advisory and deletes the issue (`docs/processes/triaging-a-finding.md`, "Triaging a public Finding").

### 4. The targets of §7 written where the triage of a Finding will see them

**What I did.** GitHub doesn't copy a form's Markdown blocks into the issue it files, but it does copy each field's answer. So the targets go where the triage reads them:

- **In the issue itself.** Each severity option in the form's dropdown carries its target, such as `high: target 30 days`, so the filed issue says it under "Severity".
- **In the form.** The table of PRD §7 (`docs/product-requirements-document/pen-testing.md:176`–`:183`) is in the form's second Markdown block, where the filer chooses from it.
- **In the owner's triage guide.** The table is in "Targets", with the steps that use it: check the severity, add its label, write the due date in a comment, and link the Finding from its scope issue. Writing the reason comes before `wontfix`.

**Answer: built.** The test "the Finding form and its triage guide carry the pen-testing PRD's targets for each severity" reads the table from PRD §7. It holds each row word for word in the form and the guide, and the dropdown's options to the targets in order, so a change to the PRD fails the test until both follow. I checked that it fails when one target, the order or the warning is changed.

2. Triage it as `docs/processes/triaging-a-finding.md` says, and link it from #13 as the brief asks.
