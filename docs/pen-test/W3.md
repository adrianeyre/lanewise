# W3 — the HTTP allow-list and every request outside it

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #16, label `prd:pen-test`). W3 probes where the main webview can send a request: through Tauri's HTTP plugin, to the URLs its capability allows, and through the webview's own `<img>`, `fetch`, `<link>` and `navigator.sendBeacon`, which the plugin never sees. It starts from H4 and H5.

- **Trust boundary.** On one side is the main webview, which holds `call` and the HTTP plugin (ADR 0003, ADR 0020). On the other is the network: the Model Providers, Jev, GitHub, and every HTTP server on this computer. Between them are the plugin's scope in `desktop/capabilities/default.json` and the webview's Content-Security-Policy in `desktop/tauri.conf.json` (ADR 0050).
- **Governed by.** `CONTEXT.md`: Model Provider, Jev, Model catalog, Gateway, Host, Issue Tracker, Release, Finding. `SECURITY.md` ("the window can only make requests to the URLs on its allow-list"). PRD §11. ADR 0020, ADR 0024, ADR 0028, ADR 0035, ADR 0050, and the new ADR 0051.
- **Deliverables.**
  - The local entries narrowed, as defence in depth. `http://localhost:*` and `http://127.0.0.1:*` are now eight entries, which allow a Model Provider on this computer only at the two paths the adapter asks for (`desktop/capabilities/default.json`).
  - Tests that hold the list:
    - `the_windows_http_requests_reach_only_its_allow_list` in `desktop/src/lib.rs` holds it through the plugin's own check, against the app's own capability in Tauri's mock runtime;
    - `app/src/platform/allowList.test.ts` holds the capability to the list, with a new test that this computer is reached only at a Model Provider's API.
  - ADR 0051, `docs/architectural-decision-record/0051-a-model-provider-on-this-computer-reached-only-at-its-apis-two-paths.md`, which is H4's dated answer. ADR 0020, ADR 0024 and ADR 0028 point to it.
  - `SECURITY.md`'s sentence reworded to match the code (probe 4), and a line in `docs/development.md` §8.

## How it was probed

This was done headless on Linux, in WebKitGTK 2.54.0, with Tauri 2.12.3 and `tauri-plugin-http` 2.8.2, the versions in `Cargo.lock`. Everything was written under `/tmp`. Nothing was committed but the deliverables.

1. **Read** every file the brief names; the plugin's scope and `fetch` command (`tauri-plugin-http-2.8.2/src/scope.rs`, `src/commands.rs`); the UI's every use of the Platform's `fetch`; and every HTTP client in the core.
2. **Matched URLs against the list** with the plugin's own pattern code: `parse_url_pattern` (`scope.rs:17-34`), copied into a scratch crate under `/tmp` with `urlpattern` 0.6.0, the version in `Cargo.lock`. Then the new Rust test did the same through the plugin itself.
3. **Built the Desktop App as a Release serves its UI**: `cargo build -p lanewise-desktop --features tauri/custom-protocol`, with the built UI under `/tmp`. The only change was one test script, added to that copy of the built UI from the app's own origin, so the policy let it run. It ran under `xvfb-run`, with `HOME` under `/tmp`. Three local listeners logged every request:
   - one on `127.0.0.1`, which stood in for a server on this computer;
   - one on `127.0.0.2`, which isn't on the list;
   - one on `127.0.0.1` for the webview's own requests.

   The script reported back through the plugin to the first. It was built twice: with the capability as it was, then with the narrowed one.

## Probes from the brief

### 1. What `http://localhost:*` and `http://127.0.0.1:*` let a script in the main webview reach, and whether they can be narrowed

**What I read.**

- A pattern's port of `*` is any port, and a pattern with no path gets `*` for its path, search and hash (`scope.rs:17-34`). So the two entries allowed every port and every path.
- The plugin checks the URL (`commands.rs:290`), then makes the request from Rust with whatever method, headers and body the page gives it. It drops the headers the fetch spec forbids, such as `Host`, `Origin` and `Cookie` (`commands.rs:524`), and sets `Origin` to `tauri://localhost` itself (`commands.rs:350`). There is no CORS, so the page reads the whole answer.
- The UI asks a server on this computer for two things only: `openai.models.list` and `openai.chat.completions.create` (`app/src/ai/openAiCompatible.ts:250`, `:274`). The SDK puts `/models` and `/chat/completions` after the base URL. `openAiCompatible.test.ts:168`, `:211` and `:605` hold each request to its URL.
- The base URL is the user's to choose, at any port and path, but always plain `http` to `localhost` or `127.0.0.1` with a port (`localBaseUrl`, `app/src/ai/aiSettings.ts:56`).

**What the live run showed, with the capability as it was.**

| What the script asked the plugin for | Answer |
| --- | --- |
| `DELETE http://127.0.0.1:<port>/admin/delete-everything`, with its own header, a `Host` and an `Origin` | Sent, and answered `200`. The listener saw the method, the path and the script's own header. It saw the `Host` and `Origin` the plugin set, not the script's |
| The same at `http://localhost:<port>/…` | Sent, and answered |
| `http://127.0.0.2:…`, `http://[::1]:…` | Refused by the plugin, with nothing sent |

So a script in the main webview could reach every HTTP server on `localhost` and `127.0.0.1`, at any path and with any method, and read each answer. That's what H4 says. There's no known way for a script to get into the page (W1, #14), and the policy refuses one (ADR 0050).

**Whether they can be narrowed.** By port, no: the port is the user's. By path, yes: to `/models` and `/chat/completions`, under any base URL. I made that change (ADR 0051). In the second build, the same `DELETE` and the request to `localhost` were refused by the plugin, with nothing sent. `GET …/v1/models` and `POST …/v1/chat/completions`, on both names, were still answered.

**Answer: confirmed as H4 says, and narrowed, as defence in depth** (ADR 0051). A server on this computer is now reached only at a path ending in `/models` or `/chat/completions`. A Release with Ollama and LM Studio is hand check B.

### 2. Every request a Release makes that isn't through the HTTP plugin: `<img>`, `fetch`, `<link>`, `navigator.sendBeacon`

**What I read.**

- **The page's own code.** It asks for one thing itself, not through the plugin: authors' pictures, as images, from `https://avatars.githubusercontent.com`, with no referrer (`app/src/avatars/avatars.ts:13`, `:61`, `:70`, ADR 0035). The policy's `img-src` names that origin, and `connect-src` names only IPC (`desktop/tauri.conf.json:29-30`). Nothing else in `app/src` calls the webview's `fetch`, `XMLHttpRequest`, `sendBeacon`, `EventSource` or `WebSocket` outside tests. Every other request goes through `platform.fetch`.
- **The core's own requests.** These go through no webview at all:
  - Host Integrations and Issue Trackers, through one `ureq` agent (`commands/src/hosts/mod.rs:703`, `commands/src/issues/mod.rs:279`);
  - Gateways, through their own (`commands/src/gateway.rs:307`);
  - the updater, at the one endpoint `allowList.test.ts` pins;
  - and `git` for fetch, pull, push and clone.

  Each is governed by its own ADR (ADR 0016, ADR 0030, ADR 0035, ADR 0038). None is the window's.

**What the live run showed.** The script tried each of these at the third listener. None reached it. The page was sent a violation report for each, naming the directive that refused it:

| Tried | Refused by |
| --- | --- |
| `new Image()`, `<svg><image>`, `<link rel=preload as=image>`, a CSSOM `background-image`, `<video poster>` | `img-src` |
| The webview's `fetch`, `XMLHttpRequest`, `navigator.sendBeacon`, `EventSource`, `WebSocket`, `<a ping>` | `connect-src` |
| `<link rel=stylesheet>` | `style-src` (as `style-src-elem`) |
| `FontFace` | `font-src`, from `default-src` |
| `<audio>`, `<video src>` | `media-src`, from `default-src` |
| `<script src>`, `import()` | `script-src` (as `script-src-elem`) |
| `<iframe>`, `<object>`, a form post | `frame-src`, `object-src`, `form-action` |

`<link rel=icon>`, `<link rel=prefetch>` and `new Worker` made no request and no report: WebKitGTK's webview didn't ask for them at all. `RTCPeerConnection` is undefined in WebKitGTK's webview, so WebRTC wasn't there to try. `window.open` returned `null` and nothing reached the listener. `<link rel=dns-prefetch>` sends only a name lookup, which this sandbox can't watch. Hand checks A and C cover name lookups and WebRTC, on a Release.

**Answer: for the four the brief names, and the others in the table, disproved on a Linux build.** Each was refused by the policy W1 added (ADR 0050). Authors' pictures from GitHub are the page's one request outside the plugin, as the policy allows. WKWebView and WebView2 are hand checks A and C.

### 3. Redirects, and patterns with no path

**Patterns with no path.** I matched 52 URLs against the list with the plugin's own pattern code. Then the new test held 27 of them through the plugin itself.

| A pattern like | Allows | Doesn't allow |
| --- | --- | --- |
| `https://api.anthropic.com`, with no path | Every path and query on that host, over `https`, at its own port | `http://`, another port (`:8443`), `api.anthropic.com.example.test`, `evilapi.anthropic.com` |
| `https://raw.githubusercontent.com/adrianeyre/lanewise/main/package.json` | That path, with any query. `…/main/catalog/../package.json` too, which the URL parser resolves to it | Another file, branch or owner. `%2F..%2F` stays in the path and isn't resolved |
| `http://localhost:*/*/models`, after ADR 0051 | `/v1/models`, `/api/openai/v1/models` on any port | `/`, `/api/pull`, `/v1/models/a-model`, `…/models/../../api/pull`, `?at=/models`, `#/models` |

`localhost` is matched as a name. `127.0.0.1` is matched as an address, which `127.1`, `2130706433` and `0x7f000001` also parse to. `127.0.0.2`, `[::1]`, `[::ffff:127.0.0.1]`, `0.0.0.0`, `localhost.` and `https://localhost` are all refused. A user name and password in a URL don't change which host it goes to.

**Answer: a pattern with no path is its host's every path, and its host alone.** For a cloud Model Provider that's its own API. For this computer it was every server, which ADR 0051 narrows.

**Redirects.**

- **The UI's own requests.** Every request goes through `platform.fetch`, which asks the plugin to follow no redirect (`app/src/platform/tauri.ts:90`). `tauri.test.ts:111` holds that, and ADR 0020 records it. In the live run, a request through it to a local URL that answered `302` came back as the `302`, with the redirect not followed.
- **The core's requests.** Both its `ureq` agents follow none (`commands/src/hosts/mod.rs:703`, `commands/src/gateway.rs:307`).

**Answer:** the UI's own requests, and the core's, follow no redirect.

### 4. Whether `SECURITY.md`'s sentence matches what the code does

The sentence was "The window can only make requests to the URLs on its allow-list, which a test holds it to."

**What I read.** `allowList.test.ts` holds the plugin's scope to a list derived from the code. The window makes one more request, outside the plugin: authors' pictures from GitHub, which ADR 0035 documents and ADR 0050's policy names. So the sentence left that request out. It also said nothing about the core's requests, which aren't the window's.

**Answer: it didn't quite match, and is reworded.** It now says:

- the window's own requests go only to the allow-list, which a test holds;
- a Model Provider on this computer is reached only at its API's own paths (ADR 0051);
- besides those, it shows authors' pictures from GitHub, while Settings allows them;
- Hosts, Issue Trackers and Gateways are asked by the core, not the window.

The line after it, about the policy, was W1's and is as it was.

One more thing doesn't match. H5 calls the pictures "opt-in". They're on unless they're turned off in Settings (ADR 0035, `app/src/settings/avatarSetting.ts:7`), and the Cookie Policy says so. Only an author's email is sent, and only for a repository with a remote on GitHub.com.

## Hand checks (need the owner)

**A. Every connection a Release makes**

Do this once on macOS and once on Windows, each in a disposable account with the latest Release installed (rules of engagement §3).

1. Install Wireshark, which is free, and start a capture on the machine's network interface with the display filter `dns`.
2. Start Lanewise. Open a clone of the round's private repository (E2), which has a remote on GitHub.com. Leave "Show authors' pictures from GitHub" on.
3. Open Settings → AI, turn AI on with a throwaway key for one cloud Model Provider, and ask for one Suggestion on E1's `conflict-merge` fixture.
4. Open Help → "Check for the latest version…".
5. Stop the capture. Write down every name looked up. Expect only these: `raw.githubusercontent.com` (the Model catalog and the version), `avatars.githubusercontent.com` (pictures), `github.com` and the hosts its Releases' downloads redirect to (Updates), `api.github.com` (if signed in to GitHub), the Model Provider's API host, and the hosts `git fetch` reaches for the repository's remotes.
6. Any other name is a lead. Report it privately first (PRD §4). Write the date, the Release and the platform in H5's row above.

**B. A Model Provider on this computer, on a Release**

Do ADR 0051's hand checks 1 to 3 on macOS and on Windows. Then write the date and what was found in H4's row above.

**C. The policy refuses the webview's own requests, in WKWebView and WebView2**

A Release has no inspector, so this needs a debug build of the same tree. Its policy is the same.

1. In a clone of this tree on the disposable machine, run `pnpm exec tauri build --debug --no-bundle`, then start `target/debug/lanewise-desktop` (`.exe` on Windows).
2. In another terminal, run `python3 -m http.server 8765 --bind 127.0.0.1`.
3. Open the webview's inspector: Safari's Develop menu on macOS, or right-click → Inspect on Windows. In its console, run each of these:
   - `new Image().src = "http://127.0.0.1:8765/img"`
   - `fetch("http://127.0.0.1:8765/fetch").catch(() => {})`
   - `document.head.append(Object.assign(document.createElement("link"), { rel: "stylesheet", href: "http://127.0.0.1:8765/css" }))`
   - `navigator.sendBeacon("http://127.0.0.1:8765/beacon", "x")`
4. Check that the server logs none of the four, and that the console shows a `Content-Security-Policy` message for each.
5. Also run `typeof RTCPeerConnection`, and write down what it says. Anything other than `"undefined"` is worth a note in H5's row.
