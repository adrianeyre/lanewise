# R3 — Caches, branch protection and the Model catalog

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #29, label `prd:pen-test`). R3 asked three things. Can anything but `main` write a cache that the release jobs restore? What does `main`'s branch protection allow, and who can push to it? And what could a hostile Model catalog do? It starts from H13, and takes the two parts of H12 that R2 left to it.

- **Trust boundary.** `main`, the caches restored into the release jobs, and the Model catalog the app fetches from `main`. On one side are what `release.yml` builds, signs and publishes, and the catalog every running Lanewise with AI on reads. On the other are whoever and whatever can write to `main` or save a cache the release jobs restore.
- **Governed by.** `CONTEXT.md`: Model catalog, Release, Update key, Finding. ADR 0021 (a Model catalog in the repository describes the live model lists) and ADR 0029 (Releases by semantic-release). Beside them, ADR 0052 (who can change a Release's files) and ADR 0053 (the Update key in a job that only `main` can use).
- **Deliverables.**
  - Defence in depth in `parseCatalog` (`app/src/ai/modelCatalog.ts:75`). A `match` or `exclude` pattern now has to be a regular expression on its own, which is what the schema's `regex` format checks. Before, being one once Lanewise had put its anchors round it was enough. Such a pattern could match no more model IDs than `.*` already can, so this brings Lanewise's check into line with the schema; it closes no hole.
  - Tests pinning what held. Each was checked to fail when the behaviour it holds is broken:
    - `app/src/ai/modelCatalog.test.ts`:
      - `refuses a catalog with a pattern that's one only inside the anchors`;
      - `refuses a catalog with a Model Provider named as an object's own property` (`__proto__`), by the schema and by Lanewise;
      - `offers only the model IDs the live list returns, however much a pattern matches`;
    - `app/src/settings/ModelProviderSettings.test.tsx`: `the model catalog's names are drawn as text, and it offers no model the live list doesn't have`, with markup in a model's and a version's name, checked with axe;
    - `app/scripts/workflows.test.ts`:
      - `no workflow runs on main for anything but a push to it, a schedule or someone who can write to the repository`;
      - `the jobs that sign and publish a Release restore no cache another job saved`.

## How it was probed

This was done headless on Linux (Debian 13), with Node 26.11.1 and Git 2.47.3, and the tree at `f7f8f3b`. The actions were the ones the workflows pin: `actions/setup-node` v7.1.0 (`949feb2`), `Swatinem/rust-cache` v2.9.2 (`6323deb`) and `pnpm/action-setup` v6.1.0 (`ea17c68`). Their sources were downloaded to `/tmp` and read, not run. Ajv was 8.20.0 and `ajv-formats` 3.0.1, as the lockfile has them.

Three things were sent to GitHub, all of them unauthenticated `GET`s of `adrianeyre/lanewise`'s public metadata: `branches/main`, `rules/branches/main` and `rulesets`. Nothing was written to GitHub. No catalog was published, and nothing was sent to a Model Provider. Scratch files were written under `/tmp` and deleted.

1. **Read** `ci.yml`, `release.yml` and `codeql.yml`, and in each job, every step that restores or saves a cache. Read where the three actions' sources build their cache keys and restore keys. Read GitHub's documentation on who can restore a cache ("Caching dependencies to speed up workflows", under "Restrictions for accessing a cache").
2. **Read** `main`'s ruleset and classic branch protection through GitHub's public REST API, and `.releaserc.json` for what semantic-release pushes.
3. **Read** `app/src/ai/modelCatalog.ts`, `catalog/models.schema.json`, `app/src/ai/requests.ts`, `app/src/ai/aiSettings.ts`, `app/src/settings/ModelProviderSettings.tsx` and `desktop/capabilities/default.json`. Built hostile catalogs in tests and in scripts under `/tmp`: markup in names, prototype keys, patterns that match everything, patterns that escape the anchors, and patterns with nested quantifiers. Timed each pattern against the model IDs that today's Model Providers list, both in Node 26's V8 and through `parseCatalog` and `describeModels`.
4. **Broke each behaviour the new tests hold**, one at a time, in a copy of the tree that wasn't committed. With the pattern's own check taken out of `parseCatalog`, `…one only inside the anchors` failed. With `cache: pnpm` given to `publish`'s `setup-node`, `the jobs that sign and publish…` failed. With a `workflow_run` trigger added to `release.yml`, `no workflow runs on main…` failed.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Whether anything but `main` can write a cache the release jobs restore

**What I read.** These are the caches each job of `release.yml` restores:

| Job | What it restores | Where |
| --- | --- | --- |
| `verify` (`ci.yml`) | pnpm's store; `~/.cargo` and `target/` | `ci.yml:58-61`, `:71`, `:106-111` |
| `release` | pnpm's store | `release.yml:70-73` |
| `windows` | pnpm's store; `~/.cargo` and `target/` | `release.yml:140-143`, `:162` |
| `macos` | pnpm's store; `~/.cargo` and `target/` | `release.yml:210-213`, `:219` |
| `sign` | nothing | `release.yml:310-312` |
| `publish` | nothing | `release.yml:376-378` |
| `website` | pnpm's store | `release.yml:464-467` |

- **`setup-node`** keys pnpm's store as `node-cache-<OS>-<arch>-pnpm-<hash of pnpm-lock.yaml>`, with no restore keys for pnpm (its `src/cache-restore.ts`). It caches by itself only when `package.json` names npm as its package manager (its `src/main.ts`, `npmRegex`). Lanewise's names `pnpm@12.8.1`, so `sign` and `publish`, which give `setup-node` no `cache`, restore nothing.
- **`rust-cache`** keys `~/.cargo`'s registry, git checkouts and installed binaries, and `target/`, as `v0-rust-<job>-<OS>-<arch>-<hash of the Rust version and its environment>-<hash of the lockfiles>`. It also restores the newest entry with the same key short of the lockfiles' hash (its `src/config.ts`, `src/restore.ts`).
- **Who can restore what.** GitHub's documentation says a run can restore caches saved on its own branch or ref, or on the default branch. It can't restore caches saved on a child or sibling branch. A pull request's run saves its caches for the pull request's merge ref, `refs/pull/<n>/merge`, whether it comes from a fork, a branch of this repository or Dependabot.
- **What starts a run.** `ci.yml` starts on a pull request, by hand, and when another workflow calls it. `codeql.yml` starts on a pull request, a push to `main`, a weekly schedule, and by hand. `release.yml` starts on a push to `main` and by hand. No workflow starts on `pull_request_target`, `workflow_run`, `issue_comment` or any other event someone without write access can cause on `main`. Starting a run by hand takes write access. The one workflow called from another is `ci.yml`, called by `release.yml`'s `verify`.
- **Artifacts.** `sign` and `publish` download only the artifacts uploaded by the same run's jobs (`release.yml:317-325`, `:380-384`).

**Answer: disproved, and pinned.** Nothing but `main` writes a cache that the release jobs restore. A pull request's run saves its caches under its own merge ref, from a fork, a branch here or Dependabot alike. So does a run started by hand on another branch, under that branch. Only runs on `main` save what `release`, `windows`, `macos` and `website` restore. `sign` and `publish` restore no cache at all. The job that holds the Update key and the job that publishes a Release read nothing another job saved, only this run's artifacts. Held by `no workflow runs on main for anything but a push to it…`, `the jobs that sign and publish a Release restore no cache another job saved` and, from before, `no workflow runs a pull request's code with the base repository's token`. Which caches a Release's own run restored is hand check B.

### 2. What `main`'s branch protection allows, and who can push to it

**What I read.**

- **The ruleset.** `GET /repos/adrianeyre/lanewise/rules/branches/main` and `/rulesets` show one ruleset, `main` (24914495), on the default branch (`~DEFAULT_BRANCH`). Its enforcement is `active`, and it was made on 12 October 2026. Its rules are `deletion` and `non_fast_forward`. `GET /branches/main` shows classic branch protection is off. A ruleset's bypass list isn't shown to anyone without admin access to the repository.
- **What the release job pushes.** `.releaserc.json`'s `@semantic-release/git` pushes semantic-release's version commit, `chore(release): <version> [skip ci]`, to `main`, with `CHANGELOG.md` and `package.json` and nothing else, and then the Release's tag. It pushes them with the `release` job's `GITHUB_TOKEN` (`release.yml:80-86`). A push made with a `GITHUB_TOKEN` starts no workflow.
- **What's checked after.** The `sign` job checks that a Release's tag is the commit merged and semantic-release's version commit, and nothing more (`release.yml:314-315`, `app/scripts/release/versionCommit.ts`, R2).

**Answer.** What held: `main` can't be deleted, and nothing can force-push to it, so a commit once on `main` stays in its history, where anyone can read it. A Release is built only from a tag that `sign` has checked is the commit merged plus the version commit. Who can push to `main` is whoever can write to the repository's contents:

- the owner, and any collaborator or team with Write, Maintain or Admin;
- any GitHub App, deploy key or token with write access to contents;
- the workflow jobs whose token has `contents: write`, which are `release` and `publish` (R2).

ADR 0052 lists the same people and Apps as able to change a Release's files. Who has that today is in the repository's settings, which this sandbox can't read: hand check A.

### 3. What a hostile catalog could do: catastrophic backtracking in a `match` expression, misleading names

**What I read.** `parseCatalog` (`app/src/ai/modelCatalog.ts:159`) reads a copy whole or not at all. It keeps patterns, names, Effort levels and budgets, and nothing else: the schema allows no other property (`catalog/models.schema.json:8`, `:40`, `:57`, `:75`). `fetchCatalog` (`:194`) fetches exactly `CATALOG_URL` (`:47`) and sends no key or header. It falls back to the bundled copy on any failure. The HTTP plugin's scope names that one file (`desktop/capabilities/default.json:22`). `describeModels` (`:273`) is called each time a Model Provider's models are listed and each time a Suggestion is asked for (`app/src/ai/requests.ts:86`, `:153`). It looks a section up by the adapter's own `catalog` name. It tests each pattern only against the model IDs the Model Provider's live list returned. A version's name is the Model Provider's own where its list gives one, and otherwise the catalog's (`:258`). Settings draws every name as the text of a native `option` or `p` (`app/src/settings/ModelProviderSettings.tsx:702-733`). `selectionFor` sends the Effort the user chose, if the version takes it, and otherwise none. It never sends the catalog's default (`app/src/ai/aiSettings.ts:159`).

**What the runs showed.**

| Hostile catalog | What Lanewise did | Held by |
| --- | --- | --- |
| Markup in a model's and a version's name | Drew it as text in the Model select and the Effort note; no element was made from it | `the model catalog's names are drawn as text…` |
| A family whose pattern is `.*`, or names a model the list doesn't return | Offered only the IDs the list returned; the unlisted family wasn't offered | `offers only the model IDs the live list returns…`, `…offers no model the live list doesn't have` |
| A new name for a Claude or Gemini model | The Model Provider's own name was shown | `takes the Model Provider's own name and efforts where its list gives them` |
| A section for a Model Provider Lanewise has no adapter for | Nothing read it; no Model Provider was added | `describeModels` is only called with an adapter's own section (`requests.ts:86`) |
| A Model Provider named `__proto__`, or a model named `other-versions` | Refused whole, by the schema and by Lanewise | `refuses a catalog with a Model Provider named as an object's own property`, `…with a model named Other versions` |
| A pattern that's a regular expression only inside Lanewise's anchors, such as `x)\|(?:` | Was taken before, matching every model ID, as `.*` does. Now refused whole, as the schema refuses it | `refuses a catalog with a pattern that's one only inside the anchors` |
| A URL, header or host anywhere in it | Refused whole by the schema; Lanewise's reader keeps none | the schema's `additionalProperties: false` |
| A default Effort for every model | Only shown in the Effort select; never sent | `selectionFor`'s `the newest version by default, with the Model Provider's default effort` |

**Answer.** What held: a hostile catalog reaches no host, header or key, adds no Model Provider, offers no model the Model Provider doesn't list, and renames neither Claude's nor Gemini's models. Every name it gives is drawn as text. It is only ever read from `main` over TLS or from the bundled copy, and only once AI is on and a Model Provider's First-use disclosure is accepted (ADR 0021). A pattern is compiled once, when the catalog is read. It is only ever tested against the model IDs a Model Provider's own list returns, never against a repository's text or anything the user typed. A catalog that's wrong anywhere is never used in part, and Lanewise's check now refuses every pattern the schema does.

## Hand checks (need the owner)

**A. Who can push to `main`**

1. In `adrianeyre/lanewise`, open **Settings → Collaborators and teams**. Note everyone with Write, Maintain or Admin.
2. Open **Settings → GitHub Apps** and **Settings → Deploy keys**. Note every App with write access to contents, and every deploy key with write access.
3. Open **Settings → Rules → Rulesets → main**. Note its rules and its **Bypass list**.
4. Keep the lists in your own records, beside ADR 0052's hand check 2. Write the date in H12's and H13's rows above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).

**B. The caches a Release's run restored**

1. Open **Actions → Caches** (under **Management**). Check that every entry's branch is `refs/heads/main` or a pull request's `refs/pull/<n>/merge`.
2. On the next run of `release.yml` that makes a Release, open the `release`, `Windows installer`, `macOS app (universal)` and `Project website` jobs. In each `setup-node` and `rust-cache` step, check that the "Cache restored from key" line names a key from that job's own platform: `node-cache-<OS>-…-pnpm-…` and `v0-rust-<job>-<OS>-…`.
3. In `Update packages` and `publish`, check that no step restores a cache.
4. Write the date and the Release in H12's row above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).

**C. The Model catalog in a Release**

1. On the disposable Windows or macOS machine of the rules of engagement, turn AI on with the round's throwaway key (E2). Accept the First-use disclosure.
2. With the free local intercepting proxy of rules §4 running, open Settings' AI section. Check that the catalog is fetched once from `raw.githubusercontent.com/adrianeyre/lanewise/main/catalog/models.json`, with no `Authorization` header or API key, and with no CORS error (ADR 0021's hand check).
3. Check that the models' names are the ones `catalog/models.json` on `main` gives, and that Claude's and Gemini's are their own.
4. Write the date, the Release and the platform in H13's row above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).
