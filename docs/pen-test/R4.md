# R4 — The Project website's content and build

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #30, label `prd:pen-test`). R4 asked three things. Can Release data read when the website is built get into the page, or change a download link? What inline scripts does the page have, and would a Content-Security-Policy in a `<meta>` hold? And is any third-party script or font loaded?

- **Trust boundary.** The data the Project website is built from, and the page a visitor downloads Lanewise from. On one side are what `release.yml`'s `website` job reads (GitHub's `releases/latest`, `CHANGELOG.md`, the npm packages' and crates' licences for the Credits) and the hosts in front of the page (GitHub Pages, and the Cloudflare the custom domain is served through). On the other is the visitor's browser, and the installer it downloads.
- **Governed by.** `CONTEXT.md`: Project website, Release, Changelog, Finding. ADR 0031 (the project website, prerendered from React and deployed to GitHub Pages), and the new ADR 0054. Beside them, ADR 0029 (Releases by semantic-release), ADR 0050 (the main webview's policy, which this follows) and ADR 0052 (who can change a Release's files). PRD §3.1: GitHub Pages is GitHub's; the website's own content and build are in scope.
- **Deliverables**, as defence in depth:
  - ADR 0054, `docs/architectural-decision-record/0054-a-content-security-policy-for-the-project-website-and-its-downloads-the-release-it-is-built-from.md`. ADR 0031, `docs/releases.md` and `website/README.md` point to it.
  - A Content-Security-Policy in the built page's head (`website/vite.config.ts:71`, put in by `:85`): its own origin, and the theme script by its hash, worked out from `index.html` as the config loads (`:58`). The config refuses to load if `index.html` has any other inline script. The dev server has no policy, as the app's has none.
  - The downloads are the Release the website is built from. `downloadsOf` (`website/src/downloads.ts:36`) takes the root `package.json`'s version, which is also the footer's, and refuses a Release whose tag isn't `v` and that version (`:37`).
  - Tests, each checked to fail when what it holds is broken:
    - `website/src/build.test.ts`, new, builds the website as the deploy job does, with a Release whose name, notes, author and an extra file's name hold markup and another origin's URLs:
      - `the Content-Security-Policy › comes first in the head, before anything it governs`;
      - `… › lets the page's own origin and the theme script run, and nothing inline besides`;
      - `… › leaves the page's own markup no inline style to refuse`;
      - `everything the built page loads is its own: no third-party script, stylesheet, font or picture`;
      - `a Release's own words never reach the built page, and its downloads are exactly its installers`;
      - `the build is refused a Release of any version but the one it is built from`;
    - `website/src/downloads.test.ts`: `only the Release the website is built from is offered, so the buttons are always the footer's version`.

## How it was probed

This was done headless on Linux (Debian 13.7), with Node 26.11.1, Vite 8.3.4, React 19.3.0, and the tree at `5bf1a43`. The real browser was WebKitGTK 2.54.0's MiniBrowser under `xvfb-run`, writing its console to standard output.

Three kinds of request left the sandbox, all unauthenticated `GET`s of public things: GitHub's `repos/adrianeyre/lanewise/releases/latest`; the deployed site's pages and files at `https://lanewise.adrianeyre.co.uk/`; and a DNS lookup of that name. Nothing was written to GitHub, Cloudflare or anywhere else. Scratch files, builds and Releases made up for the probes were kept under `/tmp` and deleted.

1. **Read** `website/` (every source file, `index.html`, `vite.config.ts`, `public/`), the footer it takes from `app/src/legal/` (`Footer.tsx`, `ExternalLink.tsx`, `Changelog.tsx`, `changelogMarkdown.ts`, `Credits.tsx`, `BundledCredits.tsx`), `app/scripts/credits.ts`, `.releaserc.json`, and `release.yml`'s `pages`, `website` and `deploy` jobs (`:415-510`).
2. **Built the site** with `pnpm website:build` and made-up Releases in `LANEWISE_LATEST_RELEASE`. One had markup in its name and notes. Others had other versions, other tags, or files and pages elsewhere. Read what each build wrote: every `<script>`, `<link>`, `<img>`, `url()` and origin in `dist/`, and where each Release's words ended up.
3. **Loaded the built site in WebKitGTK**, served from `127.0.0.1`, in three copies, with a probe script of the round's own logging what ran and every `securitypolicyviolation`. The first copy had the new policy and nothing else added. The second had the policy, and markup injected into the page as if the build had let some through. The third had the same markup and no policy, as the control. In each, the probe opened the footer's Cookie Policy and Changelog dialogs. It ran in a light and a dark GTK theme.
4. **Compared the deployed site with this tree's build.** Built the tree as it was, without the new policy, from the live `releases/latest`. Then fetched each of the built files from the deployed site and compared them byte for byte.
5. **Broke each behaviour the new tests hold**, one at a time, in the working tree, and put each back:
   - With the policy's plugin taken out, `comes first in the head…` failed.
   - With `'unsafe-inline'` added to `style-src`, `lets the page's own origin…` failed.
   - With a `style` on the page's heading, `leaves the page's own markup no inline style…` failed.
   - With a stylesheet from a web font service in the head, `everything the built page loads is its own…` failed.
   - With the Release's name drawn after its version, `a Release's own words never reach the built page…` failed.
   - With `downloadsOf` taking its version from the tag again, `the build is refused a Release of any version…` failed.
   - With a second inline script in `index.html`, the config refused to load, naming both. Every website test and the build stopped with it.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. Whether Release data read at build time can inject into the page or change a download link

**What I read.** The `website` job saves `gh api repos/adrianeyre/lanewise/releases/latest` to a file, with a token that can only read (`release.yml:453`, `:476-484`), and `vite.config.ts:24-28` hands it to `downloadsOf`. Of everything GitHub returns, `downloadsOf` reads three fields: `tag_name`, `html_url` and each file's `name` and `browser_download_url` (`downloads.ts:12-16`). The Release's name, notes, author and anything else are never read. Before this round, the version shown was the tag with its `v` taken off. The page's link to the Release had to be `…/releases/tag/<tag>` exactly (`:41`). Each installer's link had to be `…/releases/download/<tag>/<name>` exactly, or the button linked to the Release's page instead (`:43-47`). The result goes into the bundle through Vite's `define` as JSON (`vite.config.ts:110`), and into the HTML through React's `renderToString` (`src/prerender.tsx`). `Site.tsx:177-191` draws the version as text and the links as `href`s, which React escapes.

The build reads two other things written by people other than the owner. `CHANGELOG.md` is made of Commit Messages. `changelogMarkdown.ts` reads it into blocks that are drawn as React elements, never as HTML. A link in it is kept only if it starts `http://` or `https://` (`:100`), and opens in a new tab with `rel="noopener noreferrer"` (`ExternalLink.tsx:27`). The Credits hold every npm package's and crate's name, version, licence and licence text. They go into the bundle as a JSON module (`app/scripts/credits.ts:270`) and are drawn as text (`BundledCredits.tsx:13`, `:18`), with no links.

**What the runs showed.**

| Release given to the build | What the page did | Held by |
| --- | --- | --- |
| Markup and other origins' URLs in its name, notes and author, and in an extra file's name | None of it appeared in the HTML or any bundle | `a Release's own words never reach the built page…` |
| Its two installers, named for its version | Both buttons, in both places, linked to exactly those files, and "What's new" to its page | the same |
| An installer of another version, or none | That button linked to the Release's page | `an installer of another version isn't offered as this one`, `a platform whose installer the Release lacks…` |
| A page or an installer anywhere but this repository's Releases | The build failed | `a link anywhere but this repository's Releases is refused…` |
| A Release of another version than the tree's, or a tag of any other shape | Was taken before, with its tag as the version. Now the build fails, naming both | `the build is refused a Release of any version…`, `only the Release the website is built from is offered…` |
| The live `releases/latest`, `v1.1.1` | Built, linking `Lanewise_1.1.1_universal.dmg`, `Lanewise_1.1.1_x64-setup.exe` and the Release's page on `adrianeyre/lanewise` | the root `package.json`'s version is `1.1.1` |

**Answer.** What held: no part of a Release's own words reaches the page, and a download button only ever links to a file on this repository's Releases, named for the Release's version, or to the Release's page. The Changelog and the Credits are drawn as text, and the Changelog's links are only ever `http` or `https`. **Answered with a deliverable:** the Release offered is now the one the website is built from. Its tag can only be `v` and the footer's version, so the download section and the footer always agree, and no tag of any other shape gets as far as a link. What it can't do is make a Release's files what was built. The links name files on the Release, and who can change those is ADR 0052's.

### 2. Inline scripts, and whether a meta CSP would hold

**What I read.** `website/index.html` has three scripts (`:67`, `:90`, `:107`):

- the JSON-LD, which is data that no browser runs;
- the theme script, which follows the OS's light or dark setting before first paint;
- Vite's module script, which becomes `/assets/index-<hash>.js` when built. Its lazy chunks are the Changelog and the Credits, from the same origin.

The built page had no `style` attribute and no `<style>`. React and the theme script set styles through the CSSOM. The page has no form, frame, plugin or `<base>`. GitHub Pages sends no headers of a site's own. The Cloudflare that the custom domain is served through sent no policy of its own on 12 October 2026.

**What the runs showed** in WebKitGTK:

| Copy | Ran | Refused |
| --- | --- | --- |
| The built page with its policy | The theme script, in light and dark; hydration; the Cookie Policy dialog; the Changelog's lazy chunk, with its nine items | Only the probe's own `fetch` to another origin. No violation came from the page itself |
| With its policy, and injected markup | Everything above, the same | An inline script, a script from another origin, a picture from another origin, an inline `style`, and the `fetch` to another origin |
| Without a policy, and the same markup (the control) | All of the injected markup | Nothing. The `fetch` went out, and only CORS kept its answer from the script |

The first try named `manifest-src`, which WebKit doesn't know, and it said so in the console. The policy now uses `default-src 'self'` for the manifest instead, and every directive is one that every engine knows.

**Answer: a meta CSP holds, and the built site now has one.** The policy is `default-src 'self'; script-src 'self' 'sha256-…'; style-src 'self'; object-src 'none'; base-uri 'none'; form-action 'none'`. ADR 0054 gives the reason for each directive. The page runs as before under it, and markup that got into the page couldn't run a script, load anything from another origin, or restyle the page. In a `<meta>`, it can't set `frame-ancestors`, so the page can still be framed. That's recorded in ADR 0054: the page has nothing to do but follow links. Held by the three `the Content-Security-Policy › …` tests and the config's own check on `index.html`. Chrome, Firefox and Safari are hand check A.

### 3. Whether any third-party script or font is loaded

**What I read.** Every `<script src>`, `<link>` and `<img>` in the built `index.html`, every `url()`, `@import` and `@font-face` in its stylesheet, and every origin named in `dist/`. Fonts are the system's own (`app/src/styles.css:268`, `:666`), and there is no `@font-face`. The other origins named in the bundle are links a visitor follows (`github.com/adrianeyre/lanewise`, `git-scm.com`), the SVG namespace, React's error page in its error messages, and `schema.org` and `opensource.org` in the JSON-LD. None is loaded. The one `fetch` in the bundle is Vite's modulepreload polyfill, which fetches only the page's own `<link rel="modulepreload">`. Nothing in the website's code touches storage (`head.test.ts`, from ADR 0031).

**What the deployed site showed.** On 12 October 2026, every file the build writes, fetched from `https://lanewise.adrianeyre.co.uk/`, was the same byte for byte as this tree builds, without the new policy, from the live Release. Its scripts were the JSON-LD, the theme script and `/assets/index-CCbqkbAt.js`. Nothing from Cloudflare (`cdn-cgi`, an analytics beacon) or anywhere else had been added.

**Answer: disproved, and pinned.** The website loads no third-party script, stylesheet, font or picture, and nothing in front of it adds one. Held by `everything the built page loads is its own…`. With the new policy, a browser would refuse such a load even if the build or Cloudflare added one. Cloudflare's own settings are hand check B.

## Hand checks (need the owner)

**A. The policy in the browsers visitors use** (ADR 0054's hand checks 1 to 6)

1. Once this has merged and the website has deployed, open `https://lanewise.adrianeyre.co.uk/` in Chrome, Firefox and Safari, with each one's console open.
2. Load the page. Check that the console shows no message naming `Content-Security-Policy`, and that the page draws in the OS's light or dark setting with no flash of the other. Switch the OS between light and dark, and check that the page follows.
3. Open each footer dialog: the version's Changelog, Privacy Policy, Terms and Conditions, Cookie Policy, Accessibility and Credits. Each opens with its text, and still nothing is in the console.
4. In Chrome's DevTools → Network, reload. Check that every request is to `lanewise.adrianeyre.co.uk`.
5. Check that the download buttons' version, the footer's version and the latest Release on GitHub are the same.
6. Run Lighthouse as `website/README.md` says. Accessibility, best practices and SEO are each 100.
7. Write the date and the browsers' versions here. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).

**B. What's in front of the website** (ADR 0054's hand check 7)

1. In Cloudflare's dashboard for `adrianeyre.co.uk`, open `lanewise.adrianeyre.co.uk`'s settings. Check that Web Analytics' automatic setup, Rocket Loader and Zaraz are off, and that no Worker or rule changes its pages.
2. In `adrianeyre/lanewise`, open **Settings → Pages**. Check that the custom domain is `lanewise.adrianeyre.co.uk`, and that **Enforce HTTPS** is ticked. In your GitHub account's **Settings → Pages**, check that `adrianeyre.co.uk` is a verified domain.
3. Write the date here. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).

**C. The first deploy after this merges**

1. On that run of `release.yml`, check that `Project website` and `Deploy the project website` passed.
2. If `Project website` fails with "The latest Release is …, but the website is built from version …", check that the latest Release on GitHub was made by `release.yml`. A Release made by hand isn't offered on the website (ADR 0054).
