# G1 — what opening, fetching and diffing a repository runs

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #18, label `prd:pen-test`). G1 probes what Lanewise runs from a Hostile repository's own configuration and attributes when the user opens it, lets its Tab fetch, or reads its diffs. It starts from H6.

- **Trust boundary.** A Hostile repository's `.git/config`, `.gitattributes` and hooks on one side; the user's machine on the other. Between them are the core's reads through `gix` (`core/src/repository.rs`, `core/src/status.rs`, `core/src/diff.rs`) and every system `git` Lanewise runs in the repository (`core/src/git.rs`, `core/src/remote.rs`).
- **Governed by.** `CONTEXT.md`: Hostile repository, Upstream, Tab, Toolbar, Finding. ADR 0002 (`gix` for reads, the system `git` for the rest), ADR 0007 (the working tree's changes), ADR 0013 (fetch through `git`), ADR 0044 (fetching as the window is focused), with ADR 0043 and ADR 0046. `SECURITY.md`, "What a repository's own Git configuration or hooks run".
- **Deliverables.** `core/tests/repository_config.rs`, which pins what held:
  - `a_command_armed_this_way_writes_its_marker_when_git_runs_it`: the marker command the other tests arm does run, so they can't pass for want of one;
  - `opening_a_repository_and_reading_its_history_labels_upstreams_and_a_commits_diff_runs_nothing_its_configuration_names`;
  - `no_diff_of_a_commit_or_the_working_tree_runs_a_diff_drivers_textconv`;
  - `reading_the_status_runs_no_fsmonitor`.

## How it was probed

This was done headless on Linux, with `gix` 0.88.0 (the version in `Cargo.lock`) and `git` 2.47.3. Everything was written under `/tmp`. Nothing was fetched from a Host, and nothing was committed but the deliverables.

1. **Built E1's Hostile repositories** with `pnpm pen-test:fixtures`, and used `config-and-attributes`, the `conflict-*` family, and copies of them with more of `.git/config` armed. Every armed command only writes a marker file under a `lanewise-pen-test-markers-*` folder in `/tmp`. Building them fired nothing.
2. **Listed every command the UI sends with no click**, from launch to a Tab shown and the window focused, and traced each to the core: whether it reads through `gix` or runs the system `git`, and with what arguments.
3. **Ran the core itself** on each repository, in a scratch crate under `/tmp` that depends on `lanewise-core` by path and makes the same reads the commands do. The marker folder was cleared before each step and listed after it.
4. **Ran each `git` Lanewise runs on its own** in those repositories, with its arguments, `GIT_TERMINAL_PROMPT=0` and an empty stdin, as `core/src/git.rs` starts it.
5. **Read** `gix` 0.88.0's rules for trust and ownership, and for where a filter or diff driver's program comes from.
6. **Pinned what held** in the tests above.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. What a repository downloaded as an archive, or on a network drive, runs when it's opened and the user does nothing else

**What I did.** Opened E1's `config-and-attributes` repository, and one extracted from an archive, through the core as the commands do, and ran each `git` Lanewise runs on its own in them. A filter driver's `clean`, `smudge` and `process`, a diff driver's `textconv` and `command`, `core.fsmonitor`, `core.sshCommand`, a remote's `uploadpack` and a credential helper were armed.

**What I read.** Launch reopens the Tabs left open (`app/src/App.tsx:94`), and the Welcome screen opens each Recent Repository to mark one whose folder has gone (`app/src/welcome/WelcomeScreen.tsx:106`). Each is `openRepository`, which is `gix::discover` (`core/src/repository.rs:20`). Nothing chooses a file or a commit without a click (`app/src/repository/FileStatusList.tsx:116-125`, `app/src/repository/CommitHistory.tsx:284-291`), and on the Conflicts page no conflicted file is read until one is chosen.

**What held.**

| Read | Markers |
| --- | --- |
| `openRepository`: `gix::discover`, with every program armed | None |
| The Commit graph's history and Labels, a commit's files and their diffs | None |
| `branches`' `git for-each-ref`, with an Upstream to count | None |
| `checkGitSetup`'s `git config` for the credential helpers, run in the OS temp folder (`core/src/setup.rs:206-216`) | Doesn't read the repository |
| `pullRequests`' `git credential fill`, for a GitHub remote, run with no working folder of its own (`core/src/credential.rs:148-160`) | Doesn't read the repository's configuration |

The test `opening_a_repository_and_reading_its_history_labels_upstreams_and_a_commits_diff_runs_nothing_its_configuration_names` pins the first three rows with every program above armed. A network drive's ownership is probe 3's.

### 2. What `gix` runs from `.git/config` and `.gitattributes` on status and diff

**What I read.** The status is `gix`'s, comparing `HEAD`, the index and the working tree (`core/src/status.rs:84-97`). A diff is read through `gix`'s diff resource cache in `Mode::ToGit`, and a diff it would hand to an external program is made internally instead (`core/src/diff.rs:510-529`). A commit's diff has no working tree to read (`WorktreeRoots::default()`, `core/src/diff.rs:504`).

**What held.**

- **No diff runs a diff driver's `textconv` or external `command`**, of a commit or of the working tree. A `.gitattributes` giving every file a diff driver, with both armed, left the diffs as the files' own lines, and no marker (`no_diff_of_a_commit_or_the_working_tree_runs_a_diff_drivers_textconv`).
- **A commit's diff reads its objects alone**, through no filter. With every program armed, no marker.
- **The status runs no `core.fsmonitor`.** `gix` 0.88.0 has no file system monitor support, and an armed one wrote no marker (`reading_the_status_runs_no_fsmonitor`).

### 3. Whether `gix` applies ownership checks (`safe.directory`) as `git` does

**What I read.** `gix-discover` gives a repository full trust only if the current user owns the `.git` it finds (`gix-discover-0.56.0/src/upwards/mod.rs:267`, `gix-sec-0.15.0/src/identity.rs`). With reduced trust, the repository's own configuration sections aren't trusted, so a filter driver named only there isn't taken (`gix-0.88.0/src/config/mod.rs:61`, `gix-0.88.0/src/filter.rs:248`). `safe.directory` is read only from the system and global configuration, as `git` reads it (`gix-0.88.0/src/config/tree/sections/safe.rs:13-16`), and a match restores full trust.

**What I ran.** `git` in repositories with folders another account owns (root, here). `git` refused each as "dubious ownership", and ran nothing first.

**What held.** Every `git` Lanewise runs applies `git`'s own ownership check, since it's the system `git` (ADR 0002). A `.git` folder another account owns gives `gix` reduced trust, and its own configuration names no filter driver `gix` will run, unless `safe.directory` names it. That last part is read, not run: making a `.git` folder that another account owns needs root, which this sandbox doesn't have. Hand check C runs it on a Release.

### 4. What fetch on focus and at launch runs from `.git/config`

**What I read.** `useRemoteOperation` fetches the Tab shown once its Commit graph has its first window, and as the window is focused, at most every 30 seconds after the last fetch it started on its own, unless a fetch, pull or push is running (`app/src/repository/useRemoteOperation.ts:240`, `:274-285`, ADR 0043, ADR 0044). Launch restores the Tabs left open (`app/src/App.tsx:94`), so the shown one fetches with no click. The fetch is `git fetch --all --prune --progress` in the repository (`core/src/remote.rs:280`).

**What held.**

- **Its arguments are fixed.** Nothing from the repository, a remote's name or a ref, is on its command line (`core/src/remote.rs:280`). `git` is started with an argument list, never through a shell (`core/src/git.rs:168-181`).
- **Nothing waits on the user.** `GIT_TERMINAL_PROMPT=0` and an empty stdin (`core/src/git.rs:168-181`), so a Host asking for a password fails the fetch rather than prompting.
- **A repository with no remotes runs no `git`** (`core/src/remote.rs:275-277`).
- **One at a time.** A fetch started while another fetch, pull or push runs follows that one instead (ADR 0013), and a cancelled one stops `git`, with its whole process group on macOS and Linux (`core/src/git.rs:446-470`).
- **The Setting is read as the window is focused**, so turning it off stops the next fetch, not only the next Tab's (ADR 0044).

## Hand checks (need the owner)

Do each once on macOS and once on Windows, in the disposable account of the rules of engagement (§3), with the latest Release installed. The marker folder is the new `lanewise-pen-test-markers-*` folder `pnpm pen-test:fixtures` makes and prints, in the OS temp folder: `$TMPDIR` on macOS, `%TEMP%` on Windows. On Windows, Git for Windows' own `sh` runs the markers' commands.

**A. A repository from an archive, opened and left alone**

1. In a clone of this tree, run `pnpm pen-test:fixtures`. It says where the Hostile repositories are.
2. Make a zip of each of `config-and-attributes`, `conflict-merge` and `injection`, with its `.git` folder, and extract each into a new folder under Downloads, as a downloaded archive would be.
3. Delete the marker folder.
4. Open Lanewise, and open the `config-and-attributes` folder. Touch nothing. List the marker folder, and note what's there.
5. Wait for the Toolbar's fetch to finish or fail. List the marker folder again.
6. Switch to another app for a minute, and click back into Lanewise's window. List the marker folder again.
7. Quit Lanewise and open it again, so it restores the Tab. List the marker folder again.
8. Repeat steps 3 to 7 for `conflict-merge` and `injection`, then once more for each with Settings' "Fetch when you switch to a repository's tab or come back to Lanewise" turned off.
9. Record, for each step, which markers were there. Anything there is a lead: file it as PRD §7 says, privately first under PRD §4.

**B. Diffs**

1. In each repository of hand check A, with the marker folder deleted, choose each file in the Working tree Widget, then a commit in the Commit graph and each of its files.
2. List the marker folder after each, and record it as in A.

**C. A repository another account owns**

1. On macOS, copy `config-and-attributes` into `/Users/Shared`, then make another account own it: `sudo chown -R <another account> /Users/Shared/config-and-attributes`. On Windows, share a folder from a second disposable VM or account, put `config-and-attributes` in it, and map it as a network drive.
2. In a terminal, run `git status` in it. Note whether `git` refuses it as "dubious ownership".
3. Delete the marker folder, open the repository in Lanewise and do steps 4 to 6 of hand check A, then hand check B.
4. Record whether Lanewise opened it, what it said, and which markers were there.
