# R5 — Sandcastle

Part of Lanewise's first Pen-test round (pen-testing PRD §6, issue #31, label `prd:pen-test`). R5 asked three things. What can an issue comment make the agent do? What can the container reach on the network, and what credentials does it hold? And what review does a commit get before it reaches `main`? It starts from H14.

- **Trust boundary.** Public issue text, the agent that reads it with a credential, and the commits that come back to the owner's branch. On one side are anyone who can write an issue or a comment on `adrianeyre/lanewise`, and the text `gh` fetches into the prompt. On the other are the agent in its container, the keys `.sandcastle/.env` forwards to it, and the branch its commits are merged to on the owner's machine.
- **Governed by.** `docs/processes/running-sandcastle.md`. `CONTEXT.md`: Pen-test round, Finding, Release. Beside them, ADR 0029 (Releases by semantic-release from what's merged to `main`), ADR 0049 (code scanning) and ADR 0052 (who can change a Release's files). R3 recorded `main`'s ruleset.
- **Deliverables.** `app/scripts/sandcastle.test.ts` is new. It pins what held, and each test was checked to fail when the behaviour it holds was broken:
  - `a run refuses to start on main, before any sandbox is made`;
  - `a run's commits come back on a branch of their own, merged to the one it was launched from`;
  - `main.ts mounts no file of the host's itself but the CA certificate, and that read-only`;
  - `the agent runs as a user that isn't root`;
  - `dependencies are installed as the lockfile has them`;
  - `a run's keys, logs, worktrees and own prompts are never committed, and the example fills in no key`;
  - `no workflow starts on an issue or a comment, so public text runs nothing in Actions`.

## How it was probed

This was done from inside a Sandcastle run of this round: a Linux container on Debian 13 with Node 26 and `@ai-hero/sandcastle` 0.12.0, on the tree at `fbf939f`. The run was launched with no GitHub token, as the round's brief says (H14). No credential in the container was read, printed or used for a probe. Nothing was sent to GitHub or to any other service. No issue, comment or label was written. Nothing outside the worktree and `/tmp` was written.

1. **Read** `.sandcastle/` (`main.ts`, `Dockerfile`, `prompt.md`, `.env.example`, `.gitignore`), `docs/processes/running-sandcastle.md`, `CONTRIBUTING.md` ("Coding agents"), `.github/CODEOWNERS` and the three workflows.
2. **Read Sandcastle 0.12.0's own source** as the lockfile installs it: how a prompt's placeholders are filled and its commands are expanded (`dist/index.js:58-122`, `:659-710`), and how the Docker sandbox starts its container (`dist/chunk-CP3TYXZA.js:71-106`, `dist/sandboxes/docker.d.ts:48-55`).
3. **Read this container's mounts** from `/proc/self/mountinfo`, without writing to any of them.
4. **Broke each behaviour the new tests hold**, one at a time, in the working tree, and put each back:
   - with the guard on `main` made to test another branch name;
   - with the branch strategy `head`;
   - with the CA mounted writable;
   - with the Dockerfile's `USER` set to `root`;
   - with `--frozen-lockfile` taken off the install;
   - with `.env` taken out of `.sandcastle/.gitignore`;
   - with a value filled in for `GH_TOKEN` in `.env.example`;
   - with `issue_comment` added to `ci.yml`'s triggers.

   The test that holds each one failed, and passed again once it was put back.

Each answer below says what was shown to hold. A lead under PRD §4 isn't written in this file, whichever probe it came from.

## Probes from the brief

### 1. What an issue comment can make the agent do

**What I read.** `main.ts` takes the issue's number from the command line. A bare first argument must be all digits (`.sandcastle/main.ts`, `firstIsIssue`). The owner types it, and nothing public chooses it. `prompt.md:26` and `:30` fetch the issue's body and its comments with `gh issue view` inside the container, and `prompt.md:28` tells the agent they "can refine or overrule the body".

Sandcastle first marks the prompt file's own command blocks with a control character, and only then fills in `{{ISSUE}}` and the branches (`dist/index.js:701-706`). It strips that character from every value it fills in. It runs only the marked blocks, in one pass, and splices their output in without reading it again for commands (`:65-122`). `.github/workflows/` has no workflow that starts on an issue, a comment or a discussion.

**Answer.** What held:

- Nothing in an issue or a comment is run as a command by the harness. A command written in a comment is not expanded: only the committed prompt's own blocks run, before the issue's text is in the prompt.
- No GitHub Actions workflow runs on an issue or a comment.

Both are pinned, the second by `no workflow starts on an issue or a comment…`.

Not settled here: the issue's text and its comments reach the agent as part of its brief, as H14 says. What follows from that isn't written in this file (PRD §4).

### 2. What the container can reach on the network, and what credentials it holds

**What I read.**

- **Network.** `main.ts` gives `docker()` no `network` (`.sandcastle/main.ts:169`), so Sandcastle starts the container on Docker's default bridge (`docker.d.ts:53`). `running-sandcastle.md` relies on that bridge so that a Gateway at a private address can be reached.
- **Credentials.** The container is given exactly the keys `.sandcastle/.env` names: a Claude credential (`CLAUDE_CODE_OAUTH_TOKEN` or `ANTHROPIC_API_KEY`), `GH_TOKEN`, and optionally `ANTHROPIC_BASE_URL` (`running-sandcastle.md`, "Keys"). They are passed as `-e` flags on `docker run` (`chunk-CP3TYXZA.js:71-74`). `.env` is ignored in `.sandcastle/.gitignore` and in the root `.gitignore`, and `.env.example` fills in none of them.
- **Files.** `main.ts` mounts only the host's CA certificate, read-only, and only when `NODE_EXTRA_CA_CERTS` names one (`main.ts:40`). Sandcastle mounts the run's worktree, and the Git directory a worktree needs.
- **The image.** The agent runs as the non-root `agent` user (`Dockerfile:84`). Dependencies are installed with `--frozen-lockfile` (`main.ts:63`).

**Answer.** What held, and is pinned: the harness's own mount is the CA alone, and read-only. The agent isn't root. Dependencies are the lockfile's. No key is ever committed from `.sandcastle/`. Which tokens a run holds, and what each can do, is set by the owner on the host: hand check A. The rest isn't written in this file (PRD §4).

### 3. What review a commit gets before it reaches `main`

**What I read.**

- **Where the commits land.** `main.ts` refuses to start on `main` before any sandbox is made (`:152`). The branch strategy is `merge-to-head` (`:177`), so the agent works on a branch of its own in its own worktree, and its commits are merged to the branch the owner launched from, on the owner's machine. The sandbox can't push (`running-sandcastle.md`, "What a sandbox here cannot do").
- **Before it's merged.** The owner pushes that branch and opens the pull request. `CONTRIBUTING.md` says agents' pull requests "are reviewed as anyone's are, and a human merges them". `.github/CODEOWNERS` names `@adrianeyre` for every path. Every pull request runs `ci.yml` on Ubuntu, Windows and macOS, and CodeQL (ADR 0049).
- **On `main` itself.** R3 recorded `main`'s ruleset as `deletion` and `non_fast_forward`, with classic branch protection off.

**Answer.** What held, and is pinned: no run starts on `main`, and a run's commits only ever arrive on a branch of their own, merged to the launch branch on the owner's machine. From there they reach `main` only through a push or a merge the owner makes, and CI and CodeQL run on the pull request. What `main` itself requires before a merge is R3's hand check A. Applying it to agents' pull requests is hand check B.

## Hand checks (need the owner)

**A. The tokens a run holds**

1. On the machine you run Sandcastle from, open `.sandcastle/.env`. Note each key it names.
2. For `GH_TOKEN`, open GitHub → **Settings → Developer settings → Personal access tokens → Fine-grained tokens**, and open the token you use. Check that its only repository is `adrianeyre/lanewise`, and that its permissions are **Issues: read** and **Metadata: read**, as `running-sandcastle.md` says. Check that it has an expiry date.
3. For the Claude credential, check it is one you'd revoke on its own, and where you'd revoke it.
4. Write the date in H14's row above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).

**B. Review before `main`**

1. Do R3's hand check A, and keep its notes.
2. On the next pull request made from a Sandcastle branch, check that every commit on it was read before it was merged, and that `ci.yml` and CodeQL passed.
3. Write the date in H14's row above. File anything that doesn't hold as PRD §7 says, privately first (PRD §4).
